# 08 - 配置与部署

## 配置方式

根目录 `.env` 与部署环境仍是系统配置、敏感配置和所有配置的启动初始值来源；`config/config.py` 已废弃（`config/config-example.py` 仅留作历史参考）。阶段 7 配置核心新增 `app_settings` 数据库单例，仅允许保存注册表中明确标记为可热更新、非敏感且无需重启的覆盖值。生产 Web 部署仍由 `deploy/inktime-server.service` 和 `deploy/docker-compose.yml` 明确覆盖 `APP_ENV=production`。

```bash
cp .env.example .env
vi .env
```

四个入口脚本（分析、两个渲染、Web 应用工厂）都会自行 `load_dotenv()` 读取项目根的 `.env`。Web 应用已把统一配置服务注册为实例级共享依赖：后台配置页面、公开设置兼容层、展示模板、展示选片和信息面板会在每次请求时检查数据库版本并热读取。独立工作进程使用同一配置服务，并在后台任务首次认领时固化 `analysis`、`render` 或 `worker` 作用域快照；后续执行、租约恢复和重试均沿用该快照。

### 优先级

```text
可热更新配置：app_settings 数据库值 > 进程启动时捕获的环境初始值 > 注册表默认值
系统与敏感配置：进程启动环境值 > 注册表默认值
```

`src/configuration.py` 的注册表集中声明类型、范围、枚举、是否敏感、是否可编辑、是否需要重启和生效范围。服务每次读取先检查数据库全局版本，版本变化时才重载完整 JSON；管理写入必须携带期望版本，整批校验通过后配置、版本和审计才会在同一事务提交。未知键、字符串冒充数字或布尔值、非法枚举、越界值、系统项和敏感项都会使整批零写入。全部提交值与当前有效值相同时不递增版本，也不写空审计。

敏感项在管理视图中只显示“已配置/未配置”，真实值不得写入数据库、审计、任务快照或日志。系统项和需要重启的配置只允许通过部署环境修改。

管理员登录后可使用 `GET/POST /admin/settings` 管理在线配置；JSON 调用方使用 `GET/PATCH /api/admin/settings`，更新体包含整数 `expected_version` 和对象 `changes`。`GET /api/admin/settings/audit?limit=50` 返回脱敏审计。所有管理员写入口均要求跨站请求伪造令牌，过期版本返回 HTTP 409。公开 `POST /api/settings` 仍保持历史模拟响应，不会写入真实配置。

### 阶段 7 配置数据库升级

迁移 0036 至 0043 创建 `app_settings`、`app_settings_audit` 和审计时间索引，并为 `admin_jobs`、`admin_maintenance_jobs` 增加 `config_version` 与 `config_snapshot_json`。旧任务初始为版本 0 和空 JSON：尚未启动的任务会在首次认领时补写完整作用域快照；升级前已经启动的任务在恢复或重试时继续保持 `0/{}`，并按当前配置兼容执行。其他损坏或版本不一致的快照不会回退，而是稳定失败为 `invalid_config_snapshot`。

### 阶段 8 渲染期望代次数据库升级

迁移 0044 为 `display_artifact_state` 增加 `desired_generation`，迁移 0045 根据现有 `blocked` 与 `generation` 回填期望代次。当前代码结构目标因此提升到 45；历史正式库只读验收仍停留在 43，尚未执行这两条迁移。部署前必须停止 Web 服务和工作进程，先用 SQLite backup API 备份并在副本演练 `43→45`，再显式迁移受控目标库；旧代码不了解业务代次栅栏，不支持与新代码滚动混跑。

迁移、`check-schema`、Web 服务与后台工作进程共享严格迁移历史门禁：本地迁移文件必须恰好连续为 1 至 45，完整数据库台账版本集合必须恰好为 1 至 45，且每个版本的名称与 SQL 文件 SHA-256 校验值必须匹配。迁移命令允许缺少已知版本以便补齐，但会在执行任何待迁移 SQL 前拒绝未来版本和分叉身份；高版本数据库必须升级程序，不能让旧程序继续写入。

本轮已在临时目录完成 `35→43→35→43` 恢复演练：首次迁移后严格 `verify` 通过；恢复到版本 35 后，`integrity_check=ok`、`foreign_key_check=0`，照片身份不变量与基线一致；再次迁移到版本 43 后严格 `verify` 通过。备份由 SQLite backup API 创建，目标切换为可独立恢复的 DELETE 日志模式。正式 `data/photos.db` 本轮只执行只读 `check-schema`，输出目标版本 43、迁移数量 43、最大迁移版本 43、`schema_current=true`；未对正式库执行写入迁移。

应用工厂的显式覆盖仍只用于临时数据库验证或嵌入调用，例如：

```python
from src.server.app import create_app

application = create_app({
    "DB_PATH": "/tmp/inktime-validation.db",
    "TESTING": True,
    "SECRET_KEY": "仅供当前临时验证的非生产值",
    "SESSION_COOKIE_SECURE": False,
})
```

### 管理员安全配置

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| APP_ENV | development | 只允许 `development`、`testing`、`production`；其他值拒绝启动。systemd 与 Docker 的 Web 服务部署文件强制为 `production` |
| SECRET_KEY | 空 | 开发模式为空时仅在当前进程生成随机密钥且不记录；生产必须显式配置非空随机值，否则拒绝启动 |
| SESSION_COOKIE_HTTPONLY | True | 禁止客户端脚本读取会话 Cookie |
| SESSION_COOKIE_SAMESITE | Lax | 默认限制跨站携带会话 Cookie |
| SESSION_COOKIE_SECURE | 开发 False / 生产 True | 生产必须为 `True`，即使显式配置 `False` 也拒绝启动 |
| PERMANENT_SESSION_LIFETIME | 28800 | 永久会话有效期，单位秒 |
| WTF_CSRF_TIME_LIMIT | 3600 | 跨站请求伪造 token 有效期，单位秒 |
| ADMIN_LOGIN_MAX_FAILURES | 5 | 同一用户名和客户端地址组合的连续失败阈值 |
| ADMIN_LOGIN_FAILURE_WINDOW_SECONDS | 300 | 进程内连续失败窗口，单位秒 |

真实 `SECRET_KEY` 只写入部署环境或未入库的 `.env`，不得写入仓库、日志或文档。

### 迁移与创建管理员顺序

1. 先按现有备份流程生成一致性副本和基线。
2. 对明确指定的副本运行 `scripts/database_admin.py migrate` 和严格 `verify`，确认完整连续应用迁移 0001 至 0045，结构、外键和照片身份基线均通过。
3. 审批后对受控目标库显式执行 `migrate`，并使用同一迁移前基线运行严格 `verify`。
4. 对目标库执行只读 `check-schema`，确认常驻服务启动门禁通过。
5. 确认目标环境的 `DB_PATH`、`APP_ENV`、`SECRET_KEY` 和目录权限后，按需交互创建管理员：

```bash
./venv/bin/flask --app src.server.app create-admin
```

命令交互读取用户名，隐藏输入并二次确认至少 12 个字符的密码；不会输出密码或哈希，也不会自动创建默认管理员。

### 编写 .env 的两个坑

- **含空格的值必须加引号**：`PROJECT_NAME="InkTime 相册"`。不加引号时
  `source .env` 会把值当命令执行，报 `相册: 未找到命令`。python-dotenv 和 systemd
  都能正确处理引号
- **`FONT_PATH` 留空等于没配字体**：空值会被解析成 `Path(".")`，
  `ImageFont.truetype(".")` 抛异常后静默退回 PIL 默认位图字体，中文全部渲染成豆腐块
  且不报错。必须显式指向一个中文字体文件

### 上传与 worker 配置

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| UPLOAD_MAX_FILES | 10 | 每批最大文件数 |
| UPLOAD_MAX_BYTES | 20971520 | 单文件最大字节数 |
| UPLOAD_MAX_PIXELS | 80000000 | 解码后最大像素数 |
| JOB_MAX_ATTEMPTS | 3 | 最大尝试次数 |
| JOB_LEASE_SECONDS | 120 | 任务租约秒数 |
| JOB_RENEW_SECONDS | 30 | 续租间隔秒数 |
| JOB_POLL_SECONDS | 2 | 空队列轮询间隔 |

独立 worker 入口为 `python -m src.analysis.run_worker`。它与 Web 服务读取相同的默认值和 `DB_PATH`；`JOB_MAX_ATTEMPTS` 会传给所有任务创建路径，固定上限仍为 3。Web 与 worker 启动都会拒绝 `JOB_RENEW_SECONDS >= JOB_LEASE_SECONDS`。运行账号需要写入上传目录、照片目录与 SQLite 数据库。Docker Compose 已定义常驻 `inktime-worker` 服务，systemd 已定义 `inktime-worker.service`；两者都依赖只读数据库结构门禁成功，不能把 worker 放入 Waitress Web 进程。当前尚未执行 Docker 实机构建或启动，也未在 Linux systemd 主机实机安装或启动。

历史最终文件摘要通过受认证且受跨站请求伪造保护的 `POST /api/admin/jobs/backfill-content-hash` 创建。可传 `{"limit": 1000}`；重复活跃任务自动跳过。任务优先级低于上传、重新分析和旁白任务，可取消、可在工作进程停止后恢复，不调用视觉语言模型。

| 配置项 | 默认值 | 严格范围 | 说明 |
|--------|--------|----------|------|
| TRASH_RETENTION_DAYS | 30 | 1–3650 | 回收站只读预览和清理任务的默认保留天数 |

`.env.example` 是正式示例来源；`config/config.py` 与 `config/config-example.py` 仅同步保留历史参考值。
Web 应用和 `python -m src.analysis.run_worker` 都会严格解析范围，非法值拒绝启动，不会静默夹取。

工作进程现在同时轮询照片任务和独立维护任务。维护任务沿用 `JOB_MAX_ATTEMPTS`、
`JOB_LEASE_SECONDS`、`JOB_RENEW_SECONDS` 和 `JOB_POLL_SECONDS`，但数据保存在
`admin_maintenance_jobs`，不修改阶段 5 `admin_jobs` 的任务类型检查约束。软删除后
`render_display` 维护任务优先级高于照片分析；其临时目录位于 `BIN_OUTPUT_DIR` 内，确保
`os.replace` 与正式产物处于同一文件系统。清理任务按固定截止时间和稳定照片编号分批续排。

部署升级时先对 `/tmp` 或一致性备份副本应用 0024 至 0035，并检查
`PRAGMA integrity_check`、`PRAGMA foreign_key_check`、单例产物状态和新字段；确认后再安排正式库迁移。
正式升级前后都不需要删除或手工处理 `photos.db-shm`、`photos.db-wal`。

```bash
cd /path/to/InkTime

# 系统依赖（Linux）；缺 exiftool 不致命，但 GPS 会不全
```

验证：

```bash
exiftool -ver
./venv/bin/python -c "import flask, requests, PIL, dotenv; print('deps ok')"
./venv/bin/python -c "import waitress; print('waitress ok')"
```

### 配置

```bash
cp .env.example .env
# 至少设置 IMAGE_DIR、API_URL、MODEL_NAME、API_KEY、FONT_PATH、DOWNLOAD_KEY
```

### 运行

```bash
# 1. 分析照片（先小批量验证 prompt 效果）
BATCH_LIMIT=20 ./venv/bin/python src/analysis/analyze_photos_docker.py
# 或用封装脚本（自动加载 .env、用 venv python）
./scripts/run_analysis.sh

# 2. 全量分析（可随时中断，按 path 去重续跑）
nohup ./venv/bin/python src/analysis/analyze_photos_docker.py > logs/analyze_full.log 2>&1 &

# 3. 渲染今日照片

# 4. 启动服务器（开发用；生产见下方 systemd）
./venv/bin/python src/server/server.py
```

数据库结构由版本化迁移维护。运行分析前先执行 `scripts/database_admin.py migrate`，并且首次迁移必须指向活动数据库的一致性备份副本；分析入口只检查结构，不会在启动时静默补表。

### 回填存量数据

改了日期兜底规则或类型规范化规则后，存量照片不会自动跟上（分析脚本按 `path`
去重会跳过已分析照片）。用回填脚本处理，它不调用 VLM、不花额度：

```bash
./venv/bin/python scripts/backfill_metadata.py          # 预览，不写库
./venv/bin/python scripts/backfill_metadata.py --apply  # 实际写入
```

回填 `exif_datetime`、`date_source`、`exif_json.datetime`、`type` 四项。
执行前建议备份：`cp data/photos.db "data/photos.db.$(date +%F)"`。


## Docker Compose 部署

Dockerfile 默认运行 `python -m src.server.run_server`。`deploy/docker-compose.yml` 定义六个服务，除结构门禁自身外，所有运行入口都通过 `condition: service_completed_successfully` 等待 `inktime-schema` 成功：

| 服务 | 类型与命令 | 照片目录 | 重启策略 |
|------|------------|----------|----------|
| `inktime-schema` | 一次性 `database_admin.py check-schema` | 不挂载 | `"no"` |
| `inktime-server` | 常驻 `python -m src.server.run_server` | 读写 | `unless-stopped` |
| `inktime-worker` | 常驻 `python -m src.analysis.run_worker` | 读写 | `unless-stopped` |
| `inktime-analyzer` | `tools` profile 一次性分析 | 只读 | 不自动重启 |
| `inktime-render-7c` | `tools` profile 7.3 寸四色渲染 | 只读 | 不自动重启 |
| `inktime-render-133c` | `tools` profile 13.3 寸六色渲染 | 只读 | 不自动重启 |

六个服务使用同一 Dockerfile 和 `.env`。schema 仅挂载 `data/`；其余服务挂载 `data/` 与 `logs/`。Web 服务和后台工作进程因上传、软删除、恢复与回收站清理需要读写 `${IMAGE_DIR}`，三个工具服务使用只读照片挂载。数据库固定为 `/app/data/photos.db`，输出固定为 `/app/data/output`，宿主 `IMAGE_DIR` 必须是绝对路径，并在容器内保持同一路径。

```bash
# 仅展开配置；构建与启动前应先人工确认输出
DOCKER_BUILDKIT=1 docker compose --env-file .env -f deploy/docker-compose.yml config
DOCKER_BUILDKIT=1 docker compose --env-file .env -f deploy/docker-compose.yml build

docker compose --env-file .env -f deploy/docker-compose.yml up -d \
  inktime-schema inktime-server inktime-worker
docker compose --env-file .env -f deploy/docker-compose.yml --profile tools run --rm inktime-analyzer
docker compose --env-file .env -f deploy/docker-compose.yml --profile tools run --rm inktime-render-7c
docker compose --env-file .env -f deploy/docker-compose.yml --profile tools run --rm inktime-render-133c
```

<callout emoji="⚠️" background-color="light-yellow">SQLite 数据库不能放在服务器消息块或网络文件系统共享目录上。若数据库照片绝对路径与容器挂载路径不一致，工具可能把照片判断为不存在；必须先运行 preflight。当前尚未执行 Docker 实机构建或启动验证。</callout>

## systemd 三单元部署

仓库提供三个实际单元：

| 单元 | 类型与入口 | 依赖 | 停止超时 |
|------|------------|------|----------|
| `inktime-schema.service` | `Type=oneshot`；`database_admin.py check-schema`；`RemainAfterExit=yes` | 网络就绪 | 未显式配置 |
| `inktime-server.service` | `python -m src.server.run_server` | `Requires/After=inktime-schema.service` | 30 秒 |
| `inktime-worker.service` | `python -m src.analysis.run_worker` | `Requires/After=inktime-schema.service` | 150 秒 |

三个单元均设置 `NoNewPrivileges=true`、`PrivateTmp=true`、`ProtectSystem=full`、`RestrictSUIDSGID=true` 和 `UMask=0077`。Web 服务显式设置 `APP_ENV=production`；后台工作进程从 `.env` 读取环境。按部署环境修改 `User`、`Group`、`WorkingDirectory`、`EnvironmentFile`、`PYTHONPATH` 与虚拟环境路径，运行账号必须可读写数据库、输出目录和照片目录。

## 定时任务

### 每日渲染（crontab）

```bash
chmod +x scripts/daily_render.sh
crontab -e
# 加入（每天凌晨 5 点渲染）
0 5 * * * /home/work/InkTime/scripts/daily_render.sh
```

改 crontab 前先备份：`crontab -l > ~/crontab.backup.$(date +%F)`。

### daily_render.sh 说明

- `PROJECT_DIR` 按脚本自身位置自动推导，不需要手改路径
- 用目录锁（`mkdir tmp/inktime_render.lockdir`）防止并发执行，
  重复触发会写入 `another render is running, skip.` 并以 0 退出
- `trap cleanup EXIT INT TERM` 保证异常退出时释放锁
- 检查 venv 与 `.env` 是否存在（旧版检查的是 `config.py`）
- 日志输出到 `logs/render.log`

### 验证

```bash
./scripts/daily_render.sh && tail -20 logs/render.log
# 连续跑两次，第二次应输出 "another render is running, skip."
crontab -l | grep daily_render
```

cron 的环境变量极少（PATH 通常只有 `/usr/bin:/bin`），建议按 cron 环境实测一次：

```bash
env -i HOME="$HOME" LOGNAME="$USER" PATH=/usr/bin:/bin SHELL=/bin/sh \
  /home/work/InkTime/scripts/daily_render.sh
```

脚本内部使用绝对路径的 venv python 并自行加载 `.env`，因此不依赖 PATH。

## 安全建议

1. **DOWNLOAD_KEY**：改成随机字符串，防止照片被随意访问
2. **同步 ESP32**：修改 DOWNLOAD_KEY 后，同步修改固件中的 `DAILY_PHOTO_PATH_PREFIX`
3. **公开与管理员访问边界**：公开相册 WebUI 与 `GET /api/photos` 等公开接口无需管理员登录；
   `/admin/*`、`/api/admin/*` 必须管理员登录，后台写请求受跨站请求伪造保护。`FLASK_HOST=0.0.0.0`
   时同网段设备仍能浏览公开照片、文案和 GPS 信息；网络环境不完全可信时应限制监听地址或增加反向代理访问控制
4. **公网部署**：必须加 HTTPS 反代（nginx）+ 鉴权，或限制内网访问
5. **WebUI**：跑通后建议关闭（`ENABLE_REVIEW_WEBUI=False`），只留 ESP32 下载接口
6. **目录浏览**：`ENABLE_FILE_BROWSER` 保持 `False`
7. **API_KEY**：如使用云端 VLM，妥善保管密钥；`.gitignore` 已包含 `.env`。
   密钥若曾出现在文档、聊天记录等处，应在平台上重置
8. **日志**：`logs/` 下的分析日志包含照片绝对路径和全部描述文案，已加入 `.gitignore`

> 改完 `.env` 需要 `sudo systemctl restart inktime-server` 才生效，
> systemd 只在启动时读一次 `EnvironmentFile`。

> `.env` 不入库，新增配置项务必同步到 `.env.example` —— 那是唯一入库的配置模板。
> 模板里值含空格必须加引号（如 `PROJECT_NAME="InkTime 相册"`），否则 `source` 会报错。
