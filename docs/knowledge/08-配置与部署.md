# 08 - 配置与部署

## 配置方式

基础 `deploy/docker-compose.yml` 面向可信家庭局域网，无需根目录 `.env` 即可启动。它固定使用 `/app/data/photos.db`、`/app/data/photos`、`/app/data/output`，并设置 `APP_ENV=development`、普通 HTTP 和 `SESSION_COOKIE_SECURE=False`。根目录 `.env` 现在是本地运行、模型接入、外部照片目录以及公网或生产部署的高级覆盖来源，不再是基础 Compose 的启动前提；`config/config.py` 已废弃（`config/config-example.py` 仅留作历史参考）。

公网或生产环境必须使用 Compose override 或部署环境同时覆盖 `APP_ENV=production`、`SESSION_COOKIE_SECURE=True`，并置于 HTTPS 反向代理之后；可以显式设置运行时密钥和首次管理员令牌。systemd 的 Web 服务仍明确使用生产模式。

四个入口脚本（分析、两个渲染、Web 应用工厂）都会在文件存在时自行 `load_dotenv()`，且不覆盖已有进程环境。Web 应用已把统一配置服务注册为实例级共享依赖：后台配置页面、公开设置兼容层、展示模板、展示选片和信息面板会在每次请求时检查数据库版本并热读取。独立工作进程使用同一配置服务，并在后台任务首次认领时固化 `analysis`、`render` 或 `worker` 作用域快照；后续执行、租约恢复和重试均沿用该快照。

### 优先级

```text
可热更新配置：app_settings 数据库值 > 进程启动时捕获的环境或 .env 初始值 > 注册表默认值
锁定的一般配置：显式进程环境 > 项目 .env > 注册表默认值
SECRET_KEY / DOWNLOAD_KEY：显式进程环境或应用覆盖 > 数据库同目录持久化密钥文件
```

`src/configuration.py` 的注册表集中声明类型、范围、枚举、是否敏感、是否可编辑、是否需要重启和生效范围。服务每次读取先检查数据库全局版本，版本变化时才重载完整 JSON；管理写入必须携带期望版本，整批校验通过后配置、版本和审计才会在同一事务提交。未知键、字符串冒充数字或布尔值、非法枚举、越界值、只读项和需重启项都会使整批零写入。全部提交值与当前有效值相同时不递增版本，也不写空审计。

Web 进程构造配置服务时，先取进程环境中的注册表键，再用 Flask 配置覆盖同名键。分析与渲染类配置不存在于 Flask 配置中，因此其启动初始值直接来自 `.env`，后台配置页不会把它们显示成注册表默认值，也不会在保存时用默认值覆盖 `.env` 的真实值。

代价是「启动值」这一来源里混了 Flask 配置默认值：注册表 70 个键在 `app.config` 中全部存在，因此 `_resolved()` 对未被在线覆盖的项一律返回 `environment`，它并不表示部署方真设过这一项。为了让配置页能区分两者，`ConfigurationService` 另接一个可选参数 `environment_keys`，Web 进程只传真正出现在 `os.environ`（含 `_load_environment_file()` 载入的 `.env`）里的键；不传时退化为初始值映射的全部键，兼容直接传 `os.environ` 的工作进程与扫描脚本。管理视图据此输出 `from_environment` 与 `environment_overridden`，供页面提示「值由部署环境设置」与「环境变量已被在线配置压住」。

「全部提交值与当前有效值相同则不写库」是相对**发起写入的那个进程**的有效值判断的。正常部署下 Web 与工作进程读同一份 `.env`，两者有效值一致，这条过滤没有歧义。但若给两个进程配置了不同的环境变量，则可能出现：管理员提交的值恰好等于 Web 进程的环境值而被判为无变化、不落库，工作进程却仍在用它自己的环境值。因此不要给 Web 与工作进程配置不同的 `.env` 或环境覆盖。

### 多照片目录

`IMAGE_DIR` 支持分号分隔的多个目录，值中没有分号时与单目录完全等价，现有 `.env` 与数据库配置无需改动。分隔符选分号而非冒号，避免与 Windows 盘符冲突，也让含空格的路径无需转义。

```bash
# 单目录，与改造前一致
IMAGE_DIR=/home/me/pic

# 多目录，第一个是主目录
IMAGE_DIR=/home/me/pic;/mnt/nas/album;/mnt/usb/photos
```

| 规则 | 说明 |
|------|------|
| 主目录 | 列表第一个目录。上传的照片、`.upload-staging` 暂存、照片文件锁只写主目录，其余目录只读扫描 |
| 不得嵌套 | 任意两个目录不能是父子关系，也不能相同；比较在 `resolve()` 之后进行，因此指向另一个目录内部的符号链接同样被拒绝 |
| 自动去重 | 指向同一位置的重复配置按首次出现顺序保留一份 |
| 必须可用 | 后台保存时逐个校验存在、是目录且可读，任一不满足整批拒绝 |
| 按根回收站 | 每个目录各自生成 `.trash`，软删除、恢复、永久删除都只在照片所属目录内进行 |

`parse_image_dirs()` 是唯一的解析入口，写入路径以 `require_existing=True` 强校验，运行期读取只做结构校验，避免网络存储临时不可用导致服务整体不可读配置；解析失败时各服务回退到进程启动时的目录列表并记录错误日志。后台配置页顶部有「照片目录状态」表，展示每个目录的角色、可用性与照片数量，便于确认多目录是否都真的生效。

嵌套之所以必须拒绝，是因为同时配置 `/photos` 与 `/photos/private` 时，`/photos/private/.trash/1/x.jpg` 对第一个根来说不在 `/photos/.trash` 下，会被当成合法的活动照片，导致已删除照片通过公开接口泄露。按根建 `.trash` 则是因为软删除用 `os.link()` 加 `os.unlink()` 实现原子移动，硬链接不能跨文件系统：若照片在网络存储、回收站在本地磁盘，软删除会直接抛 `Invalid cross-device link`。

批量分析脚本 `analyze_photos_docker.py` 的「文件缺失同步」会一次扫描全部配置目录，`LIKE` 条件按目录数量展开为多前缀。若任一配置目录当前不可用，则整体跳过该同步并打印警告，避免把该目录下的照片误标为 `source_file_missing`、从此不再参与选片。

Docker 部署要注意：基础 Compose 的 `/app/data/photos` 已包含在宿主 `data/` 到 `/app/data` 的绑定挂载中，无需额外照片卷。后台在线修改 `IMAGE_DIR` 只会改变应用配置，不会创建容器挂载，因此只能选择容器已经可见、存在且可读的目录。

外部照片库必须使用 Compose override 逐个显式挂载。Web 服务与后台工作进程需要读写，三个工具服务可按用途只读；所有会消费数据库照片路径的容器必须使用一致的容器内绝对路径。宿主路径可以不同于容器路径，例如把 `/srv/family-photos` 挂载为统一的 `/photos/family`。只挂载到 Web 容器可能让后台保存成功，但工作进程随后仍会因目录不可见而失败。

### 展示页生效时间段

展示页默认全天轮播。配置 `DISPLAY_ACTIVE_WINDOWS` 后，只在生效时间段内轮播与记账，段外既不切换画面也不累加 `display_stats.show_count`，避免夜间无人观看时白白消耗照片。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `DISPLAY_ACTIVE_WINDOWS` | 空 | 分号分隔的 `星期@HH:MM-HH:MM`，星期可省略表示每天；留空表示全天生效 |
| `DISPLAY_IDLE_MODE` | `freeze` | 段外画面：`freeze` 停在最后一张、`photo` 固定照片、`rest` 显示文案 |
| `DISPLAY_IDLE_PHOTO_ID` | 0 | `photo` 模式的照片编号，照片不可用时回退 `freeze` |
| `DISPLAY_REST_TEXT` | 休息中 | `rest` 模式的文案 |

格式规则：星期写 `Mon` 到 `Sun`（大小写不敏感）或 `1` 到 `7`（1 为周一），范围用 `-`、列表用 `,`；时间为 24 小时制，允许 `24:00` 作为结束边界；区间左闭右开；跨零点自动拆分且**后半段归属次日星期**（`Fri@22:00-01:30` 即周五夜到周六凌晨）；重叠或相邻区间在同一星期内合并；非法写法在保存时整批拒绝。

判定在服务端完成，使用服务器本地时间。**不能交给前端判断**：展示页常跑在电子相框、旧平板等时钟与时区不准的设备上，前端判断会让休息时段整体偏移，而且前端仍会发请求、记账照旧发生。段外 `GET /api/display/next` 返回 `status=idle`，带 `idle_mode`、`resume_at` 与 `next_check_after_sec`（退避上限 300 秒），前端据此低频轮询等待恢复，最多五分钟内感知配置变更。`freeze` 模式的画面取自 `display_stats.last_shown_at` 最新一条，因此休息期刷新页面仍能显示停留的那张；没有任何展示历史时退化为 `rest`。

### 后台任务失败重试

任务失败后不会立即重试：`claim_next` 增加了时间门禁，`attempts > 0` 的任务必须距上次失败超过退避时长才可再被认领。退避以 `JOB_RETRY_BACKOFF_SECONDS`（默认 30 秒）为基数按尝试次数指数增长，即 30 秒、60 秒；设为 0 恢复立即重试。

这条门禁复用现有的 `updated_at` 字段（`fail_attempt` 每次失败都会刷新它），**不新增数据库列、不需要迁移**。

之所以必须有退避：原先 `fail_attempt` 把任务打回 pending 后，工作循环下一圈会立刻重新认领——只有队列为空才等待轮询间隔。实际事故表现为模型接口瞬时返回 400 时，三次尝试在 3 秒内烧光，第三次还撞上上游 429 限流，那次限流基本是自己打出来的，照片随即被永久标记失败、只能人工重试。

人工重试不受退避约束：`retry()` 会清空 `error_code`，门禁据此与自动重排队区分开——退避是为了防止自动重试把上游打爆，管理员主动点重试就该立刻执行。

配套三处可观测性修复：模型接口返回非 2xx 时，响应正文（截断 300 字）会带进异常消息，经 `LOGGER.exception` 落到日志，并写入 `admin_jobs.error_summary` 直接展示在后台任务页（原先只有「后台处理失败」加异常类名，真实原因只能翻日志）；systemd 单元与 Docker Compose 全部服务增加 `PYTHONUNBUFFERED=1`，否则脚本里的 `print` 在长驻进程中受 stdout 块缓冲影响，诊断信息写了却拿不到（`logging` 走 stderr 不受影响）。

### 展示页天气

展示页可显示当前天气，默认**关闭**（`WEATHER_ENABLED=false`），关闭时不会向外部服务发起任何请求。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `WEATHER_ENABLED` | `false` | 总开关 |
| `WEATHER_PROVIDER` | `open-meteo` | 数据源，免注册免 API key |
| `WEATHER_LOCATION` | 空 | `纬度,经度`；留空回落 `HOME_LAT`/`HOME_LON` |
| `WEATHER_LOCATION_NAME` | 空 | 展示用地名，留空不显示 |
| `WEATHER_CACHE_MINUTES` | 15 | 服务端缓存时长 |
| `DISPLAY_WEATHER_SHOW` | `true` | 仪表盘模板是否显示天气块 |
| `DISPLAY_WEATHER_CORNER` | `false` | 沉浸式模板是否显示右上角天气角标 |

数据源为 Open-Meteo，免注册免密钥，按位置自动选最优预报模型（国内位置会用到中国气象局 CMA GRAPES）。返回 WMO 天气代码，中文与图标映射维护在 `src/server/weather.py` 的 `WEATHER_CODES`。

位置默认复用照片分析已在用的常驻地坐标 `HOME_LAT`/`HOME_LON`，因此通常不需要额外配置；`WEATHER_LOCATION` 可覆盖，写入时校验格式与经纬度范围。**坐标会发送给第三方天气服务**，Open-Meteo 无需账号所以请求是匿名的，介意的话只填到小数点后一位（约 11 公里精度）。

降级是硬要求：天气是本项目除历史事件数据源（默认百度百科）与模型接口之外唯一的外网依赖，请求超时 5 秒，任何异常都返回 `{"available": false}` 而不向上抛出，日期、农历、历史上的今天与照片展示均不受影响。曾成功取过数则在后续失败时返回上次结果并标注 `stale` 与获取时间，超过 6 小时不再展示。服务端缓存默认 15 分钟，单实例每天约 96 次外部请求。

两套模板的天气元素**由服务端按开关条件渲染**，元素不存在时前端连一次请求都不会发，因此沉浸式模板默认关闭天气就是真的零开销。

### 上传格式与压缩

上传受理五类内容格式：JPEG、MPO、PNG、WebP、HEIF。

| 内容格式 | 落盘格式 | 说明 |
|----------|----------|------|
| JPEG | JPEG | 原样重新编码 |
| MPO | JPEG | 手机 HDR 与人像模式产出的「JPEG 加多帧」，取首帧 |
| PNG | PNG | 只缩放不降质，避免截图文字发虚 |
| WebP | WebP | 超过目标体积时由无损转有损 |
| HEIF / HEIC | **JPEG** | iPhone 默认格式，浏览器与墨水屏渲染链路都不支持，必须转码。依赖 `pillow-heif`，缺失时该格式会以「只支持 JPEG、PNG、WebP 和 HEIC」被拒绝，其余格式不受影响 |

**不要求扩展名与真实格式一致**。微信与浏览器另存常出现「内容是 WebP、文件名叫 `.jpg`」，这类文件手机与电脑都能正常查看，早期版本却报「图片扩展名与实际格式不一致」。落盘文件名本来就按检测出的真实格式生成，原始扩展名不影响存储正确性；真正有安全意义的是内容格式必须在白名单内，这一条保持不变。扩展名仍作为廉价前置过滤，允许 `.jpg`、`.jpeg`、`.png`、`.webp`、`.heic`、`.heif`。

多帧文件统一取首帧转为静态图，不再整张拒收：MPO 是「JPEG 加多帧」，HEIF 可能含连拍或深度图，手机相册里的动态照片也属这一类。展示与渲染链路只处理静态图，而首帧就是使用者想要的那一张。

**批次内逐文件独立处理**：某个文件不合法只让它自己失败并给出原因，同批其余文件照常入库。一次勾选十张、其中一张是动图或坏文件就要求全部重选，代价远大于让合法文件先进来。批次级限制（单批文件数超限）仍整批拒绝，因为那属于操作错误而非单文件问题。落盘文件**保留原始 EXIF**（方向标签除外，像素已固化方向，保留会导致看图软件二次旋转）：数据库只存解析结果，一旦解析逻辑有缺陷，不带 EXIF 的副本就再也无从补救，只能让使用者重新上传原片。

EXIF 提取逐字段容错，GPS 段独立降级：拍摄设备与修图软件写出的畸形字段很常见（实际遇到过 ISO 写成字节串 `b'\x00'`，`int()` 直接抛 ValueError，整张照片被当成无法解码而拒收），任何解析异常只导致对应字段缺失，不影响其余字段与照片入库。特别注意 `GPSAltitudeRef` 按 EXIF 标准是 BYTE 类型、值本来就是 `b'\x00'`，早期用 `int()` 解析它会让**每张带 GPS 的照片**都失败——改造前表现为整张被拒，加了整段兜底后表现为元数据全丢，两者都源于同一行代码。解码失败的提示会带上底层异常类型与原因（截断 150 字），否则「图片损坏或无法解码」无法区分格式不支持、文件被截断与编解码器缺失。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `UPLOAD_MAX_BYTES` | 64 MiB | 单文件上限，手机原图常有四五十兆；上界 100 MiB |
| `UPLOAD_TARGET_BYTES` | 5 MiB | 落盘目标体积，零表示不压缩 |
| `UPLOAD_MAX_LONG_EDGE` | 4096 | 落盘长边像素上限，零表示不缩放 |

压缩顺序是「先按长边缩放，再逐档降质」：先缩放能一次砍掉大部分体积，也让后续多次试编码的成本可控——五十兆原图解码后可能上亿像素，直接反复编码会很慢。实测 15 MB 的 6000×4000 照片压到 3.7 MB、4096×2731，耗时 0.8 秒。仍压不到目标时保留最小的那次尝试并写警告日志，不会因为压不下去而拒收照片。

注意 `MAX_CONTENT_LENGTH` 是派生值（单批文件数 × 单文件字节数 + 1 MiB），默认配置下为 641 MiB。它只是请求体上限，不代表内存占用；若走反向代理，需同步调大 `client_max_body_size`。

| 后台任务 | `UPLOAD_MAX_FILES`、`UPLOAD_MAX_BYTES`、`UPLOAD_MAX_PIXELS`、`UPLOAD_TARGET_BYTES`、`UPLOAD_MAX_LONG_EDGE` | 立即，下一次上传 |
| 后台任务 | `JOB_MAX_ATTEMPTS` | 立即，之后新建的任务 |
| 后台任务 | `JOB_RETRY_BACKOFF_SECONDS` | 立即，下一次认领判定 |
| 后台任务 | `JOB_LEASE_SECONDS`、`JOB_RENEW_SECONDS`、`JOB_POLL_SECONDS` | 立即，工作进程下一轮循环与下一次续租 |
| 后台任务 | `TRASH_RETENTION_DAYS` | 立即，下一次清理预览与清理任务 |

上传与任务类配置原先被固化在服务构造参数上，现在改为在方法内按需读取：`UploadService` 的三项上限、`AdminJobRepository` 与 `MaintenanceJobRepository` 的 `max_attempts`、`LibraryScanService` 的 `max_attempts`、`PhotoLifecycleService` 的 `retention_days`、`FileBrowserService` 的两个开关，以及 `AnalysisWorker`、`MaintenanceWorker`、`CombinedWorker` 的租约、续租与轮询间隔。同一次上传批次内会固定一份上限快照，避免批中途改配置导致同批文件判定不一致。

两项跨字段与派生约束需要注意：

- **续租必须小于租约**。注册表只能逐项校验，无法表达跨项约束，因此工作器在读取时兜底收敛：一旦 `JOB_RENEW_SECONDS` 不小于 `JOB_LEASE_SECONDS`，实际取租约减一秒并写告警日志。`JOB_LEASE_SECONDS` 的实际生效下界因此为 2 秒。
- **`MAX_CONTENT_LENGTH` 是派生值**，由 `单批上传文件数 × 单文件上传字节数 + 1 MiB` 得出，由 Werkzeug 在解析请求体时读取，不属于注册表配置项。Web 应用用 `before_request` 钩子在每次请求前重算，因此上传上限改大后不会再被应用启动时的旧上限拦截。

系统与网络路径类（`APP_ENV`、`DB_PATH`、`BIN_OUTPUT_DIR`、`FLASK_HOST`、`FLASK_PORT`）、安全边界类（会话与登录限流）以及 `SECRET_KEY`、`DOWNLOAD_KEY` 保持锁定，只能改 `.env` 并重启：前者指错位置会让数据整体失联，后者存在改完就再也登不进后台或设备拉不到图的自我锁定风险。照片目录是唯一放开在线编辑的路径类配置，因为它有 `parse_image_dirs()` 的强校验兜底，写错会被当场拒绝而不是静默生效。

敏感项在管理视图、接口响应与配置审计中一律只体现“已配置/未配置”或“已脱敏”，真实值不写入任何日志。`API_KEY` 是唯一可在线修改的敏感项，采用只写语义：页面用密码框提交，留空表示保持原值，填值则覆盖。它的值以明文保存在 `app_settings.settings_json` 中，信任级别与 `.env` 明文一致，因此数据库文件必须与 `.env` 同等保护；它仍然不进入任务快照，工作进程在每次调用模型时实时读取。`SECRET_KEY` 与 `DOWNLOAD_KEY` 保持只读。

管理员登录后可使用 `GET/POST /admin/settings` 管理在线配置；JSON 调用方使用 `GET/PATCH /api/admin/settings`，更新体包含整数 `expected_version` 和对象 `changes`。`GET /api/admin/settings/audit?limit=50` 返回脱敏审计。所有管理员写入口均要求跨站请求伪造令牌，过期版本返回 HTTP 409。公开 `POST /api/settings` 仍保持历史模拟响应，不会写入真实配置。

### 阶段 7 配置数据库升级

迁移 0036 至 0043 创建 `app_settings`、`app_settings_audit` 和审计时间索引，并为 `admin_jobs`、`admin_maintenance_jobs` 增加 `config_version` 与 `config_snapshot_json`。旧任务初始为版本 0 和空 JSON：尚未启动的任务会在首次认领时补写完整作用域快照；升级前已经启动的任务在恢复或重试时继续保持 `0/{}`，并按当前配置兼容执行。其他损坏或版本不一致的快照不会回退，而是稳定失败为 `invalid_config_snapshot`。

### 容器首次初始化与既有数据库升级

当前迁移集合为 0001 至 0052，`SCHEMA_TARGET_VERSION=52`。容器镜像的通用入口默认仅在 `DB_PATH` 指向的数据库文件完全不存在时执行首次迁移；已有数据库只运行严格结构检查，不会在普通启动时自动升级。入口会创建数据库父目录、输出目录和环境变量指定的照片目录，在数据库同目录创建初始化锁并请求 `0600` 权限；零字节文件和非普通文件不是新库，必须拒绝而不能覆盖。

显式设置 `AUTO_MIGRATE_ON_START=true` 可把「已有数据库仅落后若干版本」改为自动补齐：入口在初始化锁内先只读探测缺失版本，再通过 `src/database_backup.py` 的 `create_backup()` 强制创建一致性备份，只有备份成功才应用迁移，最后仍执行结构断言。已是最新时既不备份也不写库，所以重启不会堆积备份文件。未知版本、分叉历史、零字节与损坏数据库仍然一律拒绝。备份目录由 `DB_BACKUP_DIR` 决定，留空为数据库同级 `backups/`。

该开关必须在 `inktime-schema`、`inktime-server`、`inktime-worker` 上取一致的值，基础 Compose 已用 `${AUTO_MIGRATE_ON_START:-false}` 对三者统一插值；`inktime-schema` 最先执行门禁，只配置后两个服务不会生效。启用它的代价是回滚变重：自动升级后回退旧镜像必须同时恢复对应的数据库备份，否则旧程序会因未知迁移版本拒绝启动。因此生产与公网部署仍建议保持关闭，走备份、演练、显式迁移的受控流程。

应用工厂在数据库结构门禁通过后，才读取或创建数据库同目录的 `.inktime-secret-key` 与 `.inktime-download-key`。显式环境变量优先；新文件权限为 `0600`，已有文件损坏、权限向组或其他用户开放、不是普通文件或不可安全读取时拒绝启动。基础 Compose 把整个 `/app/data` 挂载到宿主 `data/`，所以数据库、默认照片、输出和密钥文件一起持久化。

全新容器与既有数据库使用两套流程：

1. **可信家庭局域网全新容器**：不需要 `.env` 或初始化令牌；只创建宿主 `data/` 与 `logs/`，不预建 `photos.db`；启动后立即访问 `/admin/setup`，局域网内首位完成设置的人创建管理员。
2. **公网或不可信网络全新容器**：使用生产覆盖启用 HTTPS、安全 Cookie 与 `APP_ENV=production`，并配置 `INITIAL_SETUP_TOKEN` 或令牌文件；设置成功后删除令牌来源并重启。
3. **既有数据库升级**：停止写入；使用 SQLite backup API 创建一致性备份和基线；在副本执行 `migrate` 与严格 `verify`；审批后对受控目标库显式执行 `migrate`；运行 `check-schema`；最后重建容器。

未配置两种初始化令牌来源时，设置页隐藏令牌字段并允许首位访问者创建管理员；配置任一来源后，令牌必须至少 24 个字符且不允许空白，页面显示必填字段并严格校验。两种来源互斥。`/admin/setup` 提交受跨站请求伪造保护；错误令牌返回 HTTP 403，成功后跳转登录页且不自动登录。只要 `admin_users` 存在任意记录，GET 与 POST 都返回 HTTP 404。

### 编写 .env 的两个坑

- **含空格的值必须加引号**：`PROJECT_NAME="InkTime 相册"`。不加引号时
  `source .env` 会把值当命令执行，报 `相册: 未找到命令`。python-dotenv 和 systemd
  都能正确处理引号

  `ImageFont.truetype(".")` 抛异常后静默退回 PIL 默认位图字体，中文全部渲染成豆腐块
  且不报错。必须显式指向一个中文字体文件

### 上传与 worker 配置

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| UPLOAD_MAX_FILES | 10 | 每批最大文件数；应用启动时规范化到 1–10 |

| UPLOAD_MAX_PIXELS | 80000000 | 解码后最大像素数；应用启动时规范化到 1–80,000,000 |
| Flask MAX_CONTENT_LENGTH | 派生值 | `UPLOAD_MAX_FILES × UPLOAD_MAX_BYTES + 1 MiB` multipart 元数据预算；超限稳定返回 HTTP 413“请求体过大” |
| JOB_MAX_ATTEMPTS | 3 | 最大尝试次数 |

| JOB_POLL_SECONDS | 2 | 空队列轮询间隔 |

独立 worker 入口为 `python -m src.analysis.run_worker`。它与 Web 服务读取相同的默认值和 `DB_PATH`；`JOB_MAX_ATTEMPTS` 会传给所有任务创建路径，固定上限仍为 3。Web 与 worker 启动都会拒绝 `JOB_RENEW_SECONDS >= JOB_LEASE_SECONDS`。运行账号需要写入上传目录、照片目录与 SQLite 数据库。Docker Compose 已定义常驻 `inktime-worker` 服务，systemd 已定义 `inktime-worker.service`；两者都依赖只读数据库结构门禁成功，不能把 worker 放入 Waitress Web 进程。Podman 指定 `linux/amd64` 的单镜像构建、容器级依赖与空库迁移检查、单 Web 容器本机启动及目标 Docker 主机导入启动已经实测；Docker Compose 六服务仍未整组实机启动，Linux systemd 主机也未实机安装或启动。

历史最终文件摘要通过受认证且受跨站请求伪造保护的 `POST /api/admin/jobs/backfill-content-hash` 创建。可传 `{"limit": 1000}`；重复活跃任务自动跳过。任务优先级低于上传、重新分析和旁白任务，可取消、可在工作进程停止后恢复，不调用视觉语言模型。

|--------|--------|----------|------|
| TRASH_RETENTION_DAYS | 30 | 1–3650 | 回收站只读预览和清理任务的默认保留天数 |

`.env.example` 是正式示例来源；`config/config.py` 与 `config/config-example.py` 仅同步保留历史参考值。

工作进程现在同时轮询照片任务和独立维护任务。维护任务沿用 `JOB_MAX_ATTEMPTS`、
`JOB_LEASE_SECONDS`、`JOB_RENEW_SECONDS` 和 `JOB_POLL_SECONDS`，但数据保存在
`admin_maintenance_jobs`，不修改阶段 5 `admin_jobs` 的任务类型检查约束。软删除后
`render_display` 维护任务优先级高于照片分析；其临时目录位于 `BIN_OUTPUT_DIR` 内，确保

## Docker Compose 部署

`deploy/docker-compose.yml` 的基础模式面向可信家庭局域网，无需 `.env` 即可启动。六个服务使用同一正式 Dockerfile；默认 `DB_PATH=/app/data/photos.db`、`IMAGE_DIR=/app/data/photos`、`BIN_OUTPUT_DIR=/app/data/output`，宿主 `data/` 整体挂载到 `/app/data`。Web 服务和后台工作进程明确使用 `APP_ENV=development`、普通 HTTP 与 `SESSION_COOKIE_SECURE=False`。

正式镜像把 `deploy/gai.conf` 安装到 `/etc/gai.conf`，保留 GNU C Library 默认地址优先级并把 IPv4-mapped 地址优先级提高到 100。双栈域名同时返回 A 与 AAAA 记录时，容器内的 `requests`、可选 OpenAI 客户端和标准库网络请求都会优先 IPv4；只有 AAAA 记录时仍会使用 IPv6，因此这不是禁用 IPv6。该默认值用于规避网络附加存储宿主 IPv6 路由不可用、Docker 桥接网络未启用 IPv6，但 DNS 仍返回 AAAA 记录造成的连接等待和地址族漂移。

这项策略随镜像生效，覆盖 Docker Compose、独立 `docker run` 和图形界面单容器，不要求修改 Docker daemon，也无需额外挂载配置文件。需要恢复系统地址排序时，切回旧版本镜像，或用部署环境自己的完整 `gai.conf` 只读覆盖 `/etc/gai.conf`。地址排序与模型业务超时相互独立：`ReadTimeout` 中的等待上限仍由后台 `TIMEOUT` 控制，思考型视觉模型应保持默认 600 秒。

可在运行容器中检查解析顺序：

```bash

  "import socket; print([(a[0].name, a[4][0]) for a in socket.getaddrinfo('dashscope.aliyuncs.com', 443, type=socket.SOCK_STREAM)])"
```

双栈目标的第一项预期为 `AF_INET`；纯 IPv6 目标仍应返回 `AF_INET6`。该检查只能验证地址排序，真实网络可达性仍需结合 TCP 连接和模型请求日志判断。

### 使用正式 Dockerfile 构建

`deploy/Dockerfile` 是 Docker 与 Podman 共用的唯一正式构建入口，不再需要创建或维护临时 Dockerfile。它提供以下构建参数：

| 构建参数 | 默认值 | 用途 |
|----------|--------|------|
| `BASE_IMAGE` | `python:3.10-slim` | Python 基础镜像，可替换为可信镜像代理中的同版本镜像 |
| `DEBIAN_MIRROR` | 空 | Debian 主仓库地址；非空时必须与安全仓库参数同时提供 |
| `DEBIAN_SECURITY_MIRROR` | 空 | Debian 安全仓库地址；非空时必须与主仓库参数同时提供 |
| `PIP_INDEX_URL` | `https://pypi.org/simple` | Python 包索引地址 |

默认使用官方源：

```bash
VERSION="$(git rev-parse --short HEAD)"
/opt/podman/bin/podman build \
  --platform linux/amd64 \
  --format docker \
  --tag "inktime:${VERSION}-linux-amd64" \
  -f deploy/Dockerfile .
```

国内网络可使用本次实测较快的镜像源。先确保目标架构的基础镜像已拉取，再使用 `--pull=never` 避免构建阶段回源：

```bash

BASE_IMAGE='docker-hub-mirror.d.xiaomi.net/library/python:3.10-slim'

/opt/podman/bin/podman pull --platform linux/amd64 "$BASE_IMAGE"
/opt/podman/bin/podman build \
  --pull=never \
  --platform linux/amd64 \
  --format docker \
  --build-arg "BASE_IMAGE=$BASE_IMAGE" \
  --build-arg DEBIAN_MIRROR=https://mirrors.tuna.tsinghua.edu.cn/debian \
  --build-arg DEBIAN_SECURITY_MIRROR=https://mirrors.tuna.tsinghua.edu.cn/debian-security \
  --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
  --tag "inktime:${VERSION}-linux-amd64" \
  -f deploy/Dockerfile .
```

本次网络测速中，Debian 主仓库速度约为：清华大学开源软件镜像站 5.20 MB/s、阿里云 3.54 MB/s、中国科学技术大学 1.31 MB/s、`deb.debian.org` 428 B/s；清华 Debian 安全仓库约 2.40 MB/s。以上是单次环境记录，不是长期性能承诺。

`DEBIAN_MIRROR` 与 `DEBIAN_SECURITY_MIRROR` 必须同时设置；只传一个时 Dockerfile 会主动失败，避免主仓库替换后安全仓库地址被错误拼接。`--platform linux/amd64` 适用于 x86_64 目标主机；其他架构应改成对应平台。正式交付前应先提交构建内容，使版本标签准确对应 Git 提交，不要只使用 `latest`。

国内网络下漏传这三个镜像源参数是最常见的构建变慢原因，且现象容易被误判成容器运行时或虚拟机性能问题。`apt-get` 安装 `libimage-exiftool-perl` 会带入大量 Perl 依赖，按 `deb.debian.org` 实测的 428 B/s 需要数小时；改用上述镜像源后整体构建约一分钟即可完成。构建明显变慢时先核对参数是否传全，不要先去调整虚拟机规格。基础镜像另需提前 `podman pull --platform` 拉取目标架构，再配合 `--pull=never` 才能避免构建阶段回源。

### 首次自动初始化、启动和创建管理员

先把三个变量改成目标 Docker 主机上的真实值。首次部署只创建目录，不要预先创建空的 `photos.db` 文件：零字节数据库会被视为异常并拒绝覆盖。Web 服务和后台工作进程必须使用同一份 `.env`、数据库目录、日志目录和照片目录挂载。

```bash

PHOTO_DIR='/path/on/host/photos'
IMAGE='localhost/inktime:replace-with-version-linux-amd64'

mkdir -p "$APP_DIR/data" "$APP_DIR/logs"
chmod 700 "$APP_DIR"
chmod 600 "$APP_DIR/.env"

# 1. 启动 Web 服务；通用入口会为不存在的数据库自动执行首次迁移
sudo docker run -d \
  --name inktime \
  --restart unless-stopped \
  --env-file "$APP_DIR/.env" \
  -e DB_PATH=/app/data/photos.db \
  -e BIN_OUTPUT_DIR=/app/data/output \
  -e IMAGE_DIR="$PHOTO_DIR" \
  -e FLASK_HOST=0.0.0.0 \
  -p 5005:5005 \
  -v "$APP_DIR/data:/app/data" \
  -v "$APP_DIR/logs:/app/logs" \
  -v "$PHOTO_DIR:$PHOTO_DIR" \
  "$IMAGE"

# 2. 启动后台工作进程，不映射 Web 端口
sudo docker run -d \
  --name inktime-worker \
  --restart unless-stopped \
  --env-file "$APP_DIR/.env" \
  -e DB_PATH=/app/data/photos.db \
  -e BIN_OUTPUT_DIR=/app/data/output \
  -e IMAGE_DIR="$PHOTO_DIR" \
  -v "$APP_DIR/data:/app/data" \
  -v "$APP_DIR/logs:/app/logs" \
  -v "$PHOTO_DIR:$PHOTO_DIR" \
  "$IMAGE" \
  python -m src.analysis.run_worker
```

通用入口在数据库同目录使用 `photos.db.initialize.lock` 串行化初始化。Web 服务与后台工作进程同时启动时，只有取得锁的首个进程会创建数据库并执行迁移，其余进程取得锁后只检查完整结构。锁文件不保存业务状态，可以随数据库目录一起持久化；容器运行期间不要手动删除。

已有且结构正确的数据库只做只读检查。已有数据库缺少迁移、包含未来版本、迁移身份分叉、文件损坏或文件为空时，容器会以非零状态退出，不会在普通启动时自动升级或覆盖；此时应按后文升级流程先备份、在副本演练，再显式迁移。

若 `.env` 中的 `FLASK_PORT` 不是 5005，端口映射右侧必须改成相同的容器端口。多照片目录需要为每个目录增加一条 `-v "宿主绝对路径:相同的容器绝对路径"`，不能把分号列表直接写成一个挂载参数。

通过宿主的 Docker 图形界面创建时，若界面支持环境变量文件，选择宿主 `.env`；不支持时，把其中键值逐项录入环境变量表。不要覆盖镜像的入口命令：通用入口负责首次数据库初始化和已有数据库结构门禁。数据目录映射到 `/app/data`，日志目录映射到 `/app/logs`，照片目录在容器内保持同一个绝对路径；Web 容器使用镜像默认命令，工作进程容器只把目标命令设置为 `python -m src.analysis.run_worker`。

Web 容器启动后，打开 `http://宿主地址:5005/admin/setup`。管理员表为空时，登录页也会显示首次设置入口。输入用户名、至少 12 个字符的密码与二次确认，以及 `.env` 或密钥文件中配置的一次性初始化令牌；创建成功后页面跳转到登录页。

管理员保存在已挂载的 `/app/data/photos.db` 中，密码只保存哈希。首个管理员创建后，`/admin/setup` 的 GET 与 POST 都永久返回 HTTP 404，即使令牌仍存在也不能创建第二个首位管理员。确认新账号能够登录后，从 `.env` 删除 `INITIAL_SETUP_TOKEN`，或卸载 `INITIAL_SETUP_TOKEN_FILE` 对应的密钥文件，然后重启 Web 容器。不要把管理员密码写入 `.env`、容器命令或日志。

### 数据持久化与镜像升级

镜像、容器可写层和持久化目录是三种不同存储：

- 镜像层只应包含程序和静态资源，不能包含业务数据库；
- 容器 `stop/start` 会保留可写层，但删除、重新创建或换镜像后可写层会消失；
- 绑定挂载或固定命名卷独立于容器，才是 `/app/data` 的正式存储位置。

如果不挂载 `/app/data`，数据库修改会进入容器可写层：停止再启动看似正常，但删除或重建容器后会丢失，并再次看到镜像内错误打包的数据。正式部署必须把整个 `/app/data` 挂到宿主固定目录或固定命名卷，不能只单独挂载 `photos.db`，因为迁移备份、预写日志和输出文件也位于该目录。

升级步骤：

1. 记录旧镜像标签、容器参数和全部挂载；
2. 停止 Web 服务和工作进程，使用 `database_admin.py backup` 创建 SQLite 一致性备份与基线；
3. 导入带新版本标签的镜像，先用备份副本执行 `migrate` 和严格 `verify`；
4. 审批后迁移正式库并执行 `check-schema`；
5. 删除旧容器但**不删除宿主目录或命名卷**，用新镜像和完全相同的挂载重建；
6. 验证管理员、照片数量、配置、任务、公开页面和后台登录后，再保留或清理旧镜像。

镜像升级不会覆盖已挂载的 `/app/data`。使用 Docker Compose 时禁止执行 `docker compose down -v`；`-v` 会删除命名卷。若新版本已经迁移数据库，回滚旧镜像可能因数据库版本过高而拒绝启动，此时必须同时恢复升级前的一致性数据库备份，不能只切回旧镜像。

## 极空间部署案例（可选）

本节只记录特定设备的兼容排障，不属于通用 Docker 部署要求。镜像构建、导入、配置、持久化和升级仍按上一节执行。

### Docker 20.10.2 的 seccomp 兼容问题

极空间旧 Docker 20.10.2 使用默认 seccomp 配置运行基于 Debian Trixie/glibc 的镜像时，普通 Python 线程也会失败：

```text
RuntimeError: can't start new thread
```

实测默认安全选项为 `apparmor` 和 `seccomp,profile=default`；加入 `--security-opt seccomp=unconfined` 后线程测试输出 `thread ok`，从而确认根因是旧 seccomp 配置未放行 glibc 使用的 `clone3`，不是内存、进程数或 InkTime 代码问题。

**优先解法是升级设备上的 Docker**：升级后原镜像无需关闭 seccomp 即可正常启动。`seccomp=unconfined` 会降低系统调用隔离，只能用于确认根因或无法升级时的临时兼容，不能作为该设备或其他 Docker 主机的默认参数。诊断时可比较：

```bash
sudo docker version --format 'client={{.Client.Version}} server={{.Server.Version}}'
sudo docker info --format 'security={{json .SecurityOptions}}'

sudo docker run --rm --network none --read-only \
  --entrypoint python localhost/inktime:722dd74-linux-amd64 \
  -c 'import threading; t=threading.Thread(target=lambda: None); t.start(); t.join(); print("thread ok")'
```

## systemd 三单元部署

仓库提供三个实际单元：

| 单元 | 类型与入口 | 依赖 | 停止超时 |
|------|------------|------|----------|
| `inktime-schema.service` | `Type=oneshot`；`database_admin.py check-schema`；`RemainAfterExit=yes` | 网络就绪 | 未显式配置 |
| `inktime-server.service` | `python -m src.server.run_server` | `Requires/After=inktime-schema.service` | 30 秒 |
| `inktime-worker.service` | `python -m src.analysis.run_worker` | `Requires/After=inktime-schema.service` | 150 秒 |

三个单元均设置 `NoNewPrivileges=true`、`PrivateTmp=true`、`ProtectSystem=full`、`RestrictSUIDSGID=true` 和 `UMask=0077`。Web 服务显式设置 `APP_ENV=production`；后台工作进程从 `.env` 读取环境。按部署环境修改 `User`、`Group`、`WorkingDirectory`、`EnvironmentFile`、`PYTHONPATH` 与虚拟环境路径，运行账号必须可读写数据库、输出目录和照片目录。

### 安装与启动

```bash
sudo cp deploy/inktime-schema.service deploy/inktime-server.service deploy/inktime-worker.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now inktime-schema inktime-server inktime-worker
```

### 部署后检查

以下命令是 Linux systemd 主机上的待执行检查清单，不代表本轮已经执行：

```bash
systemctl is-active inktime-schema inktime-server inktime-worker
systemctl is-enabled inktime-schema inktime-server inktime-worker
systemctl show inktime-server -p Requires -p After -p TimeoutStopUSec
systemctl show inktime-worker -p Requires -p After -p TimeoutStopUSec
journalctl -u inktime-schema -u inktime-server -u inktime-worker --since "10 min ago"
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8888/
```

## 定时任务

### 每日扫描新照片（crontab）

直接拷入 `IMAGE_DIR` 的照片不会自动入库，需要扫描后才会出现在后台并进入选片候选池。

```bash
chmod +x scripts/scan_library.sh
crontab -e
# 加入（每天 03:30 扫描，留出时间让工作进程完成分析）
30 3 * * * /home/work/InkTime/scripts/scan_library.sh
```

### scan_library.sh 与 run_scan 说明

- 入口是 `python -m src.analysis.run_scan`，只做发现、登记与排队；真正的分析由 `inktime-worker` 承接
- **不要用 `analyze_photos_docker` 做定时分析**：它把 `pending` 状态的照片也视为待处理对象（`filter_unscored` 只排除 `legacy` 与 `succeeded`），会与工作进程重复分析同一张照片、重复消耗模型额度
- 任务归属记录为编号最小的管理员；尚未创建管理员时以非零状态退出并提示执行 `create-admin`
- 照片目录不存在时以非零状态退出，避免静默无操作
- 用目录锁（`mkdir tmp/inktime_scan.lockdir`）防止并发，重复触发会写入 `another scan is running, skip.` 并以 0 退出
- 单次登记上限 500 张，超出会在日志提示剩余数量，由下一次扫描继续
- 日志输出到 `logs/scan.log`

与渲染任务的先后顺序：扫描安排在渲染之前，新照片才有机会在当天被选中。工作进程常驻运行，扫描完成后会立即开始分析，不必等到渲染时刻。

### 每日渲染（crontab）

```bash
chmod +x scripts/daily_render.sh
crontab -e
# 加入（每天凌晨 5 点渲染）
0 5 * * * /home/work/InkTime/scripts/daily_render.sh
```

改 crontab 前先备份：`crontab -l > ~/crontab.backup.$(date +%F)`。

### daily_render.sh 说明

- `PROJECT_DIR` 按脚本自身位置自动推导，不需要手改路径
- 用目录锁（`mkdir tmp/inktime_render.lockdir`）防止并发执行，
  重复触发会写入 `another render is running, skip.` 并以 0 退出
- `trap cleanup EXIT INT TERM` 保证异常退出时释放锁
- 检查 venv 与 `.env` 是否存在（旧版检查的是 `config.py`）
- 日志输出到 `logs/render.log`

### 验证

```bash
./scripts/daily_render.sh && tail -20 logs/render.log
# 连续跑两次，第二次应输出 "another render is running, skip."
crontab -l | grep daily_render
```

cron 的环境变量极少（PATH 通常只有 `/usr/bin:/bin`），建议按 cron 环境实测一次：

```bash
env -i HOME="$HOME" LOGNAME="$USER" PATH=/usr/bin:/bin SHELL=/bin/sh \
  /home/work/InkTime/scripts/daily_render.sh
```

脚本内部使用绝对路径的 venv python 并自行加载 `.env`，因此不依赖 PATH。

## 安全建议

1. **DOWNLOAD_KEY**：改成随机字符串，防止照片被随意访问
2. **同步 ESP32**：修改 DOWNLOAD_KEY 后，同步修改固件中的 `DAILY_PHOTO_PATH_PREFIX`
3. **公开与管理员访问边界**：公开相册 WebUI 与 `GET /api/photos` 等公开接口无需管理员登录；
   `/admin/*`、`/api/admin/*` 必须管理员登录，后台写请求受跨站请求伪造保护。`FLASK_HOST=0.0.0.0`
   时同网段设备仍能浏览公开照片、文案和 GPS 信息；网络环境不完全可信时应限制监听地址或增加反向代理访问控制
4. **公网部署**：必须加 HTTPS 反代（nginx）+ 鉴权，或限制内网访问
5. **WebUI**：跑通后建议关闭（`ENABLE_REVIEW_WEBUI=False`），只留 ESP32 下载接口
6. **目录浏览**：`ENABLE_FILE_BROWSER` 保持 `False`
7. **API_KEY**：如使用云端 VLM，妥善保管密钥；`.gitignore` 已包含 `.env`。
   密钥若曾出现在文档、聊天记录等处，应在平台上重置
8. **日志**：`logs/` 下的分析日志包含照片绝对路径和全部描述文案，已加入 `.gitignore`

> 改完 `.env` 需要 `sudo systemctl restart inktime-server` 才生效，
> systemd 只在启动时读一次 `EnvironmentFile`。

> `.env` 不入库，新增配置项务必同步到 `.env.example` —— 那是唯一入库的配置模板。
> 模板里值含空格必须加引号（如 `PROJECT_NAME="InkTime 相册"`），否则 `source` 会报错。
