# 09 - 开发指南

## 本地开发环境搭建

### 前置条件

- Python 3.10+
- VLM 服务（如 LM Studio + Qwen3-VL-32B）
- 一些测试照片

### 快速开始

```bash
# 1. 克隆项目
git clone <repo-url>
cd InkTime

# 2. 创建虚拟环境
python3 -m venv venv
source venv/bin/activate

# 3. 安装依赖（已包含固定版本 Waitress）
pip install -r requirements.txt

# 4. 本地分析或自定义部署时再创建高级覆盖配置
cp .env.example .env
# 编辑 .env：按需设置 IMAGE_DIR、FONT_PATH（模型接入改在后台「模型厂商」页建档）
# 仅启动可信家庭局域网 Docker Compose 时可跳过此步：
# docker compose -f deploy/docker-compose.yml up -d inktime-schema inktime-server inktime-worker

# 5. 数据库和路径预检
./venv/bin/python scripts/database_admin.py preflight --env-file .env

# 6. 用 SQLite backup API 创建一致性备份与身份基线
./venv/bin/python scripts/database_admin.py backup \
  --database data/photos.db --output-dir data/backups

# 7. 只在备份副本上首次演练迁移与严格验证
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/backup.db
./venv/bin/python scripts/database_admin.py verify \
  --database /absolute/path/to/backup.db \
  --baseline /absolute/path/to/backup.baseline.json

# 8. 审批后对受控目标显式迁移，再用只读门禁确认结构
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/target.db
./venv/bin/python scripts/database_admin.py check-schema --database /absolute/path/to/target.db

# 9. 准备视觉大模型：本地 LM Studio，或直接填云端 OpenAI 兼容 API

# 10. 运行分析（入口只检查当前结构，不自动迁移；建议先设 BATCH_LIMIT=3）
BATCH_LIMIT=3 ./scripts/run_analysis.sh

# 11. 启动独立后台工作进程
./venv/bin/python -m src.analysis.run_worker

# 12. 渲染
./scripts/daily_render.sh

# 13. 启动生产服务器
./venv/bin/python -m src.server.run_server
# 访问 http://127.0.0.1:5005/（端口取 .env 的 FLASK_PORT）
```

### 数据库管理与运行入口边界

| 命令 | 是否写数据库或文件 | 用途 |
|------|--------------------|------|
| `database_admin.py preflight` | 否 | 检查路径、权限、挂载点及异常照片路径 |
| `database_admin.py baseline` | 写基线 JSON | 记录迁移前照片身份与数据库状态 |
| `database_admin.py backup` | 写备份数据库和基线 JSON | 使用 SQLite backup API 创建一致性副本，并把目标切换为独立 DELETE 日志模式 |
| `database_admin.py migrate` | 是 | 先校验已有台账，拒绝未来版本或名称、校验值分叉，再仅升级显式 `--database` 指定数据库缺少的已知版本 |
| `database_admin.py check-schema` | 否 | 调用 `assert_current_schema()` 的只读门禁；只在版本集合恰好为 1 至 `SCHEMA_TARGET_VERSION`（当前 58）且每个版本名称与 SQL 文件 SHA-256 校验值匹配时成功 |
| `database_admin.py verify` | 否 | 严格检查连续 1 至 `SCHEMA_TARGET_VERSION`（当前 58）、完整性、外键、忙等待、关键结构和照片身份基线 |
| `python -m src.container_entrypoint <command...>` | 新库首次写入；已有库只读 | 容器通用入口：创建数据库父目录、输出目录、环境变量指定的照片目录和初始化锁；数据库不存在时完整迁移，已有库严格校验；成功后用 `execvp` 原样转交目标命令，失败时不执行目标命令 |
| `python -m src.server.run_server` | 运行期按请求读写 | 直接启动 Web 服务时先检查结构、不迁移；门禁通过后读取或创建数据库同目录运行时密钥，再注册服务并认领、对账过期照片生命周期操作 |
| `python -m src.analysis.run_worker` | 运行期处理任务 | 直接启动独立工作进程时只检查结构、不迁移；首次认领时固化配置快照，每轮认领并对账租约已经过期的照片生命周期操作 |
| `python -m src.analysis.analyze_photos_docker` | 启动时可能迁移，运行期写分析结果 | 先调用共享迁移器校验历史并补齐缺少的已知迁移，再执行照片分析 |

严格 `verify` 只有在 `integrity_check` 与 `quick_check` 都为 `ok`、外键开启且无违规、`busy_timeout=5000`、关键字段、管理员表、`admin_login_failures` 复合主键及过期索引、`photo_lifecycle_operations` 与 `photo_purge_operations` 表及照片编号唯一约束存在、迁移版本恰好连续 1 至 `SCHEMA_TARGET_VERSION`（当前 58）、六项照片身份不变量一致时才成功。

## 自动测试

`npm test` 是完整自动测试的唯一入口，底层执行：

```bash
python3 -m unittest discover -s tests -p "test_*.py"
```

- 每个数据库测试都在 `TemporaryDirectory` 中创建隔离数据库、图片目录和输出目录，并调用真实迁移完整应用版本 1 至 `SCHEMA_TARGET_VERSION`（当前 58），最后确认版本等于该常量；禁止复制、打开或修改活动数据库及其预写日志文件。
- `tests/support.py` 提供公共基类 `TemporaryDatabaseTestCase`：`setUp` 在 `TemporaryDirectory` 里建 `database/test.db`、`images/`、`output/`，断言目标路径不在 `FORBIDDEN_DATABASE_PATHS`（正式 `data/photos.db` 与仓库根 `photos.db`）之内后跑真实迁移，并按 `SCHEMA_TARGET_VERSION` 常量（不写死数字）断言版本连续无缺口；`tearDown` 用 `PRAGMA foreign_key_check` 断言无外键违规。基类还提供 `database()` 上下文连接、`create_admin_user`、`create_photo`（默认 `is_included=1`，与库内默认排除相反，以便造「可用照片」）、`read_job` / `read_photo` / `read_events`、`expire_job_lease`（把租约改成确定的过去时间触发恢复）与 `application_config()`（绑定临时路径、禁用生产安全要求的 Flask 测试配置）。
- `tests/test_database_initialization.py`：验证缺失数据库迁移全部 `SCHEMA_TARGET_VERSION`（当前 58）个版本、当前库不重复迁移，以及零字节文件和非普通路径拒绝。
- `tests/test_container_entrypoint.py`：使用独立进程验证并发只初始化一次、锁文件请求权限、先准备后转交、命令参数原样保留、空命令和准备失败门禁。
- `tests/test_first_admin.py`：验证两个并发首管理员请求仅一个成功，已有任意管理员时拒绝再次首次创建。
- `tests/test_initial_setup_authentication.py`：验证令牌来源互斥、格式和文件边界、常量时间校验前置、密码哈希及凭据边界。
- `tests/test_admin_setup.py`：验证设置页与登录引导、跨站请求伪造保护、密码确认、错误令牌不回显、并发竞态关闭、成功登录及入口关闭。
- `tests/test_model_providers.py`：验证模型厂商档案（`model_providers` 表）的存储、字段校验、密钥脱敏（不进列表接口、页面与审计表）、`resolve_endpoint` 端点归一化与连通性测试；同时钉住「不建任何档案时旧分析链路完全不受影响」。
- `tests/test_provider_routing.py`：验证 `ANALYSIS_PROVIDER` / `NARRATION_PROVIDER` / `PANEL_PROVIDER` 三类用途路由的写入校验、运行时厂商选择、面板优先级，以及不再注入 `API_URL` / `API_KEY` / `MODEL_NAME` 后旧配置的兼容处理。
- `tests/test_provider_fallback.py`：验证候选链只对明确网络类故障（连接失败、超时、HTTP 429、HTTP 5xx）单向降级；HTTP 400 / 401 等其他 4xx 与响应内容解析失败不降级。
- `tests/test_provider_snapshot.py`：验证任务首次认领时把候选链固化进快照、旧快照与新 `provider` 块的双读兼容，以及快照密钥边界。
- `tests/test_provider_request_options.py`：验证厂商特有请求参数（如千问的 `enable_thinking`、`response_format`）的解析与合并，尤其是「取值为 `null` 表示删除该参数不发送」这一语义，以及手工改库留下的非法值按无参数宽容处理。
- `tests/test_narration_extraction.py`：验证旁白正文提取对纯文本、JSON 对象、被数组多包一层、代码围栏等偏离格式的容错，避免把整段 JSON 或残缺围栏静默当成旁白入库。
- `tests/test_exif_metadata.py`：验证上传与分析共用的 `src/exif_metadata` 提取：GPS 走 `get_ifd(34853)`、拍摄参数走 Exif 子 IFD（34665），杜绝「有经纬度、城市为空」这类自相矛盾记录。
- `tests/test_curation_triggers_analysis.py`：验证收录状态与分析排队的联动——只在真正发生收录跃迁时排一次队、已有分析结果不重跑、批量逐张判定、`NEW_PHOTO_CURATION=included` 模式不绕过按张放行，以及照片改回未收录时撤销未执行的分析任务。
- `tests/test_settings_display_units.py`：验证后台配置页字节/时间类字段按显示单位（MiB、百万像素、小时、分钟）填写，而落库与接口仍用基准单位（字节、像素、秒），且换算来回不产生精度漂移。
- 涉及数据库迁移、跨进程登录限流、上传超限与后台筛选的手工验证同样只允许使用 `/tmp` 或 `TemporaryDirectory`；不得声称临时库结果代表正式库已迁移或生产部署已验证。
- 公开接口和首次设置测试使用 `create_app(config_overrides)` 与 Flask `test_client`，不会启动真实 HTTP 服务。
- 后台任务状态机测试直接使用真实 `AdminJobRepository` 和真实 SQLite 事务，不模拟被测仓储方法，也不会调用网络或视觉语言模型。
- 任一断言或测试异常都会让命令返回非零退出码；手工 `curl` 仅用于人工调试，不属于自动测试套件。

## scripts/ 脚本一览

| 脚本 | 用途 | 注意事项 |
|------|------|----------|
| `run_analysis.sh` | 首次全量导入的批量分析封装：校验 venv 与 `.env` 存在、`source .env` 后 `exec python -m src.analysis.analyze_photos_docker "$@"` | 支持传参覆盖，如 `BATCH_LIMIT=20 ./scripts/run_analysis.sh`；**不要用它做定时分析**，见下方陷阱 |
| `scan_library.sh` | 定时扫描照片目录（`python -m src.analysis.run_scan`），登记新照片并按收录状态排队，分析本身交给工作进程 | 带 `tmp/inktime_scan.lockdir` 目录锁，重复触发跳过；日志写 `logs/scan.log`；需要 `.env` |
| `daily_render.sh` | 每日选片渲染（`python -m src.render.render_daily_photo`）；项目路径按脚本位置自动推导 | 带 `tmp/inktime_render.lockdir` 目录锁；日志写 `logs/render.log`；需要 `.env` |
| `display_kiosk.sh` | 全屏 kiosk 播放 `/display` 展示页，并用 `gnome-session-inhibit` 抑制系统息屏；用局域网 IP 访问也有效 | 需要 `gnome-session-inhibit`（缺失时提示改用 `systemd-inhibit`）；端口取 `.env` 的 `FLASK_PORT`（缺省 8888）；可用 `BROWSER=<命令>` 指定浏览器 |
| `database_admin.py` | 数据库管理命令行：`preflight` / `baseline` / `backup` / `migrate` / `check-schema` / `verify`，详见上方「数据库管理与运行入口边界」 | 只对显式 `--database` 指定的库操作；不会触碰活动库以外的路径 |
| `fix_mtime_dates.py` | 修正历史上把文件 mtime 当拍摄时间的照片：按 `original_filename` / 磁盘名重解析日期，解析不出则拍摄时间留空、来源记 `none` | 默认只预览，加 `--apply` 才写库；写库前自动备份；需 `--database` |
| `backfill_metadata.py` | 不调用 VLM、不花额度地回填存量照片元数据：按 EXIF→XMP→文件名→mtime 四级重算 `exif_datetime`/`date_source`，并把 `type` 统一成 `/` 分隔 | 默认预览，`--apply` 才写入；适用于改了日期兜底或类型规范化规则后让存量数据跟上 |
| `generate_favicon.py` | 按 `favicon.svg` 几何生成位图图标，保证矢量与位图一致 | 生成结果需提交进仓库——运行/构建环境无 SVG 光栅化库，无法即时生成；改了 `favicon.svg` 后重跑 |
| `install-git-hooks.sh` | 把 `core.hooksPath` 指向仓库内 `scripts/git-hooks`，使本地提交自动校验 | 需 git ≥ 2.9.0；执行一次即可 |
| `git-hooks/commit-msg` | 校验提交信息符合 `<type>(<scope>)!: <subject>`，自动放行 merge/revert/fixup/squash | 由 `install-git-hooks.sh` 挂载；`--no-verify` 可跳过（不推荐） |
| `git-hooks/pre-push` | 校验被推送分支名符合 `<type>/<负责人>_<说明>_<日期>`，放行 `master`/`main`/`dev`/`release/*` | 由 `install-git-hooks.sh` 挂载；`--no-verify` 可跳过（不推荐） |

> **不要用 `analyze_photos_docker`（即 `run_analysis.sh`）做定时分析**：它会把已排队的 `pending` 照片当作待处理对象，与工作进程重复分析同一张照片，白白消耗两倍模型额度。批量脚本只适合首次全量导入，日常增量交给 `scan_library.sh` 扫描登记 + `run_worker` 工作进程执行。

## 代码结构说明

### src/analysis/analyze_photos_docker.py

| 函数 | 职责 |
|------|------|
| `main()` | 主流程：扫描 → 过滤 → 清理 → 逐张分析 |
| `call_vlm(path, image_b64=None)` | 调用 VLM 获取描述和评分，传入 base64 可跳过重复编码 |
| `generate_side_caption(path, image_b64=None)` | 调用 VLM 生成一句话文案，传入 base64 可跳过重复编码 |
| `read_exif(path)` | 提取 EXIF 信息，字段解析委托给上传/分析共用的 `src/exif_metadata.extract_exif_fields`（GPS 走子 IFD 34853、拍摄参数走子 IFD 34665） |
| `encode_image_to_b64(path)` | 图片预处理 + Base64 编码 |
| `find_nearest_city(lat, lon, ...)` | GPS 逆地理编码 |
| `list_images(limit)` | 递归扫描图片文件 |
| `filter_unscored(conn, paths)` | 筛选未分析的照片 |
| `migrate_database(DB_PATH)` | 启动分析前校验迁移身份并补齐缺少的已知迁移；未来版本或分叉历史在写入前失败 |

### src/render/render_daily_photo.py

| 函数 | 职责 |
|------|------|
| `main()` | 主流程：加载数据 → 选片 → 渲染 → 输出 |
| `choose_photos_for_today(items, today, count)` | 选片算法 |
| `render_image(item)` | 渲染单张照片到 480×800 画布 |
| `apply_four_color_dither(img)` | Floyd-Steinberg 四色抖动 |
| `image_to_palette_bin(img)` | 图像转 BIN 格式 |
| `write_h_array(bin_path, h_path)` | 生成 C 头文件 |
| `load_sim_rows()` | 从数据库加载照片数据 |

### src/server Web 服务分层

| 文件 | 职责 |
|------|------|
| `app.py` | 每次创建独立 Flask 应用；加载配置覆盖；注册数据库 teardown、Service、Blueprint 和错误处理 |
| `blueprints/public.py` | 现有 27 条显式公开路由，只解析请求、调用 Service、转换响应 |
| `blueprints/admin.py` | `/admin` 登录、退出和页面路由，以及 `/api/admin` 接口；两个后台 Blueprint 默认要求认证并保护写请求 |
| `services.py` | 照片序列化、设置读取、媒体边界、展示、面板、设备下载和目录浏览行为 |
| `repositories/photo_repository.py` | 照片只读 SQL；值参数化，排序走服务端白名单 |
| `service_contracts.py` | 认证、任务、审计的 `typing.Protocol` 扩展接口 |
| `errors.py` | 页面错误页和安全 JSON 错误响应；未知异常只在服务端记录上下文 |
| `server.py` | 兼容旧的直接执行和 `src.server.server:create_app` 导入路径 |

依赖方向固定为 Blueprint → Service → Repository → `src.database`。普通请求连接放在
Flask `g` 中并由应用 teardown 关闭；`gallery.py` 的独立短写事务保持不变。

## 调试技巧

### 分析模块调试

1. **设置 BATCH_LIMIT=1**：只处理一张照片，快速验证流程
2. **查看 VLM 输出**：脚本会打印每张照片的分析结果
3. **跳过文案生成**：注释掉 `generate_side_caption` 调用可加速测试
4. **检查数据库**：`sqlite3 data/photos.db "SELECT id, memory_score, side_caption FROM photo_scores LIMIT 5;"`
   没装 sqlite3 CLI 时用：
   `./venv/bin/python -c "import sqlite3;print(sqlite3.connect('data/photos.db').execute('SELECT id,memory_score,side_caption FROM photo_scores LIMIT 5').fetchall())"`
5. **确认候选池**：没有 EXIF 拍摄时间的照片不会进选片候选池，
   用 `SELECT COUNT(*) FROM photo_scores WHERE exif_datetime IS NOT NULL AND exif_datetime != ''` 看比例

### 渲染模块调试

1. **查看预览图**：`data/output/preview_0.png` 是抖动后的效果
2. **调整阈值**：降低 MEMORY_THRESHOLD 可以让更多照片被选中
3. **指定日期测试**：修改 `TODAY = dt.date(2024, 12, 2)` 测试特定日期

### 服务器调试

1. **Flask debug 模式**：直接跑 `python src/server/server.py` 并把 `app.run(debug=True)`，仅用于本地调试；常驻请用 Waitress
2. **API 测试**：`curl "http://127.0.0.1:8888/api/photos?page=1&limit=3"`
3. **ESP32 模拟**：先以管理员登录 `/admin/settings`，复制完整 `latest.bin` 设备地址，再执行 `curl -o test.bin '<完整地址>'`。不要把包含下载路径口令的地址写入日志或公开截图

### 管理员认证调试

所有调试都应使用临时数据库和 `create_app(config_overrides)`，不要直接操作活动库。推荐检查：

# 仅做 Python 语法检查，不会启动服务或迁移数据库
python -m compileall -q src/server src/migrations.py scripts/database_admin.py

# 查看迁移和后台路由静态定义
python scripts/database_admin.py --help

### 后台任务调试

只使用临时数据库和临时 `IMAGE_DIR` 验证任务，不调用真实模型。迁移加载器会拒绝空 SQL 或一份文件多条 SQL。推荐用注入的假分析函数调用 `AnalysisWorker.run_once()`，覆盖两个连接原子认领、照片 pending→running→succeeded、照片取消后 failed 且 `analysis_error=job_canceled`、普通失败、取消与完成竞态、租约恢复、旧工作进程晚完成、三次失败和管理员编辑版本冲突。后台任务取消后的 `admin_jobs.status` 仍为 canceled。

上传验证应创建带拍摄时间与 GPS 的临时照片，确认重编码后任务仍使用原始拍摄语义、数据库摘要等于正式文件字节；同时覆盖 SHA-256 去重、第三张非法时前两张不落库不落盘、数据库提交失败补偿、系统专属孤儿临时文件清理及 SQLite 锁定时无半记录。历史摘要回填要验证稳定照片编号、低优先级让出、取消、恢复和不调用视觉语言模型。认证验证继续覆盖匿名访问、登录与跨站请求伪造保护。

### 阶段 6 回收站与维护任务调试

只使用 `/tmp` 下的新数据库、照片目录和输出目录验证，不迁移正式 `data/photos.db`，也不要触碰
`data/photos.db-shm` 与 `data/photos.db-wal`。推荐覆盖以下边界：

1. 活动照片路径必须位于已配置的某个照片目录内，任意根的 `.trash` 路径都不能走公开媒体端点；
2. 软删除后原文件消失、回收站实际路径存在、`blocked=1` 且只有一个活跃 `render_display`；
3. 重复删除返回冲突，恢复目标存在返回冲突；
4. 在 `soft_delete_before_commit` 和 `restore_before_commit` 注入普通异常，文件必须反向补偿，补偿成功后对应 `photo_lifecycle_operations` 台账被删除；
5. 在临时数据库分别覆盖移动前、来源与目标为同一 inode 的双硬链接、移动后但业务提交前这三种强杀窗口；重新启动 Web 服务或运行维护工作进程后，断言只认领过期台账，并按数据库严格前态或后态把文件对齐到来源或目标路径；数据库 `path` 使用相对路径时也必须先解析到 `IMAGE_DIR` 后得到相同结论；
6. 对账遇到数据库状态不明确、来源与目标路径冲突或双路径不是同一 inode 时，必须保留操作台账并报告错误，不得覆盖或猜测；双路径确认为同一 inode 时只删除冗余链接。所有原业务请求、补偿和恢复者都必须竞争同一个按照片编号稳定命名的跨进程文件锁：让失租原请求在所有权检查后暂停，再由恢复者接管并等待文件锁，释放旧请求后断言旧请求不能提交、恢复者最终按数据库状态收敛且台账被清除；两个恢复者交错时也必须得到同样结果，文件操作期间不得持有 SQLite 全局写锁；
7. 永久删除必须同时满足回收站状态、确认文本和 `expected_version`，并在 `photo_purge_operations` 中为每张照片建立唯一在途操作。验证恢复先创建生命周期台账时永久删除被拒绝、永久删除先创建在途台账时恢复被拒绝；让两个永久删除请求竞争同一照片文件锁，第一请求注入文件删除失败并只关闭自己的操作，第二请求随后创建新操作并成功完成，期间表内最多一条记录。还要验证进程强杀遗留的过期操作可由下一次同版本同路径请求接管，未过期操作拒绝并发请求，完成或失败后操作台账与对应审计在同一事务闭合；
8. 清理预览前后审计数量不变；在批次中间注入永久删除失败时，断言此前项目成功、失败项及其后项目保留，安全游标停在最后成功项目，失败项仍计入剩余数量；
9. 待认领维护清理任务设置取消后不能被领取；运行任务带取消请求且租约过期时直接进入 `canceled`，不能重新排队；
10. 让 `cleanup_batch` 在项目开始边界观察到取消或失租，断言返回 `interrupted` 且不再开始该项和后续项；若该项的边界检查已经通过，则允许当前项完成，只保证不再开始后续项。工作进程不完成已中断任务，也不创建后继任务；单项失败仍由当前任务按原始载荷有限重试，不能完成任务或创建后继任务；
11. 在 `render_before_publish` 注入失败，设备下载和 `/files/` 必须持续被屏蔽；重试成功后 manifest 保存且解除屏蔽；
12. 让续租返回 `False` 或抛出数据库异常，释放假渲染阻塞点后断言旧正式文件字节完全不变，任务未完成且仍保持屏蔽；
13. 让工作进程甲的租约过期，由工作进程乙恢复并重新领取，再释放甲继续执行，断言甲不能进入正式发布、乙可以发布；过期但尚未恢复的任务也不能续租或完成；
14. 工作进程遇到未知照片任务或维护任务类型必须稳定失败，不能调用照片分析函数。

渲染验证可以在 `/tmp` 注入只生成最小假产物的两套 `main`，验证临时目录、事务所有权栅栏内逐文件 `os.replace`、失租时旧正式文件不变、失败保持 blocked 和成功保存 manifest，不需要调用真实模型，也不改变选片算法。公开前端安全回归应向旁白、分类、相机型号、照片文件名和无效拍摄时间写入 `<img src=x onerror=...>` 及引号闭合文本，断言页面只显示字面文本、没有新增脚本或攻击图片节点，媒体地址仍限制在预期同源接口。

## 常见问题

### Q: 照片分析直接失败，日志说没有可用模型配置

**原因**：模型接入已整体移出 `.env`，`model_providers` 表里的厂商档案是模型配置的唯一来源，`API_URL` / `MODEL_NAME` / `API_KEY` 等兜底键已移除。没有建档、或建了档但用途路由（`ANALYSIS_PROVIDER` 等）没指向任何厂商时，分析会明确失败而不是悄悄换一套配置——后者更难排查。
**解决**：
- 在后台「模型厂商」页（`/admin/providers`）建档：名称、接口地址、密钥，以及各自独立的超时与图片最长边
- 在配置管理页「模型与分析 → 用途路由」把 `ANALYSIS_PROVIDER` 指向厂商名称；`NARRATION_PROVIDER`、`PANEL_PROVIDER` 留空时跟随分析
- 建档本身不改变行为，只表示「允许被引用」；真正决定谁干活的是用途路由

### Q: 分析「成功」了，但用的不是我想要的模型

**原因**：用途路由填的厂商名称写错或指到了别的档案。路由填错时分析照样成功，只是用了别的模型，等发现时已经烧了一批额度。
**解决**：
- 厂商列表页会标注每条档案被哪些用途引用，未被引用的明确标「未被引用」，据此核对
- 每条档案点「测试连通性」发一次最小请求验证地址与密钥
- 同一厂商下可填多个可选模型，但**不会自动轮换、也不会故障自动切换**（各模型授权额度不同），换模型是需要明确决定的动作，用列表页「启用模型」下拉或编辑页逐行测试后切换

### Q: 连通性测试报 HTTP 404

**原因**：接口地址格式不对。`resolve_endpoint` 按后缀归一化：已指向 `/chat/completions` 的完整端点原样使用，否则补上 `/chat/completions`。因此 `/v1` 结尾的基础地址会被补成 `/v1/chat/completions`（正确），而误填 Responses API 的 `/responses` 会被补成 `/responses/chat/completions`，导致 404。
**解决**：接口地址填 **OpenAI 兼容模式的基础地址**，通常以 `/v1` 结尾（如 `https://dashscope.aliyuncs.com/compatible-mode/v1`、`http://127.0.0.1:1234/v1`）；已指向 `/chat/completions` 的完整端点也接受；不要填其他协议路径（如 `/responses`）。

### Q: 编辑厂商时密钥留空会不会把密钥清掉

**原因**：密钥在页面上只显示末四位，属于「只写不回显」。
**解决**：编辑时留空表示**保持原值**，不是清空；要更换才填新值。

### Q: 改了用途路由，已排队的任务还是走旧厂商

**原因**：后台任务在首次认领时把候选链固化进任务快照，因此排队时指向某厂商的任务执行时一定走该厂商，即使中间改了路由。这是有意设计，避免排队期间路由变动导致额度以不可预期的方式消耗。
**解决**：改完路由在后台任务页点「重试」即可立即生效；实际发生的厂商切换会写入任务事件并记录警告日志，可在任务页复盘。

### Q: 改了模板文件，页面没变化

**原因**：`app.py` 把 `TEMPLATES_AUTO_RELOAD` 设为 `app_environment == "development"`。开发环境（`APP_ENV=development`）下改动模板刷新即生效；生产环境（`APP_ENV=production`）模板被缓存，避免每次请求都做磁盘检查。静态文件始终直接读盘，不受此项影响。
**解决**：生产环境改完模板需重启服务（`systemctl restart inktime-server` 或重建容器）；本地调试用 `development` 即可热更新。

### Q: 后台改了配置却没有生效

**原因**：分三类，先判断属于哪一类
**解决**：
- 属于锁定项（数据库与输出目录、监听地址端口、会话与登录限流、`SECRET_KEY`、`DOWNLOAD_KEY`）：只能改 `.env` 并重启，配置页显示为禁用
- 属于分析或渲染类：已认领任务沿用认领时固化的快照，改动从队列中的下一个任务开始生效，这是有意设计
- 提交后审计里没有该项记录：说明提交值与当前有效值相同，被「无变化不写库」过滤掉了。注意这条过滤按发起写入进程的有效值判断，Web 与工作进程必须使用同一份 `.env`，否则可能出现 Web 侧判为无变化、工作进程仍用自己环境值的分歧

### Q: 运行时密钥文件损坏或删除后发生什么

**原因**：`SECRET_KEY` 与 `DOWNLOAD_KEY` 缺省时由数据库同目录隐藏文件持久化
**解决**：
- 文件不是普通文件、权限向组或其他用户开放、内容含空白或长度不足时，应用会拒绝启动；先从可信备份恢复，不要让程序猜测或静默覆盖
- 删除 `.inktime-secret-key` 会使现有登录会话失效；删除 `.inktime-download-key` 会改变设备下载地址，需要重新从 `/admin/settings` 复制并更新设备
- 显式环境变量优先于文件；排查时确认所有 Web 进程使用同一数据库目录和覆盖值

### Q: 后台保存了 IMAGE_DIR，但工作进程找不到照片

**原因**：后台配置只能选择 Web 容器当前可见的目录，不能给其他容器动态增加挂载
**解决**：使用 Compose override 把外部目录显式挂载到 Web 服务、后台工作进程和所需工具服务，并让各容器使用一致的容器内绝对路径；重建容器后再保存配置

### Q: 上传上限改大了仍然被拒

**原因**：`MAX_CONTENT_LENGTH` 是由单批文件数与单文件字节数派生的 Werkzeug 请求体上限
**解决**：
- 应用已用 `before_request` 钩子每次请求前重算，无需重启；若仍被拒，先确认注册表上界：单文件字节数最大 20 MiB、单批最多 10 张、单图最多 8000 万像素，超出部分会被收敛
- 反向代理（Nginx 的 `client_max_body_size` 等）另有自己的上限，需要同步调大

### Q: VLM 返回非 JSON 格式

**原因**：模型未严格遵循 JSON 输出指令
**解决**：
- 确认使用支持视觉的模型（如 qwen3-vl）
- 检查 temperature 设置（分析用 0.2，文案用 0.7）
- 查看 `[DEBUG] 非 JSON 输出` 日志

### Q: GPS 信息缺失

**原因**：PIL 无法解析某些格式的 GPS 数据
**解决**：安装 exiftool（`brew install exiftool`），脚本会自动使用

### Q: 渲染时找不到照片

**原因**：数据库中的绝对路径与实际文件或容器挂载路径不匹配
**解决**：
- 先运行 `./venv/bin/python scripts/database_admin.py preflight --env-file .env`
- 检查输出中的 `photo_paths.outside_image_dir` 与 `photo_paths.missing_files`
- 修正 `IMAGE_DIR`、容器同路径挂载或缺失文件后再渲染
- 分析入口不会自动清理不存在的照片记录，不要把重新分析当作路径修复手段

### Q: ESP32 下载失败

**排查步骤**：
1. 确认服务器运行中：`curl http://server:8888/`
2. 确认 DOWNLOAD_KEY 匹配
3. 确认 .bin 文件存在：`ls data/output/photo_*.bin`
4. 检查 ESP32 串口日志

### Q: 墨水屏不显示

**排查步骤**：
1. 检查 SPI 接线（6 根信号线）
2. 串口是否有 "BUSY timeout" 错误
3. 确认 PSRAM 已启用（Arduino IDE 设置）
4. 确认 .bin 文件大小为 384,000 字节
