# 09 - 开发指南

## 本地开发环境搭建

### 前置条件

- Python 3.10+
- VLM 服务（如 LM Studio + Qwen3-VL-32B）
- 一些测试照片

### 快速开始

```bash
# 1. 克隆项目
git clone <repo-url>
cd InkTime

# 2. 创建虚拟环境
python3 -m venv venv
source venv/bin/activate

# 3. 安装依赖（已包含固定版本 Waitress）
pip install -r requirements.txt

# 4. 配置（.env 是唯一配置源）
cp .env.example .env
# 编辑 .env：至少设置 IMAGE_DIR、API_URL、MODEL_NAME、API_KEY、FONT_PATH

# 5. 数据库和路径预检
./venv/bin/python scripts/database_admin.py preflight --env-file .env

# 6. 用 SQLite backup API 创建一致性备份与身份基线
./venv/bin/python scripts/database_admin.py backup \
  --database data/photos.db --output-dir data/backups

# 7. 只在备份副本上首次演练迁移与严格验证
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/backup.db
./venv/bin/python scripts/database_admin.py verify \
  --database /absolute/path/to/backup.db \
  --baseline /absolute/path/to/backup.baseline.json

# 8. 审批后对受控目标显式迁移，再用只读门禁确认结构
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/target.db
./venv/bin/python scripts/database_admin.py check-schema --database /absolute/path/to/target.db

# 9. 准备视觉大模型：本地 LM Studio，或直接填云端 OpenAI 兼容 API

# 10. 运行分析（入口只检查当前结构，不自动迁移；建议先设 BATCH_LIMIT=3）
BATCH_LIMIT=3 ./scripts/run_analysis.sh

# 11. 启动独立后台工作进程
./venv/bin/python -m src.analysis.run_worker

# 12. 渲染
./scripts/daily_render.sh

# 13. 启动生产服务器
./venv/bin/python -m src.server.run_server
# 访问 http://127.0.0.1:5005/（端口取 .env 的 FLASK_PORT）
```

### 数据库管理与运行入口边界

| 命令 | 是否写数据库或文件 | 用途 |
|------|--------------------|------|
| `database_admin.py preflight` | 否 | 检查路径、权限、挂载点及异常照片路径 |
| `database_admin.py baseline` | 写基线 JSON | 记录迁移前照片身份与数据库状态 |
| `database_admin.py backup` | 写备份数据库和基线 JSON | 使用 SQLite backup API 创建一致性副本，并把目标切换为独立 DELETE 日志模式 |
| `database_admin.py migrate` | 是 | 先校验已有台账，拒绝未来版本或名称、校验值分叉，再仅升级显式 `--database` 指定数据库缺少的已知版本 |
| `database_admin.py check-schema` | 否 | 调用 `assert_current_schema()` 的只读门禁；只在版本集合恰好为 1 至 50 且每个版本名称与 SQL 文件 SHA-256 校验值匹配时成功 |
| `database_admin.py verify` | 否 | 严格检查连续 1 至 50、完整性、外键、忙等待、关键结构和照片身份基线 |
| `python -m src.container_entrypoint <command...>` | 新库首次写入；已有库只读 | 容器通用入口：创建数据库父目录和初始化锁；数据库不存在时完整迁移，已有库严格校验；成功后用 `execvp` 原样转交目标命令，失败时不执行目标命令 |
| `python -m src.server.run_server` | 运行期按请求读写 | 直接启动 Web 服务时只检查结构、不迁移；门禁通过后认领并对账租约已经过期的照片生命周期操作 |
| `python -m src.analysis.run_worker` | 运行期处理任务 | 直接启动独立工作进程时只检查结构、不迁移；首次认领时固化配置快照，每轮认领并对账租约已经过期的照片生命周期操作 |
| `python -m src.analysis.analyze_photos_docker` | 启动时可能迁移，运行期写分析结果 | 先调用共享迁移器校验历史并补齐缺少的已知迁移，再执行照片分析 |

严格 `verify` 只有在 `integrity_check` 与 `quick_check` 都为 `ok`、外键开启且无违规、`busy_timeout=5000`、关键字段、管理员表、`admin_login_failures` 复合主键及过期索引、`photo_lifecycle_operations` 与 `photo_purge_operations` 表及照片编号唯一约束存在、迁移版本恰好连续 1 至 50、六项照片身份不变量一致时才成功。

## 自动测试

`npm test` 是完整自动测试的唯一入口，底层执行：

```bash
python3 -m unittest discover -s tests -p "test_*.py"
```

- 每个数据库测试都在 `TemporaryDirectory` 中创建隔离数据库、图片目录和输出目录，并调用真实迁移完整应用版本 1 至 50，最后确认版本为 0050；禁止复制、打开或修改活动数据库及其预写日志文件。
- `tests/test_database_initialization.py`：验证缺失数据库迁移 50 个版本、当前库不重复迁移，以及零字节文件和非普通路径拒绝。
- `tests/test_container_entrypoint.py`：使用独立进程验证并发只初始化一次、锁文件请求权限、先准备后转交、命令参数原样保留、空命令和准备失败门禁。
- `tests/test_first_admin.py`：验证两个并发首管理员请求仅一个成功，已有任意管理员时拒绝再次首次创建。
- `tests/test_initial_setup_authentication.py`：验证令牌来源互斥、格式和文件边界、常量时间校验前置、密码哈希及凭据边界。
- `tests/test_admin_setup.py`：验证设置页与登录引导、跨站请求伪造保护、密码确认、错误令牌不回显、并发竞态关闭、成功登录及入口关闭。
- 涉及数据库迁移、跨进程登录限流、上传超限与后台筛选的手工验证同样只允许使用 `/tmp` 或 `TemporaryDirectory`；不得声称临时库结果代表正式库已迁移或生产部署已验证。
- 公开接口和首次设置测试使用 `create_app(config_overrides)` 与 Flask `test_client`，不会启动真实 HTTP 服务。
- 后台任务状态机测试直接使用真实 `AdminJobRepository` 和真实 SQLite 事务，不模拟被测仓储方法，也不会调用网络或视觉语言模型。
- 任一断言或测试异常都会让命令返回非零退出码；手工 `curl` 仅用于人工调试，不属于自动测试套件。

### 后台任务调试

只使用临时数据库和临时 `IMAGE_DIR` 验证任务，不调用真实模型。迁移加载器会拒绝空 SQL 或一份文件多条 SQL。推荐用注入的假分析函数调用 `AnalysisWorker.run_once()`，覆盖两个连接原子认领、照片 pending→running→succeeded、照片取消后 failed 且 `analysis_error=job_canceled`、普通失败、取消与完成竞态、租约恢复、旧工作进程晚完成、三次失败和管理员编辑版本冲突。后台任务取消后的 `admin_jobs.status` 仍为 canceled。

上传验证应创建带拍摄时间与 GPS 的临时照片，确认重编码后任务仍使用原始拍摄语义、数据库摘要等于正式文件字节；同时覆盖 SHA-256 去重、第三张非法时前两张不落库不落盘、数据库提交失败补偿、系统专属孤儿临时文件清理及 SQLite 锁定时无半记录。历史摘要回填要验证稳定照片编号、低优先级让出、取消、恢复和不调用视觉语言模型。认证验证继续覆盖匿名访问、登录与跨站请求伪造保护。

### 阶段 6 回收站与维护任务调试

只使用 `/tmp` 下的新数据库、照片目录和输出目录验证，不迁移正式 `data/photos.db`，也不要触碰
`data/photos.db-shm` 与 `data/photos.db-wal`。推荐覆盖以下边界：

1. 活动照片路径必须位于已配置的某个照片目录内，任意根的 `.trash` 路径都不能走公开媒体端点；
2. 软删除后原文件消失、回收站实际路径存在、`blocked=1` 且只有一个活跃 `render_display`；
3. 重复删除返回冲突，恢复目标存在返回冲突；
4. 在 `soft_delete_before_commit` 和 `restore_before_commit` 注入普通异常，文件必须反向补偿，补偿成功后对应 `photo_lifecycle_operations` 台账被删除；
5. 在临时数据库分别覆盖移动前、来源与目标为同一 inode 的双硬链接、移动后但业务提交前这三种强杀窗口；重新启动 Web 服务或运行维护工作进程后，断言只认领过期台账，并按数据库严格前态或后态把文件对齐到来源或目标路径；数据库 `path` 使用相对路径时也必须先解析到 `IMAGE_DIR` 后得到相同结论；
6. 对账遇到数据库状态不明确、来源与目标路径冲突或双路径不是同一 inode 时，必须保留操作台账并报告错误，不得覆盖或猜测；双路径确认为同一 inode 时只删除冗余链接。所有原业务请求、补偿和恢复者都必须竞争同一个按照片编号稳定命名的跨进程文件锁：让失租原请求在所有权检查后暂停，再由恢复者接管并等待文件锁，释放旧请求后断言旧请求不能提交、恢复者最终按数据库状态收敛且台账被清除；两个恢复者交错时也必须得到同样结果，文件操作期间不得持有 SQLite 全局写锁；
7. 永久删除必须同时满足回收站状态、确认文本和 `expected_version`，并在 `photo_purge_operations` 中为每张照片建立唯一在途操作。验证恢复先创建生命周期台账时永久删除被拒绝、永久删除先创建在途台账时恢复被拒绝；让两个永久删除请求竞争同一照片文件锁，第一请求注入文件删除失败并只关闭自己的操作，第二请求随后创建新操作并成功完成，期间表内最多一条记录。还要验证进程强杀遗留的过期操作可由下一次同版本同路径请求接管，未过期操作拒绝并发请求，完成或失败后操作台账与对应审计在同一事务闭合；
8. 清理预览前后审计数量不变；在批次中间注入永久删除失败时，断言此前项目成功、失败项及其后项目保留，安全游标停在最后成功项目，失败项仍计入剩余数量；
9. 待认领维护清理任务设置取消后不能被领取；运行任务带取消请求且租约过期时直接进入 `canceled`，不能重新排队；
10. 让 `cleanup_batch` 在项目开始边界观察到取消或失租，断言返回 `interrupted` 且不再开始该项和后续项；若该项的边界检查已经通过，则允许当前项完成，只保证不再开始后续项。工作进程不完成已中断任务，也不创建后继任务；单项失败仍由当前任务按原始载荷有限重试，不能完成任务或创建后继任务；
11. 在 `render_before_publish` 注入失败，设备下载和 `/files/` 必须持续被屏蔽；重试成功后 manifest 保存且解除屏蔽；
12. 让续租返回 `False` 或抛出数据库异常，释放假渲染阻塞点后断言旧正式文件字节完全不变，任务未完成且仍保持屏蔽；
13. 让工作进程甲的租约过期，由工作进程乙恢复并重新领取，再释放甲继续执行，断言甲不能进入正式发布、乙可以发布；过期但尚未恢复的任务也不能续租或完成；
14. 工作进程遇到未知照片任务或维护任务类型必须稳定失败，不能调用照片分析函数。

渲染验证可以在 `/tmp` 注入只生成最小假产物的两套 `main`，验证临时目录、事务所有权栅栏内逐文件 `os.replace`、失租时旧正式文件不变、失败保持 blocked 和成功保存 manifest，不需要调用真实模型，也不改变选片算法。公开前端安全回归应向旁白、分类、相机型号、照片文件名和无效拍摄时间写入 `<img src=x onerror=...>` 及引号闭合文本，断言页面只显示字面文本、没有新增脚本或攻击图片节点，媒体地址仍限制在预期同源接口。

## 常见问题

### Q: 后台改了配置却没有生效

**原因**：分三类，先判断属于哪一类
**解决**：
- 属于锁定项（数据库与输出目录、监听地址端口、会话与登录限流、`SECRET_KEY`、`DOWNLOAD_KEY`）：只能改 `.env` 并重启，配置页显示为禁用
- 属于分析或渲染类：已认领任务沿用认领时固化的快照，改动从队列中的下一个任务开始生效，这是有意设计
- 提交后审计里没有该项记录：说明提交值与当前有效值相同，被「无变化不写库」过滤掉了。注意这条过滤按发起写入进程的有效值判断，Web 与工作进程必须使用同一份 `.env`，否则可能出现 Web 侧判为无变化、工作进程仍用自己环境值的分歧

### Q: 上传上限改大了仍然被拒

**原因**：`MAX_CONTENT_LENGTH` 是由单批文件数与单文件字节数派生的 Werkzeug 请求体上限
**解决**：
- 应用已用 `before_request` 钩子每次请求前重算，无需重启；若仍被拒，先确认注册表上界：单文件字节数最大 20 MiB、单批最多 10 张、单图最多 8000 万像素，超出部分会被收敛
- 反向代理（Nginx 的 `client_max_body_size` 等）另有自己的上限，需要同步调大

### Q: VLM 返回非 JSON 格式

**原因**：模型未严格遵循 JSON 输出指令
**解决**：
- 确认使用支持视觉的模型（如 qwen3-vl）
- 检查 temperature 设置（分析用 0.2，文案用 0.7）
- 查看 `[DEBUG] 非 JSON 输出` 日志

### Q: GPS 信息缺失

**原因**：PIL 无法解析某些格式的 GPS 数据
**解决**：安装 exiftool（`brew install exiftool`），脚本会自动使用

### Q: 渲染时找不到照片

**原因**：数据库中的绝对路径与实际文件或容器挂载路径不匹配
**解决**：
- 先运行 `./venv/bin/python scripts/database_admin.py preflight --env-file .env`
- 检查输出中的 `photo_paths.outside_image_dir` 与 `photo_paths.missing_files`
- 修正 `IMAGE_DIR`、容器同路径挂载或缺失文件后再渲染
- 分析入口不会自动清理不存在的照片记录，不要把重新分析当作路径修复手段

### Q: ESP32 下载失败

**排查步骤**：
1. 确认服务器运行中：`curl http://server:8888/`
2. 确认 DOWNLOAD_KEY 匹配
3. 确认 .bin 文件存在：`ls data/output/photo_*.bin`
4. 检查 ESP32 串口日志

### Q: 墨水屏不显示

**排查步骤**：
1. 检查 SPI 接线（6 根信号线）
2. 串口是否有 "BUSY timeout" 错误
3. 确认 PSRAM 已启用（Arduino IDE 设置）
4. 确认 .bin 文件大小为 384,000 字节

- 调整分数区间定义
- 修改加分/减分规则
- 添加新的照片类型

### 修改文案风格

编辑 `generate_side_caption` 函数中的 `system_prompt`：
- 调整创作原则
- 修改禁用词列表
- 改变风格方向

### 添加新的 Web 页面

1. 在 `src/server/templates/` 下创建模板；公开页面路由加到 `blueprints/public.py`，后台页面加到 `blueprints/admin.py`
2. Blueprint 只解析请求和转换响应，业务行为写入 `services.py`
3. 新增照片数据库查询时写入 `repositories/photo_repository.py`，所有值参数化；动态排序必须使用服务端白名单
4. 在 `app.py` 的 `_register_services()` 注册新增 Service；模板中的 Blueprint 端点使用 `url_for('public.<端点>')`
5. 前端 JavaScript 放在 `src/server/static/js/`；除非明确做接口版本升级，否则保持既有 URL 不变

阶段 2 若实现登录、任务和审计，优先实现 `service_contracts.py` 中的 `AuthService`、
`JobService`、`AuditService` 协议，不要把认证逻辑塞回公开设置接口。

- 数据库操作后立即 commit（保证断点续跑）
