# 07 - 数据库与存储

## 数据库选型

使用 SQLite，原因：
- 零配置，无需独立服务器
- 单文件存储，易于备份和迁移
- Python 标准库内置 `sqlite3`
- 适合单用户、中小规模数据量

## 表结构

### photo_scores 表

```sql
CREATE TABLE photo_scores (
    id                INTEGER PRIMARY KEY AUTOINCREMENT, -- 自增主键，WebUI 的 /api/photo/<id> 依赖它
    path              TEXT UNIQUE NOT NULL,  -- 照片文件绝对路径，唯一约束 + 断点续跑去重依据
    caption           TEXT,              -- AI 生成的画面描述（80-200字）
    type              TEXT,              -- 照片类型（人物/风景/美食等，可多个用/分隔）
    memory_score      REAL,              -- 值得回忆度（0-100，一位小数）
    beauty_score      REAL,              -- 美观程度（0-100，一位小数）
    reason            TEXT,              -- 评分理由（不超过60字）
    width             INTEGER,           -- 照片宽度（像素）
    height            INTEGER,           -- 照片高度（像素）
    orientation       TEXT,              -- 方向：landscape/portrait/square
    used_at           TEXT,              -- 上次被选中展示的时间
    exif_json         TEXT,              -- 完整 EXIF 数据（JSON 格式）
    raw_json          TEXT,              -- VLM 原始返回（JSON 格式）
    exif_datetime     TEXT,              -- 拍摄时间
    exif_make         TEXT,              -- 相机制造商
    exif_model        TEXT,              -- 相机型号
    exif_iso          INTEGER,           -- ISO 感光度
    exif_exposure_time REAL,             -- 曝光时间
    exif_f_number     REAL,              -- 光圈值
    exif_focal_length REAL,              -- 焦距
    exif_gps_lat      REAL,              -- GPS 纬度
    exif_gps_lon      REAL,              -- GPS 经度
    exif_gps_alt      REAL,              -- GPS 海拔
    side_caption      TEXT,              -- 一句话文案（8-24字）
    exif_city         TEXT,              -- 拍摄城市（中文）
    date_source       TEXT,              -- exif_datetime 来源：exif/xmp/filename/mtime/none/manual
    original_filename TEXT,              -- 导入时原始文件名；历史数据不可推断时为 NULL
    content_sha256    TEXT,              -- 文件内容 SHA-256；未回填或文件缺失时为 NULL
    analysis_status   TEXT NOT NULL DEFAULT 'legacy', -- legacy/pending/running/succeeded/failed
    analysis_error    TEXT,              -- 稳定错误类型或 source_file_missing
    is_deleted        INTEGER NOT NULL DEFAULT 0, -- 软删除标记，阶段 4 暂不开放操作
    deleted_at        TEXT,              -- 软删除时间
    original_path     TEXT,              -- 删除前的规范绝对路径
    trash_path        TEXT,              -- 回收站中的实际文件路径
    deleted_by_user_id INTEGER,           -- 执行软删除的管理员编号快照
    deleted_by_username TEXT,             -- 执行软删除的管理员用户名快照
    created_at        TEXT,              -- 入库时间；历史数据不可推断时为 NULL
    updated_at        TEXT,              -- 最近写入时间
    version           INTEGER NOT NULL DEFAULT 1 -- 乐观锁版本
);
```

共 39 列。阶段 4 历史迁移只设置可可靠确定的 `analysis_status=legacy`、`is_deleted=0` 和
`version=1`；阶段 6 新增的删除前路径、回收站路径和删除人快照仅在实际软删除时写入。不会用当前文件名冒充原始文件名，也不会用拍摄时间、文件修改时间或自增编号
推导创建时间。分析脚本为新处理照片计算文件摘要并维护运行、失败、成功状态。

`date_source` 标记 `exif_datetime` 是真实拍摄时间还是兜底来的（四级兜底规则详见 03 文档）。
`xmp`（多为 PS 编辑时间）和 `mtime`（文件修改时间）两类语义较弱，
排查「照片日期不对」类问题时先看这个字段。

### admin_users 表

管理员账号由正式迁移 `sql/migrations/0003_create_admin_users.sql` 创建：

```sql
CREATE TABLE admin_users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT NOT NULL COLLATE NOCASE UNIQUE,
    password_hash TEXT NOT NULL,
    is_active     INTEGER NOT NULL DEFAULT 1,
    last_login_at TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
```

- `username` 使用 `COLLATE NOCASE UNIQUE`，用户名唯一性不区分大小写；
- `password_hash` 只保存 Werkzeug 安全哈希，迁移不创建默认管理员或默认密码；
- `is_active` 控制账号是否允许建立和恢复会话；
- 登录成功时，`AuthenticationService` 在单一 `BEGIN IMMEDIATE` 短事务中删除当前匿名组合键的失败事件，并更新 `last_login_at` 和 `updated_at`；任一步失败全部回滚；
- 密码哈希校验和管理员查询均在写事务之外完成；管理员创建和查询集中在 `AdminUserRepository`，复用应用工厂的请求级连接提供器，值全部参数化。

### admin_login_failures 表

迁移 0046 创建 `admin_login_failures(attempt_key, failed_at_epoch, attempt_nonce)`，三列组成复合主键；迁移 0047 创建以 `failed_at_epoch` 为首列的过期清理索引。用户名先执行 `strip().casefold()`，直接连接客户端地址通过 `ipaddress` 规范化，二者以空字符分隔后使用 `SECRET_KEY` 做 HMAC-SHA256，只保存不可逆的 `attempt_key`，不保存明文用户名或地址，也不信任 `X-Forwarded-For`。

限流判断使用只读连接统计滑动窗口事件；失败记录在短写事务中删除当前键过期事件、插入随机 nonce 事件并计数，同时借助过期索引最多清理 256 条全局过期事件。多个 Web 进程和独立应用实例共享同一窗口。

`src/migrations.py::assert_current_schema()` 先校验迁移历史，再断言照片生命周期字段、`photo_audit_log`、
`admin_users`、两类后台任务、配置单例与审计表、`photo_lifecycle_operations`、任务关键索引和大小写不敏感用户名唯一约束。唯一目标常量要求本地迁移文件和数据库台账版本集合都恰好为 0001 至 0048；台账内每个已知版本的名称与 SQL 文件 SHA-256 校验值必须匹配。未来版本或同版本不同身份的分叉历史会在业务结构检查前失败。所有迁移仍遵守
“一份文件一条 SQL”，不修改任何已执行迁移的原始字节。

### app_settings 与 app_settings_audit 表

阶段 7 配置核心通过迁移 0036 至 0043 增加全局配置和任务快照结构：

- `app_settings` 是 `id=1` 单例，`settings_json` 只保存允许热更新的非敏感覆盖值，`version` 从 0 开始并在每次成功批量更新时递增；同时保留最后修改人的编号、用户名快照和时间；
- `app_settings_audit` 每次批量更新保存唯一批次编号、旧新版本、变更键、旧新值和操作人快照，按创建时间与编号建立倒序索引；
- 配置 JSON、全局版本和审计插入位于同一个 `BEGIN IMMEDIATE` 事务，审计失败会回滚配置更新；提交使用期望版本执行乐观锁检查；
- `admin_jobs` 与 `admin_maintenance_jobs` 均新增 `config_version INTEGER NOT NULL DEFAULT 0` 和 `config_snapshot_json TEXT NOT NULL DEFAULT '{}'`。首次认领依据认领前 `started_at IS NULL`，并在认领的同一 `BEGIN IMMEDIATE` 事务中写入作用域版本和完整非敏感快照；租约恢复、自动重试和人工重试不更新这两个字段。仅升级前已启动且仍为 `0/{}` 的历史任务按当前配置回退执行，其他非法 JSON、版本不一致、缺键或越权快照统一按 `invalid_config_snapshot` 失败；
- 系统配置和敏感配置不通过服务写入 `settings_json`，敏感值不进入配置审计或任务快照。

截至 2026-08-07，正式 `data/photos.db` 本轮仅执行只读 `check-schema`，输出目标版本 43、迁移数量 43、最大迁移版本 43、`schema_current=true`；运行入口不会自动迁移，只有显式执行 `scripts/database_admin.py migrate` 才会升级数据库。

### photo_audit_log 表

阶段 4 新增不可级联删除的照片修改审计表：

```sql
CREATE TABLE photo_audit_log (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    photo_id        INTEGER NOT NULL,
    admin_user_id   INTEGER NOT NULL,
    admin_username  TEXT NOT NULL,
    action          TEXT NOT NULL,
    old_values_json TEXT NOT NULL,
    new_values_json TEXT NOT NULL,
    batch_id        TEXT,
    created_at      TEXT NOT NULL,
    FOREIGN KEY (photo_id) REFERENCES photo_scores(id),
    FOREIGN KEY (admin_user_id) REFERENCES admin_users(id)
);
```

照片更新和审计插入在同一个 `BEGIN IMMEDIATE` 事务内提交，任何数据库异常都会一起回滚。
审计保留操作时的用户名快照，批量操作使用 `batch_id` 关联同批成功项；不存在或版本冲突的
项目不会写入审计。索引覆盖 `(photo_id, created_at DESC)` 和
`(admin_user_id, created_at DESC)`。

### admin_jobs 与 admin_job_events 表

阶段 5 的 `admin_jobs` 保存三种任务：照片分析、旁白生成和历史最终文件摘要回填。任务有 pending、running、succeeded、failed、canceled 五态及优先级；队列索引按状态、优先级、租约、创建时间和编号选择任务。部分唯一索引禁止同一照片和任务类型同时存在多个 pending/running 任务。认领在单一 `BEGIN IMMEDIATE` 事务中完成，并同时递增 `photo_scores.version`、把分析照片切为 running、刷新 `admin_jobs.photo_version` 和写入认领事件。

`admin_job_events` 记录任务编号、事件类型、旧新状态、管理员编号或工作进程编号、稳定原因码与时间。取消请求及终结、人工重试、认领、自动重试、租约恢复、成功、最终失败和照片版本冲突均与状态变化同事务记录；不保存密钥、模型原始响应或异常正文。

分析任务排队时照片进入 pending；认领进入 running；成功进入 succeeded，普通最终失败与任务取消均进入 failed，取消时 `analysis_error=job_canceled`。`canceled` 只属于 `admin_jobs.status`，不写入 `photo_scores.analysis_status`。自动重试回到 pending。无取消请求的 `analyze_photo` 租约过期时，恢复事务读取未删除照片的当前版本，并且仅在 `analysis_status=running` 时按该版本协调照片和任务：未耗尽尝试次数时同步回到 pending 并清空分析错误及任务终态字段，耗尽时同步进入 `failed/max_attempts_exceeded` 并补齐稳定摘要与结束时间。旁白、摘要或管理员编辑可以合法推进全局照片版本，因此恢复不使用任务认领时的旧版本；同类型活跃任务唯一约束保证当前版本仍对应唯一分析任务。若照片不存在、已删除、分析状态已改变或条件更新失败，照片保持不变，任务以完整的 `failed/photo_version_conflict` 终态关闭、清空租约并记录 `lease_recovered` 事件。重新分析失败只改变生命周期与稳定错误码，不清空旧描述、评分、拍摄字段或旁白。结果提交使用 `photo_id + photo_version` 乐观锁，管理员并发编辑会产生 `photo_version_conflict` 事件且不会被覆盖。

主动让出只适用于可中断的 `backfill_content_hash` 历史最终文件摘要回填任务；事务会把任务放回 pending、退还本次尝试次数、清空租约并记录 `yielded` 事件。`analyze_photo` 照片分析任务和 `generate_narration` 旁白生成任务不允许进入 `defer`，仓储校验与 SQL 更新条件同时限制任务类型，避免任务与照片分析状态分裂。

普通运行任务取消先设置 `cancel_requested=1`，工作进程在安全边界关闭任务；如果照片版本已被编辑或恢复流程推进，旧任务只终结自身，不更新当前照片。续租要求任务仍为当前持有者、未取消且租约未过期；租约恢复遇到取消请求时优先写入 `canceled`、清空租约并补齐 `finished_at`。照片软删除则在同一个 `BEGIN IMMEDIATE` 事务中按顺序完成照片删除及分析状态收口、全部活跃照片任务终结与事件、生命周期审计、显示屏蔽和渲染排队。软删除事务直接撤销旧任务提交权，恢复照片和后续新任务通过新的版本链与旧任务隔离。

上传正式目录为 `IMAGE_DIR/uploads/YYYY/MM/<uuid>.<ext>`。规范化临时文件直接创建在同一年月目录，以系统专属 `.inktime-upload.tmp` 后缀标识；完成磁盘同步后用 `os.replace` 原子发布。整批照片与分析任务在单数据库事务创建，失败删除本批正式文件。`content_sha256` 始终对应规范化后的正式文件字节，原始上传流摘要不写入该字段。迁移 0020 至 0023 每份文件恰好一条 SQL，并由迁移加载器在接触数据库前校验。

### 阶段 6 回收站、维护表与生命周期操作台账

迁移 0024 至 0035 连续增加回收站和维护任务结构，迁移 0044 至 0045 补充显示产物期望代次，迁移 0048 新增照片生命周期操作台账；每个迁移文件仍恰好一条 SQL 语句：

- `photo_scores.original_path`、`trash_path`、`deleted_by_user_id`、`deleted_by_username` 保存删除前位置、实际回收站位置和操作人快照；
- `photo_lifecycle_audit` 保存软删除、恢复、永久删除意图与完成、清理逐项结果。它只保存照片编号和路径快照，不对 `photo_scores` 或管理员建立强外键；
- `admin_maintenance_jobs` 独立承载 `render_display` 和 `cleanup_expired_trash`，含五态、租约、最多三次尝试、`result_json` 和创建人快照；同类型 pending/running 任务由部分唯一索引去重。续租、普通完成和渲染发布都要求任务仍为 running、当前工作进程仍为 `lease_owner`、未请求取消且 `lease_expires_at` 晚于当前协调世界时，过期租约不能被续回；
- `admin_maintenance_job_events` 保存维护任务状态事件，不保存异常正文；
- `display_artifact_state` 是 `id=1` 单例，保存 `blocked`、已发布代次 `generation`、期望代次 `desired_generation`、`manifest_json`、更新时间和关联维护任务。迁移 0044 增加期望代次，0045 按既有屏蔽状态回填：未屏蔽时与已发布代次相等，已屏蔽时至少领先一代。删除或恢复在照片事务内递增期望代次；渲染任务载荷携带 `render_generation`，只有该代次同时通过租约与业务代次栅栏时才能发布并解除屏蔽；
- `idx_photo_trash_expiry(is_deleted, deleted_at, id)` 支持按协调世界时截止和稳定编号分批清理。

`photo_lifecycle_operations` 不对照片或管理员建立外键，避免恢复时被级联或引用约束阻断。迁移 0048 创建的关键字段如下：

| 字段 | 语义 |
|------|------|
| `operation_id` | 非空操作标识，主键 |
| `action` | 仅允许 `soft_delete` 或 `restore` |
| `photo_id`、`expected_version` | 唯一照片编号与操作开始时的乐观锁版本；唯一约束保证同一照片最多一条生命周期操作 |
| `source_path`、`destination_path` | 本次文件移动的来源和目标绝对路径 |
| `admin_user_id`、`admin_username` | 操作管理员编号与用户名快照 |
| `lease_owner`、`lease_expires_at` | 对账认领者与租约过期时间；只有过期操作可被恢复流程认领 |
| `created_at`、`updated_at` | 操作创建与最近更新时间 |

`PhotoLifecycleService` 在软删除或恢复移动文件前先写入带租约的持久化操作意图。文件移动后的业务状态提交与删除该操作台账位于同一数据库事务，因此不会留下“业务已提交但台账仍待对账”的中间状态。普通异常先执行反向文件补偿，补偿成功后删除台账；补偿失败则保留台账并报告错误，交给后续对账处理。

Web 服务启动和维护工作进程每轮逐条原子认领租约已经过期的生命周期操作。每条在文件对齐前都会重新读取当前台账，确认 `lease_owner` 仍为本轮恢复者且 `lease_expires_at` 尚未到期，并以该当前行判断数据库严格业务前态或后态：前态要求文件位于 `source_path`，后态要求文件位于 `destination_path`。若两条路径同时存在，只有确认指向同一 inode 时才删除冗余硬链接；数据库状态无法严格归类、租约失效、两路径内容冲突或其他路径状态不明确时，不猜测、不覆盖，保留操作台账并报错。

永久删除在写入 `purge_requested` 的同一短写事务内先确认该照片没有 `photo_lifecycle_operations` 台账；恢复创建台账时则检查最近一条永久删除状态，只有最近状态为 `purge_requested` 才拒绝恢复。SQLite 写事务串行化保证恢复先创建台账时永久删除被拒绝，永久删除先提交请求意图时恢复被拒绝；最近状态变为 `purge_failed` 后允许恢复。文件删除遇到操作系统错误或已识别服务器错误且照片仍存在时，尽力以独立短事务写入包含 `expected_version` 和稳定 `error_code` 的 `purge_failed`，不保存异常正文；失败审计自身异常只记录包含照片编号的错误日志，不覆盖原始异常。文件不存在仍可继续数据库收尾；最终事务按
`admin_job_events → admin_jobs → photo_audit_log → display_stats → photo_scores` 顺序清理强依赖并写
`purge_completed`。重复永久删除重试可以再次写 `purge_requested`，普通确认错误不写 `purge_failed`。`display_stats` 的真实结构仍是 `photo_id/channel/show_count/last_shown_at`，无外键。

过期清理预览使用只读连接，条件固定为 `is_deleted=1 AND deleted_at<=协调世界时截止`。维护任务认领会排除 `cancel_requested`；过期运行任务已有取消请求时直接进入 `canceled`，不会重新排队。执行任务按照片编号每批最多 500 项，`cleanup_batch` 采用明确的项目边界协作取消契约：每项开始前检查取消状态和租约所有权；检查通过即越过该项安全边界，当前项可能完成，之后观察到取消或失租只保证不再开始后续项。工作进程不会完成已中断的当前任务或创建后继任务，且不会为了取消语义引入覆盖单项文件操作的长期数据库事务。

未中断的每项清理独立调用幂等永久删除并写 `cleanup_item_result` 生命周期审计。候选已不存在时记为 `skipped` 并安全推进游标；版本或状态冲突以及其他异常记为 `failed`，批次在首个失败项停止，游标只跨过此前 `succeeded/skipped` 项。含失败项的维护任务不进入成功完成事务，也不创建后继任务，而是保留原始 `after_id` 由当前任务按最多三次尝试有限重试；此前已删除记录会被预览自然排除。只有无失败且未中断的批次才保存结果，并在仍有剩余项时原子创建后继清理任务，避免取消后继续删除或永久故障无限排队。

### 关于主键

早期版本以 `path TEXT PRIMARY KEY` 建表、没有 `id` 列，而 `server.py` 的 5 处查询
（`/api/photos`、`/api/search`、`/api/category/stats`、`/api/category/photos`、
`/api/photo/<id>`）都需要 `id`，导致 WebUI 全部列表页和详情页报 `no such column: id`。

现已统一为显式 `id INTEGER PRIMARY KEY AUTOINCREMENT` + `path TEXT UNIQUE NOT NULL`。
SQLite 虽然有隐式 `rowid` 可以用 `SELECT rowid AS id` 顶替，但 `rowid` 在
`INSERT OR REPLACE` 和 `VACUUM` 之后可能变化，不适合当业务标识，故不采用。

### 建表与迁移方式

数据库结构只由 `sql/migrations/` 与 `src/migrations.py` 的版本化迁移维护。
`analyze_photos_docker.py` 启动时只调用 `assert_current_schema()` 检查必要结构；缺表或缺字段时立即失败，
不再静默执行 `ALTER TABLE`。首次迁移必须先在 SQLite backup API 创建的数据库副本上演练，
确认幂等和数据不变量后才能安排正式环境迁移。

`sql/photo_scores.sql` 是历史结构参考，不是建库入口；新增或修改字段必须新增迁移文件，
禁止恢复启动时补列逻辑。

### display_stats 表

展示页的选片状态，与 `photo_scores` 分离：

```sql
CREATE TABLE display_stats (
    photo_id      INTEGER NOT NULL,           -- 关联 photo_scores.id
    channel       TEXT    NOT NULL DEFAULT 'web',  -- 展示渠道，为墨水屏预留
    show_count    INTEGER NOT NULL DEFAULT 0, -- 已展示次数，轮次算法的依据
    last_shown_at TEXT,                       -- 上次展示时间；为空表示从未展示过
    PRIMARY KEY (photo_id, channel)
);
CREATE INDEX idx_display_stats_channel_count ON display_stats (channel, show_count);
```

拆表原因：`photo_scores` 是分析产物，展示计数是运行时状态。混在一张表里会让
分析脚本的 UPSERT 每次都要小心别覆盖掉计数，而拆开后「清空展示历史」也只是
清一张表的事（`gallery.reset()`）。

`channel` 为墨水屏预留：它的选片是「历史上的今天」逻辑，与展示页完全不同，
两边计数必须分开否则会互相打乱轮次。

`display_stats` 保持历史上的无外键结构；当前分析脚本不再删除照片行，因此不会新增由
磁盘缺失导致的孤儿记录。候选查询仍通过 `JOIN photo_scores` 并应用生命周期条件，只有
`is_deleted=0` 且状态为 `legacy` 或 `succeeded` 的照片可以参与展示。

> 注意 `photo_scores.used_at` 字段虽然语义相近，但至今从未被写入，
> 展示计数一律记在本表。

## 数据写入

### 写入时机

- `analyze_photos_docker.py` 每分析完一张照片立即写库 + `COMMIT`
- 保证断点续跑：即使中途中断，已分析的数据不丢失

### 写入策略

```sql
INSERT INTO photo_scores (path, caption, ...) VALUES (...)
ON CONFLICT(path) DO UPDATE SET
    caption = excluded.caption,
    memory_score = excluded.memory_score,
    ...
```

- 用 UPSERT 而非 `INSERT OR REPLACE`：后者在 `path` 冲突时是「删旧行 + 插新行」，
  会导致自增 `id` 变化，WebUI 已有的 `/api/photo/<id>` 链接在重新分析后失效
- UPSERT 原地更新，`id` 保持不变
- `used_at` 不在 `DO UPDATE` 列表中，因此重新分析不会清掉展示记录
  （旧实现靠 `COALESCE` 子查询保留，UPSERT 下不再需要）
- 需要 SQLite ≥ 3.24（Python 3.12 自带 3.45，满足）


## 数据读取

SELECT path, exif_datetime, side_caption, memory_score,

  AND is_deleted = 0

## Docker 数据持久化

Docker Compose 六服务的权限矩阵如下：

| 服务 | `data/` | `logs/` | `${IMAGE_DIR}` | 原因 |
|------|---------|---------|----------------|------|
| `inktime-schema` | 读写 | 不挂载 | 不挂载 | 只读检查 `/app/data/photos.db` 的结构，挂载本身保留读写以复用同一部署目录 |
| `inktime-server` | 读写 | 读写 | 读写 | 上传、软删除、恢复和回收站清理需要修改照片目录 |
| `inktime-worker` | 读写 | 读写 | 读写 | 后台任务会分析、发布和维护文件 |
| `inktime-analyzer` | 读写 | 读写 | 只读 | `tools` profile 一次性分析工具 |
| `inktime-render-7c` | 读写 | 读写 | 只读 | `tools` profile 的 7.3 寸四色渲染工具 |
| `inktime-render-133c` | 读写 | 读写 | 只读 | `tools` profile 的 13.3 寸六色渲染工具 |

数据库固定为 `/app/data/photos.db`，输出为 `/app/data/output`。`${IMAGE_DIR}` 在容器内外必须保持同一个绝对路径，否则数据库保存的绝对照片路径会失效。工具服务对照片目录的只读挂载是正确的安全边界，不能套用到需要写入照片目录的 Web 服务和后台工作进程。

## 数据库迁移、门禁与连接策略

数据库结构由 `sql/migrations/` 和 `src/migrations.py` 维护，执行记录写入 `schema_migrations`。所有连接经 `src/database.py` 创建：可写连接启用预写日志，所有连接启用外键检查、`busy_timeout=5000` 和 `sqlite3.Row`。数据库不能放在服务器消息块或网络文件系统共享目录上。

运行入口不会自动迁移。只有以下显式命令会升级调用方指定的数据库：

```bash
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/target.db
```

`check-schema` 是只读结构门禁，内部调用 `assert_current_schema()`，不写数据库：

```bash
./venv/bin/python scripts/database_admin.py check-schema --database /absolute/path/to/target.db
```

成功 JSON 的关键字段是 `schema_target=48`、`migration_count`、`max_migration` 和 `schema_current`。严格 `verify` 不只调用结构断言，还要求迁移版本恰好连续为 1 至 48，并检查 `integrity_check`、`quick_check`、`foreign_key_check`、`foreign_keys=1`、`busy_timeout=5000`、`date_source`、`admin_users`、`admin_login_failures` 复合主键与过期索引、`photo_lifecycle_operations` 字段，以及照片数量、编号范围、去重编号数、去重路径数和 `id + path` 摘要六项身份基线。

## 备份、恢复与阶段 8 验证

`backup` 使用 SQLite backup API 创建活动库的一致性副本和身份基线；备份目标随后切换为独立的 DELETE 日志模式，禁止用简单 `cp` 复制启用预写日志的活动数据库：

```bash
./venv/bin/python scripts/database_admin.py backup \
  --database data/photos.db \
  --output-dir data/backups
```

恢复前先停止 Web 服务、后台工作进程、分析和渲染写入；恢复后运行严格验证：

```bash
./venv/bin/python scripts/database_admin.py verify \
  --database /absolute/path/to/restored.db \
  --baseline /absolute/path/to/photos-YYYYMMDD-HHMMSS.baseline.json
```

本轮已在临时目录完成 `35→43→35→43` 演练：首次迁移严格 `verify` 通过；恢复后 `integrity_check=ok`、`foreign_key_check=0`，照片身份不变量一致；再次迁移后严格 `verify` 通过。正式 `data/photos.db` 本轮只读 `check-schema` 输出 `schema_target=43`、`migration_count=43`、`max_migration=43`、`schema_current=true`，未对正式库执行写入迁移。
