# 07 - 数据库与存储

## 数据库选型

使用 SQLite，原因：
- 零配置，无需独立服务器
- 单文件存储，易于备份和迁移
- Python 标准库内置 `sqlite3`
- 适合单用户、中小规模数据量

## 表结构

### photo_scores 表

```sql
CREATE TABLE photo_scores (
    id                INTEGER PRIMARY KEY AUTOINCREMENT, -- 自增主键，WebUI 的 /api/photo/<id> 依赖它
    path              TEXT UNIQUE NOT NULL,  -- 照片文件绝对路径，唯一约束 + 断点续跑去重依据
    caption           TEXT,              -- AI 生成的画面描述（80-200字）
    type              TEXT,              -- 照片类型（人物/风景/美食等，可多个用/分隔）
    memory_score      REAL,              -- 值得回忆度（0-100，一位小数）
    beauty_score      REAL,              -- 美观程度（0-100，一位小数）
    reason            TEXT,              -- 评分理由（不超过60字）
    width             INTEGER,           -- 照片宽度（像素）
    height            INTEGER,           -- 照片高度（像素）
    orientation       TEXT,              -- 方向：landscape/portrait/square
    used_at           TEXT,              -- 上次被选中展示的时间
    exif_json         TEXT,              -- 完整 EXIF 数据（JSON 格式）
    raw_json          TEXT,              -- VLM 原始返回（JSON 格式）
    exif_datetime     TEXT,              -- 拍摄时间
    exif_make         TEXT,              -- 相机制造商
    exif_model        TEXT,              -- 相机型号
    exif_iso          INTEGER,           -- ISO 感光度
    exif_exposure_time REAL,             -- 曝光时间
    exif_f_number     REAL,              -- 光圈值
    exif_focal_length REAL,              -- 焦距
    exif_gps_lat      REAL,              -- GPS 纬度
    exif_gps_lon      REAL,              -- GPS 经度
    exif_gps_alt      REAL,              -- GPS 海拔
    side_caption      TEXT,              -- 一句话文案（8-24字）
    exif_city         TEXT,              -- 拍摄城市（中文）
    date_source       TEXT,              -- exif_datetime 来源：exif/xmp/filename/manual/none
    original_filename TEXT,              -- 导入时原始文件名；历史数据不可推断时为 NULL
    content_sha256    TEXT,              -- 文件内容 SHA-256；未回填或文件缺失时为 NULL
    analysis_status   TEXT NOT NULL DEFAULT 'legacy', -- legacy/pending/running/succeeded/failed
    analysis_error    TEXT,
    is_included       INTEGER NOT NULL DEFAULT 0, -- 人工收录开关，默认排除；未收录不分析、不展示              -- 稳定错误类型或 source_file_missing
    is_deleted        INTEGER NOT NULL DEFAULT 0, -- 软删除标记，阶段 4 暂不开放操作
    deleted_at        TEXT,              -- 软删除时间
    original_path     TEXT,              -- 删除前的规范绝对路径
    trash_path        TEXT,              -- 仅历史数据非空；新语义下删除不移动文件，一律 NULL
    deleted_by_user_id INTEGER,           -- 执行软删除的管理员编号快照
    deleted_by_username TEXT,             -- 执行软删除的管理员用户名快照
    created_at        TEXT,              -- 入库时间；历史数据不可推断时为 NULL
    updated_at        TEXT,              -- 最近写入时间
    version           INTEGER NOT NULL DEFAULT 1 -- 乐观锁版本
);
```

共 40 列。

`is_included` 是人工收录开关，**列默认 0（排除）**，这个默认值是有意的：它让「导入照片」这个动作
彻底免费。加一个几百张的照片目录只写库、不产生任何模型调用，要不要花钱分析由管理员逐张或批量
决定。迁移 0052 把存量的 `legacy` 与 `succeeded` 照片回填为 1，避免升级后现有相框内容突然消失。

写入这一列的三条路径口径不同，排查时要分清：

| 路径 | 写入值 | 说明 |
|---|---|---|
| 目录扫描 `LibraryScanService.scan()` | 取自配置 `NEW_PHOTO_CURATION` | `excluded`（默认）写 0，`included` 写 1；无法识别的取值按 0 处理 |
| 后台上传 `create_uploaded_photos_and_jobs()` | 固定 1 | 上传本身就是逐张的人工收录决定，且同事务直接建分析任务，不读配置 |
| 人工修改（单张详情页、批量操作栏） | 0 或 1 | 走乐观锁与 `photo_audit_log` 审计；`0 → 1` 会触发自动排队分析，`1 → 0` 会撤销待执行任务 |

收录状态与另外两个概念必须分清，混用会得出自相矛盾的界面：

| 环节 | 由谁决定 | 字段 | 性质 |
|---|---|---|---|
| 是否收录 | 管理员人工标记，新照片初值取自 `NEW_PHOTO_CURATION` | `is_included` | 长期有效的归属判断 |
| 是否分析 | 收录跃迁自动排队，或管理员按张数放行 | `analysis_status` | 一次性流水线动作 |
| 是否展示 | 回忆分与 `DISPLAY_MIN_SCORE` 阈值 | `memory_score` | 分析结果推导 |

因此「已收录」不等于「会展示」——收录只表示这张照片有资格参与，够不够好仍由评分决定。反过来
「未收录」是硬排除：候选池（`gallery._pool_where`）、公开可见条件
（`photo_repository.VISIBLE_PHOTO_CONDITION`）与两个墨水屏渲染脚本都带 `is_included = 1`，
四处缺一处就会出现「明明排除了却还在轮播」。

阶段 4 历史迁移只设置可可靠确定的 `analysis_status=legacy`、`is_deleted=0` 和
`version=1`；阶段 6 新增的删除前路径、回收站路径和删除人快照仅在实际软删除时写入。不会用当前文件名冒充原始文件名，也不会用拍摄时间、文件修改时间或自增编号
推导创建时间。分析脚本为新处理照片计算文件摘要并维护运行、失败、成功状态。

`date_source` 标记 `exif_datetime` 是真实拍摄时间还是兜底来的（四级兜底规则详见 03 文档）。
`xmp`（多为 PS 编辑时间）语义较弱，
排查「照片日期不对」类问题时先看这个字段。

### admin_users 表

管理员账号由正式迁移 `sql/migrations/0003_create_admin_users.sql` 创建：

```sql
CREATE TABLE admin_users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT NOT NULL COLLATE NOCASE UNIQUE,
    password_hash TEXT NOT NULL,
    is_active     INTEGER NOT NULL DEFAULT 1,
    last_login_at TEXT,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
```

- `username` 使用 `COLLATE NOCASE UNIQUE`，用户名唯一性不区分大小写；
- `password_hash` 只保存 Werkzeug 安全哈希，迁移不创建默认管理员或默认密码；
- `is_active` 控制账号是否允许建立和恢复会话；
- 登录成功时，`AuthenticationService` 在单一 `BEGIN IMMEDIATE` 短事务中删除当前匿名组合键的失败事件，并更新 `last_login_at` 和 `updated_at`；任一步失败全部回滚；
- 密码哈希校验和管理员查询均在写事务之外完成；管理员创建和查询集中在 `AdminUserRepository`，复用应用工厂的请求级连接提供器，值全部参数化。

### admin_login_failures 表

迁移 0046 创建 `admin_login_failures(attempt_key, failed_at_epoch, attempt_nonce)`，三列组成复合主键；迁移 0047 创建以 `failed_at_epoch` 为首列的过期清理索引。用户名先执行 `strip().casefold()`，直接连接客户端地址通过 `ipaddress` 规范化，二者以空字符分隔后使用 `SECRET_KEY` 做 HMAC-SHA256，只保存不可逆的 `attempt_key`，不保存明文用户名或地址，也不信任 `X-Forwarded-For`。

限流判断使用只读连接统计滑动窗口事件；失败记录在短写事务中删除当前键过期事件、插入随机 nonce 事件并计数，同时借助过期索引最多清理 256 条全局过期事件。多个 Web 进程和独立应用实例共享同一窗口。

`src/migrations.py::assert_current_schema()` 先校验迁移历史，再断言照片生命周期字段、`photo_audit_log`、
`admin_users`、两类后台任务、配置单例与审计表、模型厂商档案与审计表、`photo_lifecycle_operations`、`photo_purge_operations`、任务关键索引和大小写不敏感用户名唯一约束。唯一目标常量要求本地迁移文件和数据库台账版本集合都恰好为 0001 至 0058；迁移 0050 为 `admin_jobs` 增加可空 `result_json`，迁移 0051 为 `photo_scores` 增加收录标记 `is_included`、0052 回填存量照片，迁移 0053 至 0055 增加模型厂商档案表、审计表与审计时间索引，迁移 0056 为 `model_providers` 增加当前启用模型 `active_model`、0057 把存量档案回填为模型池第一项、0058 增加厂商特有请求参数 `request_options`，结构门禁也明确断言这些列。台账内每个已知版本的名称与 SQL 文件 SHA-256 校验值必须匹配。未来版本或同版本不同身份的分叉历史会在业务结构检查前失败。所有迁移仍遵守
“一份文件一条 SQL”，不修改任何已执行迁移的原始字节。

### app_settings 与 app_settings_audit 表

阶段 7 配置核心通过迁移 0036 至 0043 增加全局配置和任务快照结构：

- `app_settings` 是 `id=1` 单例，`settings_json` 只保存允许热更新且无需重启的覆盖值（含可在线只写覆盖的 `API_KEY` 明文），`version` 从 0 开始并在每次成功批量更新时递增；同时保留最后修改人的编号、用户名快照和时间；
- `app_settings_audit` 每次批量更新保存唯一批次编号、旧新版本、变更键、旧新值和操作人快照，按创建时间与编号建立倒序索引。**敏感键的旧新值在写入前就替换为「已脱敏」**，判定口径由 `configuration.is_sensitive_key()` 统一提供，写入路径与展示路径共用同一份判断；早期实现只在展示层脱敏，数据库里躺的是原值，备份、`sqlite3` 直连与误导出都能绕过展示层读到密钥；
- 配置 JSON、全局版本和审计插入位于同一个 `BEGIN IMMEDIATE` 事务，审计失败会回滚配置更新；提交使用期望版本执行乐观锁检查；
- `admin_jobs` 与 `admin_maintenance_jobs` 均新增 `config_version INTEGER NOT NULL DEFAULT 0` 和 `config_snapshot_json TEXT NOT NULL DEFAULT '{}'`。首次认领依据认领前 `started_at IS NULL`，并在认领的同一 `BEGIN IMMEDIATE` 事务中写入作用域版本和完整非敏感快照；租约恢复与自动重试不更新这两个字段；人工重试会把 `started_at` 置空，使下次认领重新写入这两个字段。仅升级前已启动且仍为 `0/{}` 的历史任务按当前配置回退执行，其他非法 JSON、版本不一致、缺键或越权快照统一按 `invalid_config_snapshot` 失败；
- 锁定的系统与安全配置不通过服务写入 `settings_json`；敏感值不进入配置审计或任务快照，唯一例外是可在线只写覆盖的 `API_KEY`，它的明文存在 `settings_json` 中，审计仍记为“已脱敏”。

截至 2026-08-16，正式 `data/photos.db` 已先备份到 `data/backups/photos-20260816-141118.db`，在备份副本成功演练迁移后显式执行 0050。正式库 `verify` 与 `check-schema` 输出目标版本 50、迁移数量 50、最大迁移版本 50、`schema_current=true`，完整性、外键和照片身份摘要均无差异。直接应用入口不会自动迁移；容器入口也只为完全不存在的数据库建库，不升级已有库，后续升级仍须显式执行 `scripts/database_admin.py migrate`。

### model_providers 与 model_provider_audit 表

迁移 0053 至 0055 增加多套模型接入档案，让公司自建、千问、豆包等配置可以共存而不互相覆盖：

```sql
CREATE TABLE model_providers (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    name             TEXT    NOT NULL UNIQUE,   -- 公司 / 千问 / 豆包
    base_url         TEXT    NOT NULL,
    model_name       TEXT    NOT NULL,
    api_key          TEXT    NOT NULL DEFAULT '',   -- 明文，与 API_KEY 同等信任级别
    api_key_hint     TEXT    NOT NULL DEFAULT '',   -- 末四位，仅供界面辨认
    timeout_seconds  INTEGER NOT NULL DEFAULT 600  CHECK (timeout_seconds >= 1),
    max_long_edge    INTEGER NOT NULL DEFAULT 2560 CHECK (max_long_edge BETWEEN 256 AND 8192),
    is_enabled       INTEGER NOT NULL DEFAULT 1    CHECK (is_enabled IN (0, 1)),
    version          INTEGER NOT NULL DEFAULT 1    CHECK (version >= 1),
    created_at       TEXT    NOT NULL,
    updated_at       TEXT    NOT NULL
);
```

**为什么另建表而不是往配置注册表加键**：`resolve_task_snapshot()` 断言任务快照的键集合与「注册表非敏感且作用域命中」的集合精确相等，往注册表加动态键（`API_URL_1`、`API_URL_2`）会让所有历史任务的旧快照立即判为 `invalid_config_snapshot`。而且厂商需要增删改，注册表是扁平单值结构撑不住。

几处约束的理由：

| 约束 | 理由 |
|---|---|
| `name` 唯一且不含分号 | 路由配置按名字引用档案；分号是降级候选串的分隔符，与 `IMAGE_DIR` 多目录沿用同一约定 |
| `model_name` 存一到多个可选模型，分号分隔 | 一个厂商常有多个可用视觉模型，逐个建档会把地址、密钥、超时抄好几遍。取值域从「一个名字」放宽到「一到多个名字」而不新开模型表：表结构与任务快照字段集合都不变，阶段三固化的历史快照因此继续可读。单个名字是这个格式的合法特例。服务层的 `_model_names()` 会去掉空格、空项与重复项后按分号归一化存回 |
| `request_options` 存厂商特有请求参数 | 同一个 OpenAI 兼容协议，各家扩展参数并不通用：`enable_thinking` 只有千问认，硬传给别家可能直接 400。因此按厂商存一个 JSON 对象，执行时合并进请求体顶层，值为 `null` 表示不发送该参数（有的参数只能靠不发送来关闭）。写入路径严格校验（必须是对象、限长），读取路径宽容（非法值按无参数处理）。该字段随候选进任务快照，且在快照校验里是**可选**字段，因此迁移 0058 之前固化的快照继续可读 |
| `active_model` 与模型池分成两列 | 只有这一列的模型会被真正调用，多模型**不自动轮换也不自动降级**——各模型授权额度不同，换模型必须是管理员的显式动作。分成两列而不是只存启用值：切换模型时不该要求把全部可选模型重抄一遍。约束由服务层保证而不是 `CHECK`：SQLite 的 `CHECK` 表达不了「属于另一列的分号列表之一」。显式选了池外的模型报错（提交与页面不一致），而只改池导致原启用模型失效时落回新池首项（正常编辑，否则得先切模型再改池）。`active_model_of()` 在列值为空或指向池外时按池首项执行，兜住存量库回填前与手工改库的情况 |
| 禁止改名（服务层拒绝） | 改名要么同步改所有引用、要么留下悬空引用。改名后分析会悄悄回退兜底配置且没有任何提示，因此只允许「删除后新建」 |
| `is_enabled` 停用而非删除 | 删除被引用的档案会让路由指向不存在的厂商 |
| 独立 `timeout_seconds`、`max_long_edge` | 本地 LM Studio 与云端千问的合理超时差很多。注册表同名键降级为「未配厂商时的兜底」 |
| `version` 乐观锁 | 与 `photo_scores`、`app_settings` 同一套约定 |

`api_key` **不进** `ModelProviderRepository.PUBLIC_COLUMNS`：`list_all`、`get`、`resolve_enabled` 一律不返回密钥，只有专用的 `secret_for()` 会返回。这样「把整行档案塞进接口响应或日志」不会泄露密钥，而不是靠每个调用方自己记得脱敏。

`model_provider_audit` 的 `provider_id` 允许悬空且**刻意不加外键**：档案删除后仍要能查到谁在什么时候删了哪个厂商，因此另存一份删除那一刻的 `provider_name` 快照。旧新值里的密钥在写入前替换为「已脱敏」，与配置审计同一口径。

<callout emoji="💡" background-color="light-blue">
表为空是完全合法的初始状态：未建档时分析链路回退注册表里的 `API_URL` 等兜底键，旧行为不变。因此结构门禁只断言表与关键列存在，不断言内容。这是过渡设计，等所有部署都建档后再单独移除兜底路径。
</callout>

### photo_audit_log 表

阶段 4 新增不可级联删除的照片修改审计表：

```sql
CREATE TABLE photo_audit_log (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    photo_id        INTEGER NOT NULL,
    admin_user_id   INTEGER NOT NULL,
    admin_username  TEXT NOT NULL,
    action          TEXT NOT NULL,
    old_values_json TEXT NOT NULL,
    new_values_json TEXT NOT NULL,
    batch_id        TEXT,
    created_at      TEXT NOT NULL,
    FOREIGN KEY (photo_id) REFERENCES photo_scores(id),
    FOREIGN KEY (admin_user_id) REFERENCES admin_users(id)
);
```

照片更新和审计插入在同一个 `BEGIN IMMEDIATE` 事务内提交，任何数据库异常都会一起回滚。
审计保留操作时的用户名快照，批量操作使用 `batch_id` 关联同批成功项；不存在或版本冲突的
项目不会写入审计。索引覆盖 `(photo_id, created_at DESC)` 和
`(admin_user_id, created_at DESC)`。

### admin_jobs 与 admin_job_events 表

阶段 5 的 `admin_jobs` 保存三种任务：照片分析、旁白生成和历史最终文件摘要回填。任务有 pending、running、succeeded、failed、canceled 五态及优先级；队列索引按状态、优先级、租约、创建时间和编号选择任务。部分唯一索引禁止同一照片和任务类型同时存在多个 pending/running 任务。迁移 0050 新增可空 `result_json`，只用于保存照片详情页待确认任务的版本化白名单结果。

`admin_job_events` 记录任务编号、事件类型、旧新状态、管理员编号或工作进程编号、稳定原因码与时间。取消请求及终结、人工重试、认领、自动重试、租约恢复、成功、最终失败和照片版本冲突均与状态变化同事务记录；不保存密钥、模型原始响应或异常正文。

普通分析任务排队时照片进入 pending；认领进入 running；成功进入 succeeded，普通最终失败与任务取消均进入 failed，取消时 `analysis_error=job_canceled`。详情页待确认任务由载荷中的严格来源、结果模式和结构版本标记识别，排队、认领、失败、取消、重试、恢复和完成都不修改 `photo_scores`；成功结果仅写 `admin_jobs.result_json`，完整分析和旁白分别使用独立字段白名单。同一照片最多存在一个活跃待确认任务，且正式任务与待确认任务双向互斥。安全查询只返回当前 `photo_scores.version` 下最新草稿，管理员在页面确认保存后才通过照片编辑事务写入正式字段并推进版本。既有正式 JSON 接口仍使用普通任务语义。

普通分析自动重试回到 pending。无取消请求的普通 `analyze_photo` 租约过期时，恢复事务读取未删除照片的当前版本，并且仅在 `analysis_status=running` 时按该版本协调照片和任务：未耗尽尝试次数时同步回到 pending，耗尽时同步进入 `failed/max_attempts_exceeded`。若照片不存在、已删除、分析状态已改变或条件更新失败，照片保持不变，任务以 `failed/photo_version_conflict` 终态关闭。普通重新分析失败不清空旧描述、评分、拍摄字段或旁白；结果提交继续使用 `photo_id + photo_version` 乐观锁。

主动让出只适用于可中断的 `backfill_content_hash` 历史最终文件摘要回填任务；事务会把任务放回 pending、退还本次尝试次数、清空租约并记录 `yielded` 事件。`analyze_photo` 照片分析任务和 `generate_narration` 旁白生成任务不允许进入 `defer`，仓储校验与 SQL 更新条件同时限制任务类型，避免任务与照片分析状态分裂。

普通运行任务取消先设置 `cancel_requested=1`，工作进程在安全边界关闭任务；如果照片版本已被编辑或恢复流程推进，旧任务只终结自身，不更新当前照片。续租要求任务仍为当前持有者、未取消且租约未过期；租约恢复遇到取消请求时优先写入 `canceled`、清空租约并补齐 `finished_at`。照片软删除则在同一个 `BEGIN IMMEDIATE` 事务中按顺序完成照片删除及分析状态收口、全部活跃照片任务终结与事件、生命周期审计、显示屏蔽和渲染排队。软删除事务直接撤销旧任务提交权，恢复照片和后续新任务通过新的版本链与旧任务隔离。

上传正式目录为 `IMAGE_DIR/uploads/YYYY/MM/<uuid>.<ext>`。规范化临时文件直接创建在同一年月目录，以系统专属 `.inktime-upload.tmp` 后缀标识；完成磁盘同步后用 `os.replace` 原子发布。整批照片与分析任务在单数据库事务创建，失败删除本批正式文件。`content_sha256` 始终对应规范化后的正式文件字节，原始上传流摘要不写入该字段。迁移 0020 至 0023 每份文件恰好一条 SQL，并由迁移加载器在接触数据库前校验。

### 删除是纯标记，不动磁盘文件

删除照片**只改数据库可见性**：`is_deleted=1` 之后后台列表、公开接口、候选池与墨水屏渲染都查不到这张照片，磁盘上的原文件留在原地不动。

早期实现会把原文件用硬链接加删除的方式搬进照片根目录下的 `.trash`，为此配了持久化操作意图台账、租约与反向补偿，来兜住「文件已移走但数据库还没提交」的中间态。改掉它有两条独立理由：

其一，和多照片目录的约定冲突。`IMAGE_DIR` 里第一个是主目录、其余「只读扫描」，搬文件等于往只读目录写入，还会在别人的照片库里建 `.trash`。

其二，硬链接不是所有文件系统都支持。挂在 SMB 网络共享上的照片目录直接返回 `[Errno 45] Operation not supported`，那些照片一张都删不掉。实测两个根目录的差异：本地 apfs 支持硬链接，`smbfs` 不支持。

因为不涉及文件操作，删除就是一次数据库事务、本身即原子，`photo_lifecycle_operations` 台账与补偿逻辑对软删除不再需要。

**记录永久保留，不提供彻底删除。** `purge()` 与 `enqueue_cleanup()`（含执行体 `cleanup_batch()`）一律抛 `ParameterError` 拒绝：

- 扫描按 `path` 去重且不限定 `is_deleted`，那条已删除的记录正是防止照片重新入库的**墓碑**。删了墓碑，同一张照片下次扫描就会重新登记。
- 原文件从不被移动，此时"永久删除"要么只删记录、留下会被重新扫入的文件，要么去删用户的原始照片库——前者无意义，后者不可接受。
- 过期自动清理尤其危险：`TRASH_RETENTION_DAYS` 默认 30 天，它会在后台悄悄抹掉墓碑，表现为「删过的照片一个月后自己回来了」，这种问题极难归因。执行体也必须拒绝，因为队列里可能残留升级前排入的清理任务。

**恢复要兼容两种形态**，靠 `trash_path` 是否为空区分：为空走 `_restore_in_place()`，只改数据库、`path` 保持原值；非空是历史记录，仍走带操作意图与补偿的文件移动路径把文件搬回原位，否则文件会永远留在 `.trash` 里。

历史遗留：旧实现每次失败的删除尝试都会先创建目标父目录再在 `os.link` 报错，因此网络共享的 `.trash` 下可能留着一批以照片编号命名的空目录。它们不含文件，可以安全删除。

### 阶段 6 回收站、维护表与生命周期操作台账

迁移 0024 至 0035 连续增加回收站和维护任务结构，迁移 0044 至 0045 补充显示产物期望代次，迁移 0048 新增照片生命周期操作台账，迁移 0049 新增唯一在途永久删除操作台账；每个迁移文件仍恰好一条 SQL 语句：

- `photo_scores.original_path`、`trash_path`、`deleted_by_user_id`、`deleted_by_username` 保存删除前位置、实际回收站位置和操作人快照；
- `photo_lifecycle_audit` 保存软删除、恢复、永久删除意图与完成、清理逐项结果。它只保存照片编号和路径快照，不对 `photo_scores` 或管理员建立强外键；
- `admin_maintenance_jobs` 独立承载 `render_display` 和 `cleanup_expired_trash`，含五态、租约、最多三次尝试、`result_json` 和创建人快照；同类型 pending/running 任务由部分唯一索引去重。续租、普通完成和渲染发布都要求任务仍为 running、当前工作进程仍为 `lease_owner`、未请求取消且 `lease_expires_at` 晚于当前协调世界时，过期租约不能被续回；
- `admin_maintenance_job_events` 保存维护任务状态事件，不保存异常正文；
- `display_artifact_state` 是 `id=1` 单例，保存 `blocked`、已发布代次 `generation`、期望代次 `desired_generation`、`manifest_json`、更新时间和关联维护任务。迁移 0044 增加期望代次，0045 按既有屏蔽状态回填：未屏蔽时与已发布代次相等，已屏蔽时至少领先一代。删除或恢复在照片事务内递增期望代次；渲染任务载荷携带 `render_generation`，只有该代次同时通过租约与业务代次栅栏时才能发布并解除屏蔽；
- `idx_photo_trash_expiry(is_deleted, deleted_at, id)` 支持按协调世界时截止和稳定编号分批清理。

`photo_lifecycle_operations` 不对照片或管理员建立外键，避免恢复时被级联或引用约束阻断。迁移 0048 创建的关键字段如下：

| 字段 | 语义 |
|------|------|
| `operation_id` | 非空操作标识，主键 |
| `action` | 仅允许 `soft_delete` 或 `restore` |
| `photo_id`、`expected_version` | 唯一照片编号与操作开始时的乐观锁版本；唯一约束保证同一照片最多一条生命周期操作 |
| `source_path`、`destination_path` | 本次文件移动的来源和目标绝对路径 |
| `admin_user_id`、`admin_username` | 操作管理员编号与用户名快照 |
| `lease_owner`、`lease_expires_at` | 对账认领者与租约过期时间；只有过期操作可被恢复流程认领 |
| `created_at`、`updated_at` | 操作创建与最近更新时间 |

`PhotoLifecycleService` 在软删除或恢复移动文件前先写入带租约的持久化操作意图。文件移动后的业务状态提交与删除该操作台账位于同一数据库事务，因此不会留下“业务已提交但台账仍待对账”的中间状态。普通异常先执行反向文件补偿，补偿成功后删除台账；补偿失败则保留台账并报告错误，交给后续对账处理。

Web 服务启动和维护工作进程每轮逐条原子认领租约已经过期的生命周期操作。软删除、恢复、普通异常补偿和崩溃对账都先取得主照片目录 `<primary>/.trash/.locks/<photo_id>.lock` 的跨进程排他锁；多目录下锁始终落在主目录，保证同一张照片只有一个锁命名空间；锁文件按照片编号稳定命名且只承担同步，不保存业务状态。所有受管路径按词法边界限制在已配置的照片根目录之一（`IMAGE_DIR` 支持分号分隔多个互不嵌套的根），归属唯一，回收站边界按所属根的 `.trash` 判断，拒绝根目录以下任何符号链接组件；移动、双路径文件身份比较和永久删除都从图片根目录文件描述符逐级使用 `O_NOFOLLOW` 打开父目录，再通过 `dir_fd` 相对执行状态检查、硬链接和删除，避免持有一张照片的锁却跟随链接操作另一张照片。原业务请求及其异常补偿取得锁后都重新确认自己的操作台账和未过期租约，已过期所有者不能续租或继续产生文件副作用，恢复者取得锁后用短只读事务确认认领所有权和数据库严格前态或后态，文件对齐后再用短 `BEGIN IMMEDIATE` 事务复核所有权、状态并删除台账。租约在文件操作期间被其他恢复者接管时，当前所有者不能删除台账，后继恢复者会在同一文件锁上等待并最终收敛；文件操作期间不持有 SQLite 全局写锁。状态判断会把 `photo_scores.path`、`original_path`、`trash_path` 的历史相对路径和台账绝对路径分别规范化到活动区或回收站受管路径后比较。若两条路径同时存在，只有确认指向同一 inode 时才删除冗余硬链接；数据库状态无法严格归类、租约失效、两路径内容冲突或其他路径状态不明确时，不猜测、不覆盖，保留操作台账并报错。

迁移 0049 新增 `photo_purge_operations`，为每张照片保存唯一在途永久删除操作编号、预期版本、回收站路径、调用者快照、租约所有者和租约时间。永久删除取得同一照片文件锁后，在短写事务内确认没有软删除或恢复台账，并创建操作或接管已经过期的同版本同路径操作；未过期操作会拒绝并发请求。恢复创建台账时只要发现任何在途永久删除就拒绝，不再依靠最新审计动作推断并发状态。文件删除失败时，只有当前操作所有者能在同一事务写 `purge_failed` 并删除自己的在途台账；完成事务同样校验操作编号和所有者、确认没有生命周期台账，再写 `purge_completed`、清理强依赖和照片行并删除在途台账。进程在删除文件后崩溃会留下台账，租约过期后重试可接管并以“文件已缺失”幂等完成；其他请求的失败审计不能解除当前在途操作的恢复门禁。

过期清理预览使用只读连接，条件固定为 `is_deleted=1 AND deleted_at<=协调世界时截止`。维护任务认领会排除 `cancel_requested`；过期运行任务已有取消请求时直接进入 `canceled`，不会重新排队。执行任务按照片编号每批最多 500 项，`cleanup_batch` 采用明确的项目边界协作取消契约：每项开始前检查取消状态和租约所有权；检查通过即越过该项安全边界，当前项可能完成，之后观察到取消或失租只保证不再开始后续项。工作进程不会完成已中断的当前任务或创建后继任务，且不会为了取消语义引入覆盖单项文件操作的长期数据库事务。

未中断的每项清理独立调用幂等永久删除并写 `cleanup_item_result` 生命周期审计。候选已不存在时记为 `skipped` 并安全推进游标；版本或状态冲突以及其他异常记为 `failed`，批次在首个失败项停止，游标只跨过此前 `succeeded/skipped` 项。含失败项的维护任务不进入成功完成事务，也不创建后继任务，而是保留原始 `after_id` 由当前任务按最多三次尝试有限重试；此前已删除记录会被预览自然排除。只有无失败且未中断的批次才保存结果，并在仍有剩余项时原子创建后继清理任务，避免取消后继续删除或永久故障无限排队。

### 关于主键

早期版本以 `path TEXT PRIMARY KEY` 建表、没有 `id` 列，而 `server.py` 的 5 处查询
（`/api/photos`、`/api/search`、`/api/category/stats`、`/api/category/photos`、
`/api/photo/<id>`）都需要 `id`，导致 WebUI 全部列表页和详情页报 `no such column: id`。

现已统一为显式 `id INTEGER PRIMARY KEY AUTOINCREMENT` + `path TEXT UNIQUE NOT NULL`。
SQLite 虽然有隐式 `rowid` 可以用 `SELECT rowid AS id` 顶替，但 `rowid` 在
`INSERT OR REPLACE` 和 `VACUUM` 之后可能变化，不适合当业务标识，故不采用。

### 建表与迁移方式

数据库结构只由 `sql/migrations/` 与 `src/migrations.py` 的版本化迁移维护。
`analyze_photos_docker.py` 启动时只调用 `assert_current_schema()` 检查必要结构；缺表或缺字段时立即失败，
不再静默执行 `ALTER TABLE`。首次迁移必须先在 SQLite backup API 创建的数据库副本上演练，
确认幂等和数据不变量后才能安排正式环境迁移。

`sql/photo_scores.sql` 是历史结构参考，不是建库入口；新增或修改字段必须新增迁移文件，
禁止恢复启动时补列逻辑。

### display_stats 表

展示页的选片状态，与 `photo_scores` 分离：

```sql
CREATE TABLE display_stats (
    photo_id      INTEGER NOT NULL,           -- 关联 photo_scores.id
    channel       TEXT    NOT NULL DEFAULT 'web',  -- 展示渠道，为墨水屏预留
    show_count    INTEGER NOT NULL DEFAULT 0, -- 轮转计数，不等于真实播放次数，见下文
    last_shown_at TEXT,                       -- 上次展示时间；为空表示从未展示过
    PRIMARY KEY (photo_id, channel)
);
CREATE INDEX idx_display_stats_channel_count ON display_stats (channel, show_count);
```

拆表原因：`photo_scores` 是分析产物，展示计数是运行时状态。混在一张表里会让
分析脚本的 UPSERT 每次都要小心别覆盖掉计数，而拆开后「清空展示历史」也只是
清一张表的事（`gallery.reset()`）。

`channel` 为墨水屏预留：它的选片是「历史上的今天」逻辑，与展示页完全不同，
两边计数必须分开否则会互相打乱轮次。

`display_stats` 保持历史上的无外键结构；当前分析脚本不再删除照片行，因此不会新增由
磁盘缺失导致的孤儿记录。候选查询仍通过 `JOIN photo_scores` 并应用生命周期条件，只有
`is_deleted=0` 且状态为 `legacy` 或 `succeeded` 的照片可以参与展示。

> 注意 `photo_scores.used_at` 字段虽然语义相近，但至今从未被写入，
> 展示计数一律记在本表。

**`show_count` 不是「被看过几次」**。新照片进入候选池时继承池内当前最小值作为基线
（`gallery._sync_new_photos`），之后每展示一次加一。这样做是为了让新照片立刻和老照片站在
同一起跑线、不至于被轮次算法连续猛推，代价是绝对值失去「播放次数」的含义，只能跨照片比较。
判断一张照片是否真的露过面要看 `last_shown_at` 是否为空，不能看 `show_count` 是否为 0。

**这张表不在 `sql/migrations` 里**，由 `gallery.ensure_table()` 在首次选片时懒创建，是历史遗留
结构。因此它有三种状态：不存在（库刚迁移完、展示页从未访问过）、存在但只有部分照片有行（只有
进过候选池的照片才有）、以及完整。任何读这张表的新代码都必须同时处理这三种情况。后台照片管理
页的展示次数列就踩过这个坑：`LEFT JOIN` 之后，缺表会让整个页面报错，于是 `create_app` 里加了
`_ensure_display_stats_table()` 启动幂等补建。补建刻意复用 gallery 的建表函数而不是在迁移目录
里复制一份 DDL——同一份结构有两个真相源，迟早漂移。

## 数据写入

### 写入时机

- `analyze_photos_docker.py` 每分析完一张照片立即写库 + `COMMIT`
- 保证断点续跑：即使中途中断，已分析的数据不丢失

### 写入策略

```sql
INSERT INTO photo_scores (path, caption, ...) VALUES (...)
ON CONFLICT(path) DO UPDATE SET
    caption = excluded.caption,
    memory_score = excluded.memory_score,
    ...
```

- 用 UPSERT 而非 `INSERT OR REPLACE`：后者在 `path` 冲突时是「删旧行 + 插新行」，
  会导致自增 `id` 变化，WebUI 已有的 `/api/photo/<id>` 链接在重新分析后失效
- UPSERT 原地更新，`id` 保持不变
- `used_at` 不在 `DO UPDATE` 列表中，因此重新分析不会清掉展示记录
  （旧实现靠 `COALESCE` 子查询保留，UPSERT 下不再需要）
- 需要 SQLite ≥ 3.24（Python 3.12 自带 3.45，满足）


## 数据读取

### 渲染模块读取

```sql
SELECT path, exif_datetime, side_caption, memory_score,
       exif_gps_lat, exif_gps_lon, exif_city
FROM photo_scores
WHERE exif_datetime IS NOT NULL
  AND is_deleted = 0
  AND analysis_status IN ('legacy', 'succeeded')
```

- `exif_datetime IS NOT NULL`（规范拍摄时间必须可用）
- `is_deleted = 0`（软删除记录不参与候选）
- `analysis_status IN ('legacy', 'succeeded')`（等待、运行和失败记录不参与候选）

- 分页值、筛选值、搜索词、分类和照片编号全部使用 SQL 参数；

## Docker 数据持久化

基础 Docker Compose 把宿主仓库 `data/` 整体读写挂载到 `/app/data`，因此默认照片目录 `/app/data/photos`、数据库 `/app/data/photos.db`、输出目录 `/app/data/output` 和两个运行时密钥文件都会随宿主 `data/` 持久化。六个服务的默认权限矩阵如下：

| 服务 | `/app/data` | `/app/logs` | 默认照片目录 | 原因 |
|------|-------------|-------------|--------------|------|
| `inktime-schema` | 读写 | 不挂载 | 包含在 `/app/data` | 为不存在的数据库执行首次迁移，对已有库只读校验 |
| `inktime-server` | 读写 | 读写 | 读写 | 上传、软删除、恢复和回收站清理需要修改照片目录 |
| `inktime-worker` | 读写 | 读写 | 读写 | 后台任务会分析、发布和维护文件 |
| `inktime-analyzer` | 读写 | 读写 | 随 `/app/data` 挂载 | `tools` profile 一次性分析工具 |
| `inktime-render-7c` | 读写 | 读写 | 随 `/app/data` 挂载 | `tools` profile 的 7.3 寸四色渲染工具 |
| `inktime-render-133c` | 读写 | 读写 | 随 `/app/data` 挂载 | `tools` profile 的 13.3 寸六色渲染工具 |

后台修改 `IMAGE_DIR` 只能选择容器已经挂载、存在且可读的目录，不能动态增加卷挂载。使用外部照片库时必须通过 Compose override 为所有消费者逐个显式挂载，并让各容器使用一致的容器内绝对路径；宿主路径不必与容器路径字面相同。Web 服务与后台工作进程需要读写，纯分析或渲染工具可按用途只读。

## 运行时密钥持久化

应用工厂在数据库结构门禁通过后处理两项运行时密钥：`SECRET_KEY` 对应 `.inktime-secret-key`，`DOWNLOAD_KEY` 对应 `.inktime-download-key`，都位于 `DB_PATH` 同目录。显式应用覆盖或环境变量优先；只有最终值为空时才访问持久化文件。

创建过程在 `.inktime-runtime-secrets.lock` 排他锁内完成，临时文件以排他、禁止跟随符号链接的方式创建并请求 `0600` 权限，写入和文件同步后原子替换，再同步父目录。多个 Web 进程因此读取相同值。已有文件必须是普通文件、不得向组或其他用户开放权限、不得超过 4096 字节，内容必须是有效 UTF-8、至少 24 个字符且不含空白；不满足时拒绝启动，不会静默覆盖或重新生成。

这三个隐藏文件与数据库一起备份和恢复。删除任一密钥文件会在下次启动生成新值：删除会话密钥会使既有登录会话失效，删除下载密钥会改变设备地址。临时显式覆盖后再移除覆盖，会重新使用原持久化值。

## 数据库迁移、门禁与连接策略

数据库结构由 `sql/migrations/` 和 `src/migrations.py` 维护，执行记录写入 `schema_migrations`。所有连接经 `src/database.py` 创建：可写连接启用预写日志，所有连接启用外键检查、`busy_timeout=5000` 和 `sqlite3.Row`。数据库不能放在服务器消息块或网络文件系统共享目录上。

直接运行 Web 服务、后台工作进程或 systemd 单元时不会自动迁移；容器镜像入口默认也只会为完全不存在的数据库自动建库。默认严格模式下任何已有数据库都不会在普通启动时补迁移，升级必须使用以下显式命令：

```bash
./venv/bin/python scripts/database_admin.py migrate --database /absolute/path/to/target.db
```

### 容器启动期自动升级开关

容器入口支持显式开启 `AUTO_MIGRATE_ON_START`，把「已有数据库仅落后若干版本」这一种情形改为自动补齐，其余判定一律不变。开关默认关闭，systemd 与直接运行的入口完全不受影响。

开启后 `src/container_entrypoint.py` 在初始化锁内改调 `upgrade_database_if_outdated()`，顺序固定为：只读探测缺失版本 → 强制备份 → 应用迁移 → 结构断言。三个环节的职责划分是：

| 函数 | 位置 | 职责 |
|------|------|------|
| `pending_migration_versions()` | `src/migrations.py` | 只读返回缺失版本；发现未知版本或名称、校验值分叉立即拒绝，不写库 |
| `upgrade_database_if_outdated()` | `src/migrations.py` | 文件校验与补齐流程，通过 `before_migrate` 回调把备份动作交给调用方注入 |
| `create_backup()` | `src/database_backup.py` | 生成一致性备份与身份基线，命令行 `backup` 子命令与自动升级共用同一实现 |

开关的能力边界必须写清，避免被当成通用修复手段：

- 只处理历史干净、仅落后若干版本的数据库；已是最新时不备份也不写库，因此重启不会堆积备份文件。
- 未知版本、分叉历史、零字节文件、非普通文件与损坏数据库仍然一律拒绝启动，与关闭时行为一致。
- 备份失败即中止升级，数据库保持原样并让容器启动失败，不存在无备份的自动迁移。
- 全新数据库不产生备份，直接一次迁移到目标版本。
- 它只保证结构到位，不校验数据内容；数据未被改动仍要靠 `verify --baseline` 的 `identity_mismatches`。
- 它使回滚变重：自动升级后回退旧镜像必须同时恢复对应的数据库备份，否则旧程序会因未知版本拒绝启动。

备份落地目录由 `DB_BACKUP_DIR` 决定，留空时为数据库同级 `backups/`，必须位于持久化挂载内。基础 Compose 已在 `inktime-schema`、`inktime-server`、`inktime-worker` 三个服务同时插值该开关；`inktime-schema` 最先执行门禁，只给后两个服务配置不会生效。

`check-schema` 是只读结构门禁，内部调用 `assert_current_schema()`，不写数据库：

```bash
./venv/bin/python scripts/database_admin.py check-schema --database /absolute/path/to/target.db
```

成功 JSON 的关键字段是 `schema_target=50`、`migration_count`、`max_migration` 和 `schema_current`。严格 `verify` 不只调用结构断言，还要求迁移版本恰好连续为 1 至 50，并检查 `integrity_check`、`quick_check`、`foreign_key_check`、`foreign_keys=1`、`busy_timeout=5000`、`date_source`、`admin_users`、`admin_login_failures` 复合主键与过期索引、`photo_lifecycle_operations`、`photo_purge_operations` 字段及照片编号单列唯一约束，以及照片数量、编号范围、去重编号数、去重路径数和 `id + path` 摘要六项身份基线。

首管理员的用户名与 Werkzeug 密码哈希写入 `admin_users`，初始化令牌不入库。未配置 `INITIAL_SETUP_TOKEN` 或令牌文件时，可信局域网内首位访问者可通过 `/admin/setup` 创建管理员；配置任一来源后仍严格校验令牌。`AdminUserRepository.create_first_admin()` 使用独立立即写事务，在同一事务中检查全表为空并插入；已有任意管理员时抛出 `FirstAdminAlreadyCreatedError`，即使并发请求使用不同用户名也只能有一个成功。

## 备份、恢复与当前验证基线

`backup` 使用 SQLite backup API 创建活动库的一致性副本和身份基线；备份目标随后切换为独立的 DELETE 日志模式，禁止用简单 `cp` 复制启用预写日志的活动数据库。实现位于 `src/database_backup.py` 的 `collect_baseline()` 与 `create_backup()`，命令行子命令与容器自动升级共用同一份代码，两条路径产生的备份格式、完整性校验与基线口径完全一致：

```bash
./venv/bin/python scripts/database_admin.py backup \
  --database data/photos.db \
  --output-dir data/backups
```

恢复前先停止 Web 服务、后台工作进程、分析和渲染写入；恢复后运行严格验证：

```bash
./venv/bin/python scripts/database_admin.py verify \
  --database /absolute/path/to/restored.db \
  --baseline /absolute/path/to/photos-YYYYMMDD-HHMMSS.baseline.json
```

截至 2026-08-16，正式 `data/photos.db` 已在一致性备份副本完成迁移演练后显式迁移到 0050，严格 `verify` 与 `check-schema` 记录目标版本、迁移数量和最大迁移版本均为 50。旧版本在 2026-08-18 使用隔离命名卷验证过新库首次迁移 50、重启后不重复迁移以及移除初始化令牌后同卷重建；该历史结果不覆盖当前家庭局域网零配置改动，也不代表 Docker Compose 六服务或正式数据库升级已重新验证。
