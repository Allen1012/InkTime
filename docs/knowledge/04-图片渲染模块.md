# 04 - 图片渲染模块

## 概述

图片渲染模块负责从数据库中选出「历史上的今天」照片，渲染为墨水屏可直接显示的格式。

**核心文件**：
- `src/render/render_daily_photo.py` — 7.3 寸四色（480×800，1 字节/像素）
- `src/render/render_daily_photo_133c.py` — 13.3 寸六色（1200×1600，4bpp 打包，左右双芯片）

## 选片算法

### 候选池的前置过滤（重要）

进入选片逻辑前，`load_sim_rows()` 直接读取规范字段 `exif_datetime`，SQL 侧执行三道硬过滤
（两套渲染脚本一致）：

1. `is_included = 1`：只选「已收录」的照片。未收录（含默认 `NEW_PHOTO_CURATION=excluded`
   的新照片）不进候选池，即使评分很高也不会被选中；
2. `is_deleted = 0`：排除已软删除（回收站）的照片；
3. `analysis_status IN ('legacy', 'succeeded')`：仅允许历史兼容状态 `legacy` 和分析成功状态
   `succeeded`，`pending`、`running`、`failed` 不参与渲染。

Python 侧还会额外排除路径含 `screenshot` 的照片。`exif_datetime` 为空的照片**仍进候选池**
（既然被收录就是想展示），只是 `md` 留空、不参与「历史上的今天」的月日匹配，但可被全局补足与
兜底选中，画布上日期渲染为空串。分析模块会通过 EXIF、XMP、文件名和文件修改时间尽量补齐该字段；
后台人工编辑日期时也会同步更新 `exif_datetime`（来源记为 `manual`），无需依赖 JSON 缓存。

> 选片全程**不调用任何模型**，纯 SQL + 算法。用途路由里的 `PANEL_PROVIDER` 只影响 web 展示页
> 信息面板的「历史上的今天」AI 筛选（`src/server/panel.py`，见 05 文档），与墨水屏渲染选片无关。

### 核心逻辑：「历史上的今天」

实际每日渲染调用 `choose_photos_for_today(items, today, count=DAILY_PHOTO_QUANTITY)`
（脚本内另有单张版 `choose_photo_for_today`，当前主流程不用）：

```
1. 取今天的月日（如 12-02）作为目标 md
2. 把候选池按 md 分组，组内按 memory_score 降序
3. 从目标 md 组内取 memory_score > MEMORY_THRESHOLD 的候选：
   - 候选 ≥ count：random.sample 随机取 count 张
   - 候选 < count：先用「同一天剩余照片」补齐（这一步不再卡阈值），
     再按 FILL_FROM_GLOBAL 从全局补足
4. 目标 md 无任何 > 阈值候选时：按 day-of-year 往前回溯一天（12-01, 11-30 …），最多 365 天
5. 365 天都没有 > 阈值候选：兜底取全局 memory_score 最高的 count 张
```

回溯用 day-of-year 计算，基于非闰年（`days_before` 表 + `dt.date(2001,...)`），因此 2 月 29 日
不单独处理。

### 全局补足（FILL_FROM_GLOBAL）

命中当天且已用同一天照片补齐后仍不足 `DAILY_PHOTO_QUANTITY` 时，原逻辑只从同一天补，
凑不满就少出几张 bin，ESP32 随机取 `photo_{0..4}.bin` 会读到旧文件。

`FILL_FROM_GLOBAL=True`（默认）时改为从全局按 `memory_score` 降序补足到目标数量。
两套脚本此处有一处细微差异：

- `render_daily_photo.py`（7.3 寸四色）：全局补足**不再二次校验阈值**，只按分数降序、排除已选路径补齐；
- `render_daily_photo_133c.py`（13.3 寸六色）：全局补足时**额外要求** `memory > MEMORY_THRESHOLD`，
  低于阈值的不补，因此满足阈值的照片不足时允许少于目标数量，不为凑数降低质量门槛。

`info` 字典会打印 `day_offset`（回溯天数）、`fallback_global_max`（是否用了全局兜底）、
`filled_from_global`（全局补足了几张），据此判断：

- `fallback_global_max` 经常为 `True` → `MEMORY_THRESHOLD` 该调低
- `filled_from_global` 经常不为 0 → 相册在该日期附近照片太少


### 日期匹配方式

- 从 `exif_datetime` 字段读取拍摄日期（YYYY-MM-DD 或 EXIF 冒号格式）
- 提取月日部分（MM-DD）进行匹配
- 使用 day-of-year 进行回溯计算（基于非闰年 365 天）

### 配置项

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| MEMORY_THRESHOLD | 70.0 | 选片最低回忆度阈值（`memory_score >` 严格大于） |
| DAILY_PHOTO_QUANTITY | 5 | 每日选片数量，对应 `photo_0..{n-1}` |
| FILL_FROM_GLOBAL | True | 当天照片不足时是否从全局高分补足到目标数量 |
| FONT_PATH | 空 | 中文字体 TTF/TTC；留空或加载失败会静默退回豆腐块字体 |
| DB_PATH | photo_scores.db | 只读打开的数据库路径 |
| BIN_OUTPUT_DIR | output/inktime | 渲染产物输出目录 |

这些值在命令行运行时来自环境变量；后台任务运行时由 `render` 作用域快照在锁内临时覆盖，
`FONT_PATH` / `MEMORY_THRESHOLD` / `DAILY_PHOTO_QUANTITY` / `FILL_FROM_GLOBAL` 从快照读取，
`finally` 中恢复旧模块全局值（见「阶段 7 渲染任务配置快照」）。

## 阶段 6 来源清单与原子发布

两套 `load_sim_rows()` 在原有生命周期过滤之外同时选择 `photo_scores.id`，每个候选项都包含
`photo_id`。`main(output_directory=None, database_path=None, today=None)` 支持维护工作进程显式传入
临时输出目录和临时数据库，同时保留无参数命令行行为；返回值包含产物名称、选中照片编号和
逐产物照片编号 manifest，不改变「历史上的今天」、阈值、回溯或全局补足算法。

软删除或恢复会在照片写事务内递增 `display_artifact_state.desired_generation`、设置 `blocked=1`，并让唯一活跃 `render_display` 任务承接最新目标代次。`generation` 表示已经成功发布的代次；设备下载和 `/files/` 只有在 `generation == desired_generation` 且 `blocked=0` 时开放。等待任务可直接提升目标代次；运行任务保留认领时的内存代次，数据库载荷则记录最新后继目标。

维护工作进程在正式 `BIN_OUTPUT_DIR` 内建立同文件系统临时目录，先完整执行四色与六色渲染并验证产物，临时生成阶段不会触碰正式文件。正式发布必须进入维护任务仓储的写事务双栅栏：租约仍属于当前工作进程且未过期，同时任务认领时的 `render_generation` 必须等于当前 `desired_generation`。如果生命周期变化使业务代次落后，发布回调不会执行，任务会原子退回 `pending`、返还本次尝试次数，并在下次认领时按最新数据库状态重新渲染。SQLite 的 `BEGIN IMMEDIATE` 写锁保证生命周期事务和发布事务具有确定顺序。

双栅栏通过后才逐个使用 `os.replace` 发布到固定兼容文件名，并删除不在新 manifest 中的旧高编号受管产物；随后把 `generation` 赋值为任务目标代次、保存 manifest、把任务置为成功并解除屏蔽。续租返回失败或抛出异常会设置失租事件；渲染、发布、旧产物清理或数据库提交失败时继续屏蔽设备下载和 `/files/`。固定文件名仍采用逐文件原子替换，不承诺进程在多文件发布中途崩溃时实现整批文件系统事务。

## 阶段 7 渲染任务配置快照

`render_display` 在首次认领维护任务的同一事务中固化 `render` 作用域快照。工作进程把同一个快照对象依次传给四色和六色渲染入口，因此管理员后续调整阈值、数量、字体或全局补位开关不会改变已认领任务。租约恢复与自动重试沿用原快照，人工重试重新固化；损坏快照在创建临时产物前稳定失败为 `invalid_config_snapshot`。

两套渲染入口使用各自模块级重入锁临时覆盖旧模块全局配置，并在 `finally` 中完整恢复。工作进程显式传入的临时输出目录和数据库路径优先于历史快照，避免任务重试时写入旧目录或错误数据库。

## 渲染流程

### 画布布局（480×800 竖屏）

```
┌────────────────────────┐ ← 0
│                        │
│                        │
│      照片区域           │  高度 = 800 - 100 = 700px
│   （铺满裁剪）          │
│                        │
│                        │
├────────────────────────┤ ← 700
│  文案（最多两行）        │
│  日期          地点     │  高度 = 100px（TEXT_AREA_HEIGHT）
└────────────────────────┘ ← 800
```

### 照片处理

1. 加载原图 → EXIF 方向纠正 → 转 RGB
2. 铺满裁剪（Cover Crop）：缩放到至少覆盖区域，从中心裁剪
3. 贴到画布上方区域

### 文字渲染

- 字体：`FONT_PATH` 指定的 TTF/TTC 文件。**加载失败会静默退回 `ImageFont.load_default()`，
  该字体不含中文字形，文案会渲染成豆腐块且不报任何错误**。`FONT_PATH` 留空时
  `Path("")` 会变成 `Path(".")`，同样触发这个退回，所以必须显式配置。
  Ubuntu 上可用 `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`

- 文案：22px，最多两行，中文按字符宽度折行
- 日期：20px，格式 "YYYY.M.D"（去掉前导零）
- 地点：20px，右对齐；优先显示城市名，无城市则显示经纬度

## 四色抖动算法

### 调色板

| 索引 | 颜色 | RGB 值 |
|------|------|--------|
| 0 | 黑 | (0, 0, 0) |
| 1 | 白 | (255, 255, 255) |
| 2 | 红 | (200, 0, 0) |
| 3 | 黄 | (220, 180, 0) |

### Floyd-Steinberg 抖动

对每个像素：
1. 加上累积误差
2. 找到最近的调色板颜色（欧氏距离）
3. 计算误差 = 原始值 - 量化值
4. 将误差扩散到相邻像素：
   - 右方：7/16
   - 左下：3/16
   - 正下：5/16
   - 右下：1/16

## 输出格式

### BIN 文件

- 大小：480 × 800 = 384,000 字节
- 编码：1 字节/像素，值为调色板索引（0-3）
- 排列：行优先，从上到下、从左到右

### H 头文件

```c
// Auto-generated from render_daily_photo.py
// Size = 384000 bytes (480x800, 1 byte/pixel)

const unsigned int daily_bin_0_size = 384000;
const uint8_t daily_bin_0[] = {
    0x01, 0x01, 0x01, ...
};
```

### 输出文件列表

| 文件 | 说明 |
|------|------|
| `photo_0.bin` ~ `photo_4.bin` | 每日渲染的多张照片 |
| `photo_0.h` ~ `photo_4.h` | 对应的 C 头文件数组 |
| `preview_0.png` ~ `preview_4.png` | 抖动后的预览图 |
| `latest.bin` | photo_0.bin 的副本（兼容旧流程） |
| `latest.h` | photo_0.h 的副本 |
| `preview.png` | preview_0.png 的副本 |

## 13.3 寸六色版本（render_daily_photo_133c.py）

选片算法（`load_sim_rows` / `choose_photos_for_today`）与 7.3 寸一致，仅全局补足处多一道阈值
校验（见上文）。差异集中在画布、调色板与输出打包：

### 画布与布局

- 分辨率：`CANVAS_WIDTH=1200`、`CANVAS_HEIGHT=1600`，`TEXT_AREA_HEIGHT=200`（1600×0.125）
- 布局与 7.3 寸同构，只是把内边距、字号、行高按比例放大：`padding_x=60`（24×2.5），
  文案字号 44（22×2）、日期/地点字号 40（20×2）、行高 48（24×2），第二行 y 偏移 108（54×2）
- 照片处理同为「铺满裁剪 + EXIF 方向纠正」；文案两行折行、日期 `YYYY.M.D`、地点右对齐规则不变

### 六色调色板与抖动

| 索引 | 颜色 | RGB |
|------|------|-----|
| 0 | 黑 | (0, 0, 0) |
| 1 | 白 | (255, 255, 255) |
| 2 | 黄 | (255, 255, 0) |
| 3 | 红 | (255, 0, 0) |
| 5 | 蓝 | (0, 0, 255) |
| 6 | 绿 | (0, 255, 0) |

注意六色索引是 `[0,1,2,3,5,6]`（跳过 4），与面板 E6 芯片约定一致。抖动同样是 Floyd-Steinberg，
误差扩散系数与四色版相同（右 7/16、左下 3/16、正下 5/16、右下 1/16）。

### 4bpp 打包与双芯片输出

屏幕由左右两颗芯片驱动，量化后按 4bpp 打包（每字节两个像素，低半字节为前一个像素），
`pack2_ino(p0, p1) = (p0 & 0x0F) | ((p1 & 0x0F) << 4)`，行优先。每张照片产出三份 bin：

- `_L.bin`：左半屏（x 0–599），600×1600÷2 = 480000 字节
- `_R.bin`：右半屏（x 600–1199），480000 字节
- `_FULL.bin`：整帧（1200×1600÷2 = 960000 字节），可选整帧调试用

ESP32 固件按行流式下载 `_L.bin` 与 `_R.bin` 直接喂芯片，不落盘，不使用 `_FULL.bin`。

### 输出目录与文件

脚本维护两个目录：独立源目录 `output/inktime_13in3_6c/`（`BIN_OUTPUT_DIR_13`）与服务器静态目录
`SERVER_STATIC_DIR`（默认复用 7.3 寸的 `BIN_OUTPUT_DIR`），产物同时写入两处。

| 文件 | 说明 |
|------|------|
| `photo_13in3_6c_{idx}_L.bin` / `_R.bin` / `_FULL.bin` | 每日多张的左半 / 右半 / 整帧 |
| `preview_13in3_6c_{idx}.png` | 抖动后预览图（六色） |
| `latest_13in3_6c_L.bin` / `_R.bin` / `_FULL.bin` | idx=0 的兼容副本 |
| `preview_13in3_6c.png` | preview_13in3_6c_0.png 的兼容副本 |

`main()` 返回 `artifacts` 列表和含 `photo_ids` / `artifact_photo_ids` 的 manifest，
供阶段 6 维护任务追踪来源并做原子发布（见「阶段 6 来源清单与原子发布」）。六色版无 `.h` 头文件。
