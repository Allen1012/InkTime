# 03 - 照片分析模块

## 概述

照片分析模块是 InkTime 的数据生产核心，负责将原始照片转化为结构化的元数据。

**核心文件**：
- `src/analysis/photo_analyzer.py` — 批量脚本与 worker 共用的单张分析、EXIF、城市、评分与旁白编排
- `src/exif_metadata.py` — 上传与分析共用的 EXIF 字段提取（含 GPS 子 IFD 解析）
- `src/provider_options.py` — 厂商特有请求参数的解析与合并，analysis 与 server 共用
- `src/analysis/analyze_photos_docker.py` — 批量扫描兼容入口（纯环境变量 + `.env`）
- `src/analysis/run_worker.py` — 持久化后台任务 worker 入口
- `old/analyze_photos.py` — 已废弃的旧版（依赖 `config/config.py`），仅作历史参考，不参与运行

> 两份脚本原本功能高度重叠，容易改错文件（尤其调 prompt 时）。现已统一到 env 版，
> 改 prompt 请改 `analyze_photos_docker.py`。


## 处理流程

```
1. 扫描 IMAGE_DIR 下所有图片（递归，支持 jpg/jpeg/png/bmp/webp）
2. 过滤截图（路径含 "screenshot" 的文件）
3. 对磁盘缺失记录标记 `analysis_status=failed` 和 `analysis_error=source_file_missing`，保留数据库行
4. 筛选尚未成功、等待重试的活动照片（`pending`、`running`、`failed`）
5. 对每张照片：
   a. 计算文件 SHA-256，写入 `running` 状态、原始文件名和更新时间
   b. 读取图片 → EXIF 方向纠正 → 缩放长边到 VLM_MAX_LONG_EDGE → JPEG 编码 → Base64（整轮只做一次，评分与文案共用）
   c. 调用 VLM 获取：caption, type, memory_score, beauty_score, reason
   d. 提取 EXIF：datetime, make, model, iso, exposure, f_number, focal_length, GPS
   e. 日期三级兜底：EXIF → XMP(含 PS 编辑时间) → 文件名（原始上传名优先，其次磁盘名），全部失败则留空；结果写入 date_source
   f. GPS 逆地理编码：经纬度 → 中文城市名（本地 CSV 查询）
   g. 异地加分：GPS 不在 HOME 范围内 → memory_score += 5
   h. 调用 VLM 生成一句话文案（side_caption）
   i. 成功写入 `succeeded` 并清除错误；模型失败写入 `failed`，两种结果都递增版本
```

## 分析的前置条件：人工收录

后台照片分析**不由目录扫描自动触发**。闸门的目的是成本控制：一个几百张的照片目录如果自动全量分析，会连续数小时调用模型并按量计费。

具体由哪个动作触发分析，取决于配置项 `NEW_PHOTO_CURATION`（新照片默认收录状态，后台「配置管理 → 模型与分析 → 新照片入库与分析闸门」可在线修改，热生效）：

| 取值 | 扫描登记为 | 分析由什么触发 | 适用场景 |
|---|---|---|---|
| `excluded`（默认，默认未收录） | `is_included=0` | 把照片**改为已收录**这个动作本身，自动排队分析 | 照片挑得细，逐张或小批筛选 |
| `included`（默认已收录） | `is_included=1` | 照片管理页的**按张数放行** | 照片基本都要，按批次控制花钱节奏 |

两种取值绑在同一个开关上是有意的。拆成「默认收录」和「收录即分析」两个独立开关，就能配出「扫描进来的每张照片都自动调用模型」这种没有任何闸门的组合，而那正是这套机制要防的事情。因此**扫描在两种取值下都不排队分析**，只是闸门位置不同。

「改为已收录即分析」的三条纪律：

- **只在真正跃迁时触发**：判定依据是数据库里「原值 0 → 新值 1」，不是「本次提交的值是已收录」。照片详情页每次保存都会提交收录字段，按提交值判断会让一张已收录且已分析成功的照片，每改一次分类就重跑一次付费分析。实现见 `AdminPhotoManagementService._curation_transition()`。
- **只对还需要分析的照片触发**：`analysis_status` 必须是 `pending` 或 `failed`，与按张数放行的口径逐字一致（`AdminPhotoManagementService.ENQUEUEABLE_ANALYSIS_STATUSES` 对应 `AdminJobRepository._RELEASABLE_CONDITION`）。`succeeded` 无需重跑，`running` 已在队列，`legacy` 是历史已有结果、要重跑得走显式的重新分析入口。两处只要有一处漏改，就会出现「按张数放行不选它、改成已收录却给它排队」这种自相矛盾的付费行为。
- **批量逐张判定**：批量修改一次最多 100 张，整批共用一个 `changes`，但跃迁必须按每张照片自己的原值判断。按整批判断会把「本来就已收录」和「已分析成功」的照片也算成新收录，凭空多花近百次模型调用。

反向动作同样有联动：把照片**改回未收录**会立刻撤销它尚未完成的分析任务（`AdminJobRepository.cancel_active_analysis()`），不受模式约束——两种模式下都该立刻停止花钱。`pending` 任务直接置为 `canceled`、照片记 `analysis_error='curation_excluded'`；`running` 任务只设协作取消标记，由工作进程自行收口。

这里不能复用按任务版本收口的 `cancel(job_id, ...)`：改收录本身就会推进照片版本，而 `cancel` 用的是任务持有的旧 `photo_version`，必然撞版本冲突。`cancel_active_analysis` 改为按照片当前版本收口，做法与租约恢复的 `_coordinate_recovered_analysis` 一致。

**上传是例外，不读这个配置**：后台上传一律登记为已收录并立即排队分析。上传本身就是一次逐张的人工动作，它自己就是收录决定，不需要第二道闸门。改动前上传登记为未收录却在同一事务里建了分析任务，结果是「钱花了、照片不展示」，还得再手动收录一次。

排查「照片一直不分析」时，按顺序确认：照片是否已收录、是否已入队（后台任务页有没有它的 `analyze_photo` 任务）、照片分析工作进程是否在运行。三者缺一，照片都会停在「等待分析」且没有任何错误信息——这是最容易被误判成程序卡死的场景。

### 排队为什么不在照片写事务里

`update_photo()` 与 `batch_update()` **只在返回值里报告跃迁方向**，不自己排队：前者返回 `curation_transition`，后者返回 `curation_activated` 与 `curation_deactivated` 两个编号列表。排队与撤销各自要开写事务，在照片写事务内再开一个 SQLite 写连接会互相锁死。真正的排队由路由层的 `_apply_curation_side_effects()` 在事务提交之后完成。

代价是提交与排队之间存在空隙：进程在这两步之间崩掉，照片会停在已收录但没排队的状态。正规解法是事务性发件箱，对这个项目偏重；这里的收敛手段是保留按张数放行作为兜底——它本身就是一个调和器（比对「已收录且未分析」与「有没有活跃任务」，把差异补平），手点一次状态就补齐了。`enqueue_curated()` 在排队前还会用同一套条件复核一遍，防止空隙期间照片又被改回未收录或已被隐藏。

## 后台任务配置快照

后台 `analyze_photo` 与 `generate_narration` 任务首次认领时，在认领事务中保存 `analysis` 作用域的配置版本和完整非敏感 `settings` 快照。后续即使管理员修改模型地址、模型名称、超时、图像尺寸或地理参数，已认领任务仍按原快照执行；租约恢复与自动重试不更换快照；人工重试会重新固化，因此改完模型点重试即生效。

阶段三把顶层 `provider` 从阶段二的单厂商对象扩展为完整有序候选数组。`analyze_photo` 可同时固化 `analysis` 与 `narration` 两条候选链，`generate_narration` 只固化 `narration`；每个档案仍只含编号、名称、版本、基础地址、模型名、超时和图片最长边。解析器双读两种格式：阶段二单对象会规范为长度一的候选链，阶段三数组逐项严格校验；阶段二之前的两字段快照继续合法。`ANALYSIS_PROVIDER`、`NARRATION_PROVIDER` 本身不进入 `settings`，路由切换只影响之后首次认领的任务，已经认领及其自动重试继续使用原候选顺序和公开参数。

**一个厂商可以配多个可选模型，但同一时刻只有「当前启用模型」会被调用。** 多模型是给人手动切换用的备选清单，不是自动降级候选，也不轮换：各模型的授权额度不同，自动轮着调用会让额度以不可预期的方式被消耗掉，因此换模型必须是管理员的显式动作。`resolve_chain()` 里每个厂商只产出一个候选，其 `model_name` 被改写为该档案的 `active_model`，所以任务快照每项仍是单模型、字段集合不变，阶段三之前固化的历史快照继续可读。厂商之间的降级链不受影响，仍按分号顺序遍历。切换启用模型只影响之后首次认领的任务，已认领任务及其自动重试沿用快照里的模型。

**厂商档案是模型配置的唯一来源，没有任何兜底。** `API_URL`、`MODEL_NAME`、`TIMEOUT`、`VLM_MAX_LONG_EDGE`、`API_KEY` 这五个注册表键已移除：两套并行的配置来源正是「改了配置却没生效」的根源，而静默回退更糟——路由填错或档案被删时分析照样「成功」，只是悄悄换了一套配置，等发现时已经烧了一批额度。现在没有可用厂商时抛 `NoModelProviderError`，错误信息直接指向建档与配路由两步。

两处兼容性由 `configuration.RETIRED_SNAPSHOT_KEYS` 承担，都必须守住：

| 场景 | 处理 | 不处理的后果 |
|---|---|---|
| 历史任务快照的 `settings` 里含这五个键 | 放行并丢弃 | 快照原先是精确相等校验，删键会让队列里所有已认领任务判 `invalid_config_snapshot`，一次配置清理打死全部在飞任务 |
| 数据库 `settings_json` 里留着旧值 | 读取时忽略 | `_validated_state` 原先对不在注册表的键判「数据库包含未知配置」并抛错，曾在后台改过模型配置的部署升级后**配置服务根本起不来** |

第二条是真实环境踩出来的：测试库是干净的，全套测试通过也发现不了。

路由优先级是：照片评分读取 `ANALYSIS_PROVIDER`，旁白读取 `NARRATION_PROVIDER`，旁白路由留空时跟随分析路由；两者都没有可用档案时直接失败。评分链与旁白链分别单向遍历，每个候选在一次任务尝试内最多调用一次。只有连接失败、超时、HTTP 429 和 HTTP 5xx 才转向下一候选；其他 HTTP 4xx、响应 JSON 错误、字段缺失和模型正文解析错误立即停止候选链，避免重复付费并掩盖配置问题。同一候选在一次尝试内只发一个请求，不存在「换一种客户端再试一次」的重发路径。

评分成功后才进入旁白链，因此旁白主厂商发生网络类故障时不会重跑已经成功的评分。同一厂商且图片最长边一致时复用已编码图片；切换到不同厂商或不同最长边时按候选快照重新编码。链内降级不调用 `fail_attempt()`，不增加后台任务尝试次数；整条链耗尽后才按一次任务失败进入既有自动重试。跨后台自动重试仍会重新评分，阶段三没有引入中间结果检查点。

每次实际切换候选时，工作进程用短事务写入 `admin_job_events`：`event_type=provider_fallback`，状态保持 `running → running`，`reason_code` 只保存用途与稳定原因，例如 `narration:timeout`。事务会复核任务仍在运行且租约属于当前工作进程。厂商起止名称只进入带 `job_id`、`photo_id`、用途和原因的警告日志，事件与日志都不保存响应正文或密钥。

`src.analysis.run_worker` 在执行前严格校验快照结构、版本、配置键集合、`provider` 用途、候选数组、公开字段白名单、类型和范围。损坏快照不会调用模型，而是按稳定错误码 `invalid_config_snapshot` 进入既有失败或重试流程。升级前已经启动且保持版本 0、空 JSON 的历史任务、阶段二之前的两字段快照以及阶段二单对象厂商快照，都会按原兼容语义执行。`API_KEY` 和厂商 `api_key` 都不进入快照；工作进程在每次调用前按快照里的厂商名称调用 `ModelProviderService.api_key_for()` 现读密钥，无厂商快照时才读取旧 `API_KEY`。

## 后台任务取消与照片删除

普通管理员取消运行任务仍采用协作取消：先设置 `cancel_requested=1`，工作进程在安全边界把任务终结为 `canceled`。若期间照片已被编辑或版本已推进，旧任务只关闭自身，不再更新照片，避免覆盖较新的状态。取消或过期任务不能继续续租；租约恢复发现取消请求时优先闭合为 `canceled`，不会进入普通失败或自动重试。

无取消请求的照片分析任务租约过期时，恢复事务会读取未删除照片的当前版本；旁白、摘要或管理员编辑可以合法推进全局照片版本，因此不沿用任务认领时的旧版本。只有照片分析状态仍为 `running` 时，才按当前版本将照片和任务同步收口为 `pending`，或在尝试次数耗尽时同步收口为 `failed/max_attempts_exceeded`。若照片不存在、已删除、分析状态已改变或条件更新失败，照片保持不变，任务以完整的 `failed/photo_version_conflict` 终态关闭并补齐结束时间，避免覆盖已经明确改变的分析状态。同一照片、同一任务类型的活跃任务唯一约束保证当前版本协调仍对应唯一分析任务。

主动让出只允许可中断的 `backfill_content_hash` 历史最终文件摘要回填任务，并保留退还尝试次数、清空租约和返回 `pending` 的语义。`analyze_photo` 照片分析任务与 `generate_narration` 旁白生成任务不会进入 `defer`，防止任务回到 `pending` 而照片状态仍停留在 `running`。

照片软删除采用更强的事务语义。在软删除的同一个 `BEGIN IMMEDIATE` 事务内，所有 `pending/running` 照片任务立即进入 `canceled`，租约和提交权被清除，写入 `finished_at` 及 `photo_deleted` 事件；若照片分析状态为 `pending/running`，同一次照片版本递增会把它收口为 `failed/job_canceled`。已经发出的视觉语言模型请求无法被强杀，可能继续消耗资源，但晚到结果会先被任务终态拦截，并继续受旧 `photo_version` 约束，不能覆盖已删除或恢复后重新排队的新版本照片。

## 照片详情页待确认结果

照片详情页发起的完整分析和旁白生成继续复用 `analyze_photo`、`generate_narration` 任务类型，但载荷必须同时包含 `source=admin_photo_detail`、`result_mode=draft`、`schema_version=1`。这一严格标记把待确认任务与正式任务隔离：排队、认领、失败、取消、人工重试和租约恢复只改变 `admin_jobs`，不会推进 `photo_scores.version`，也不会修改分析状态、描述、旁白或评分。同一照片同时最多保留一个活跃待确认任务；正式任务与待确认任务双向互斥，避免版本推进或两类结果互相遮蔽。

工作进程成功后只把白名单结果写入 `admin_jobs.result_json`：完整分析允许分类、描述、旁白、回忆分、美观分、评分理由和成功状态；旁白任务只允许 `side_caption`。页面通过当前照片版本查询最新草稿，把成功结果填入编辑表单；只有管理员确认并保存后，`AdminPhotoManagementService` 才按照片版本乐观锁写入正式字段。既有 `/api/admin/photos/<id>/reanalyze` 和 `/api/admin/photos/<id>/regenerate-narration` 正式接口不变，仍直接执行正式任务语义。

## 思考型模型的 token 预算与结构化输出

当前默认模型 `xiaomi/mimo-v2.5` 是混合推理模型：**思考过程走独立的 `reasoning_content` 字段，`content` 里是干净的正文**。实测一次纯文本旁白请求消耗 292 个 token，其中 277 是思考、正文只占 15 个。

**思考关不掉。** 推理网关的接口文档里 `reasoning_effort` 标注为「暂不支持」，`mify_extra` 只有内容审核与加密两个字段，整张参数表没有任何 `enable_thinking` 之类的开关。所以只能给思考留够预算，不能指望关掉它。

**两次踩坑都出在 `max_tokens` 上**，值得记下来：

| 上限 | 后果 |
|---|---|
| 64 | 思考阶段就耗尽配额，`content` 返回空，旁白整条丢失 |
| 512 | 纯文本够用，但带图片时思考更长，JSON 被截断成 `'{'` 这种残片 |
| 2048 | 旁白与评分都取这个值。正文本身很短，上限提高不会让它变长，只是给思考留够 |

从 qwen 系列换到 mimo 系列时只改了模型名，没意识到 token 预算的含义变了——`qwen3.5-plus` 非流式下不产生思考 token，64 个全给正文够写一句 20 字旁白；mimo 连思考都不够。**换模型必须重新评估 token 预算。**

**旁白与评分都用 `response_format` 的 `json_schema` 约束输出**（网关支持这个参数）。schema 让模型没地方铺开思考，实测思考 token 从 277 降到 87、总消耗降到三分之一，输出还变成可直接解析的 JSON。评分原先只靠提示词要求「严格只输出 JSON」，靠 `json.loads` 撞运气；现在字段与类型由网关保证。

**解析上有一条硬规则：看起来像 JSON 就必须解析成功、且取到 `caption` 才算有效，否则一律判失败。** 被截断的响应长这样：`'{'` 或 `'{"caption":"半句'`。曾经的实现在解析失败时退化成纯文本，把这些残片当旁白写进了数据库。

**这条路径的失败方式是静默写入垃圾，不是报错**，因此格式容错必须覆盖各家模型的偏离形态，否则上层的空值校验拦不住，只有人眼看到照片墙上那句话才会发现。已知并已覆盖的三种偏离：

| 形态 | 实例 | 处理 |
|---|---|---|
| 对象外再包一层数组 | `[{"caption": "..."}]` | 单元素时取出；多元素判失败（说明没按「只输出一句」执行） |
| JSON 被 Markdown 围栏包裹 | ` ```json\n{"caption": "..."}\n``` ` | 先剥围栏再判断是否 JSON，顺序不能颠倒 |
| 只吐出残缺围栏 | ` ``` ` | 判失败 |

前两种都曾把整段原文当旁白写进库：早先的实现只判断 `content` 是否以 `{` 开头，`[` 与围栏都会漏进纯文本分支。第三种是 `_clean_caption_text()` 只剥引号不剥反引号导致的，现已一并剥掉首尾反引号——正常旁白不会以反引号开头或结尾。

`qwen3.8-max` 在 `json_schema` 下实测就是第一种形态，且 `finish_reason` 为 `stop`（不是截断）。提取逻辑现在两种形态都能处理，因此这个参数的取舍不影响正确性，只影响 token 消耗。

### 厂商特有请求参数

同一个 OpenAI 兼容协议，各家的扩展参数并不通用，因此这类差异按厂商配而不是全局写死：`model_providers.request_options` 存一个 JSON 对象，执行时合并进请求体顶层，**值为 `null` 表示不发送该参数**。需要「删掉」这个语义是因为有的参数只能靠不发送来关闭——OpenAI 兼容层没有「结构化输出=关」这种取值。

千问实测四种组合（同一张照片、同一提示词）：

| 组合 | 思考 token | 正文 token | 总计 | `content` 格式 |
|---|---|---|---|---|
| 基线（无额外参数、无 schema） | 242 | 12 | 2797 | 干净一句话 |
| **`enable_thinking: false`** | **0** | 9 | **2553** | **干净一句话** |
| 关思考 + `json_schema` | 0 | 21 | 2651 | 仍是 `[{...}]` 数组 |
| `chat_template_kwargs` 写法 | 0 | 11 | 2555 | 干净一句话 |

因此千问档案填 `{"enable_thinking": false, "response_format": null}`：关思考省下每次约 240 个思考 token，而关掉思考后正文本身就干净，结构化输出反而多包一层数组。第三行还印证了格式偏离与截断无关，是模型在 schema 下的固有行为。

**这些参数不能全局加。** `enable_thinking` 只有千问认，`mimo` 那个网关的参数表里没有任何思考开关（`reasoning_effort` 标注暂不支持），硬传过去可能直接 400 把分析全打挂。知识库上文记的「schema 让思考从 277 降到 87」是在 `mimo-v2.5` 上测的——**schema 压缩思考的效果是模型相关的，换模型必须重新实测，不能沿用结论。**

实现上：写入路径由服务层严格校验（必须是 JSON 对象、不能是数组或标量、限长），读取路径宽容（非法值按「无额外参数」处理，不让手工改库导致整条链路失效）。该字段随候选一起进任务快照，因此改动只影响之后首次认领的任务；`_temporary_legacy_configuration` 把它覆盖到 `PROVIDER_REQUEST_OPTIONS` 模块全局并在 `finally` 还原——不还原会让一个配了参数的厂商污染同进程后续所有分析，表现为「随机某些照片用错参数」。纯函数放在 `src/provider_options.py` 而不是 `src/server/model_providers.py`，因为批量分析脚本也要用它，而 analysis 侧不应依赖 server 层。

**不要从 `reasoning_content` 里捞内容。** 历史上有一段「正文为空就回退到思考字段末行」的逻辑，建立在「可用文本藏在思考里」这个错误假设上。它没救回任何数据，反而把思考文本的尾巴写成了旁白，例如 `最终我觉得"…"这个不错。它描述了`、`- 风格：可以带点幽默或诗意`。正文取不到就应该判失败并重试——兜底伪装成功比直接失败更难排查。

## VLM 调用详情

### 照片分析 Prompt

系统角色：「个人相册照片评估助手」

输出格式（严格 JSON）：
```json
{
  "caption": "80-200字中文描述",
  "type": "人物/孩子/猫咪/家庭/旅行/风景/美食/宠物/日常/文档/杂物/其他",
```

### 评分规则（memory_score）

| 区间 | 含义 | 典型场景 |
|------|------|---------|
| 0-39 | 低价值 | 账单、广告、杂物、测试图、截图 |
| 58-70 | 稍有回忆价值 | 普通日常记录 |
| 68-82 | 不错的回忆 | 有故事的照片 |
| 79-96 | 特别精彩 | 重要时刻、不可复现的瞬间 |

**加分项**：人物互动、事件性、稀缺性、情绪强度、优美风景、旅行意义
**特殊处理**：孩子/猫咪/宠物题材以 75 分为中心起评
**异地加分**：GPS 距离常驻地超过 HOME_RADIUS_KM → +5 分

系统角色：「电子相框旁白短句文案助手」

创作原则：
- 不描述画面，而是写「看完画面后心里多出来的一句话」
- 避免套路词：世界、梦、时光、岁月、温柔、治愈
- 禁止模板句式
- 8-24 个汉字，最多 30 字
- 风格：日常微妙情绪 / 轻微自嘲 / 含蓄感受 / 平淡有余味

## EXIF 提取

后台上传会在规范化重编码前提取允许保存的拍摄时间、GPS、海拔、相机厂商与型号、感光度、曝光、光圈和焦距，写入新照片记录及分析任务载荷；不保存可交换图像文件格式（EXIF）Orientation。工作进程分析规范化文件后，会用任务载荷中的原始拍摄字段覆盖文件修改时间等弱兜底结果，因此重编码不保留完整 EXIF 也不会丢失拍摄语义。批量扫描入口仍直接读取原文件 EXIF，两条入口继续复用同一个 `photo_analyzer.py` 模型编排，**字段提取也共用 `src/exif_metadata.py` 同一份实现**。

### 提取方式

**上传与分析共用 `src/exif_metadata.py` 一份实现**，各自再把结果映射到自己的输出结构（数据库列名或分析结果键名）。放在 `src/` 顶层而不是任何一侧，是因为批量分析入口不应依赖 server 层。

字段分三处读，缺一处就会静默丢字段：

| 来源 | 标签 | 内容 |
|---|---|---|
| 顶层 IFD | 271 / 272 / 306 | 相机厂商、型号、文件时间 |
| Exif 子 IFD | `get_ifd(34665)` | 拍摄时间、感光度、曝光、光圈、焦距 |
| GPS 子 IFD | `get_ifd(34853)` | 经纬度、海拔及其方向标志 |

每个标签先查子 IFD 再回退顶层，兼容把参数写在顶层的写入器。exiftool 仍作为 GPS 兜底，但它是**可选依赖**，PIL 路径必须能独立读出坐标——不能把正确性押在一个可能没安装的命令行工具上。

**两条必须守住的坑**（都是真实事故）：

1. **GPS 必须走 `get_ifd(34853)`。** 顶层 IFD 里 34853 存的是**指向子 IFD 的偏移量整数**，不是标签字典。早先分析侧写的是 `exif.get("GPSInfo")` 再判断 `isinstance(..., dict)`，在现代 Pillow 上这个判断永远为假，代码静默跳过、坐标变成空值、`exif_city` 跟着算成空串写回数据库，全程不报错。表现是数据库里同一行**既有经纬度、又有空城市**——坐标是上传写的，城市是分析算的。而上传侧当时用的正是 `get_ifd`，这就是两套实现能力不一致的代价。
2. **拍摄参数必须显式读 Exif 子 IFD。** 私有的 `_getexif()` 会把子 IFD 扁平合并，所以旧代码恰好能读到 ISO；换成公开的 `getexif()` 后不读子 IFD，ISO、光圈、快门、焦距会全部静默变空。这一条是统一实现过程中实测发现的回退。

GPS 段单独解析并单独兜底：整段兜底会把已解析成功的拍摄时间与相机字段一起丢掉，等于用「不崩」换掉全部信息。实际事故正是如此——`GPSAltitudeRef` 按标准是 BYTE 类型、值本来就是 `b'\x00'`，一个 `int()` 让每张带 GPS 的照片都丢光元数据。因此 BYTE 字段用字节序数解析（`byte_flag`），不能按文本数字解析。

### GPS 逆地理编码

使用本地 `world_cities_zh.csv` 文件（基于 GeoNames 数据，随代码放在 `resources/`）：
- 网格索引加速查询（CITY_GRID_DEG = 1.0°）
- Haversine 公式计算距离
- 最大搜索距离：CITY_MAX_DISTANCE_KM（默认 100km）
- 返回最近城市的中文名

## 日期兜底（date_source）

没有 EXIF 拍摄时间的照片会被渲染模块的候选池**彻底排除、永远不展示**（见 04 文档）。
为了让这些照片也能出现在墨水屏上，`resolve_datetime()` 按四级兜底补齐日期，
并把来源记录到 `date_source` 字段：

| date_source | 来源 | 语义可信度 |
|---|---|---|
| `exif` | EXIF `DateTimeOriginal` / `DateTime` | 准确，就是拍摄时间 |
| `xmp` | exiftool 读 XMP/IPTC 残留标签（`CreateDate`、`MetadataDate`、`HistoryWhen` 等） | **PS 处理过的图多为「编辑时间」，可能与拍摄季节完全不符** |
| `filename` | **原始上传名**或磁盘名中的 8 位日期、10/13 位 Unix 时间戳（如 `MVIMG_20260620_193658`、`FIMO_1647600645102`） | 一般可信 |
| `manual` | 后台照片详情页手工填写 | 由人确认，视为准确 |
| `none` | 全部失败，`exif_datetime` 留空 | **照常展示**，只是画面上不显示日期，且不参与「历史上的今天」月日匹配 |

**文件名一级必须同时看原始上传名**：上传照片的磁盘名是随机十六进制串（防重名与路径穿越），日期线索只存在于 `original_filename` 里，只看磁盘路径等于白找。

**已移除 `mtime` 兜底**：上传落盘会把文件修改时间刷成上传时刻，拷贝移动也会改写它，把它当拍摄时间会让雪景照显示成八月，且同批导入的照片全挤在同一天。现在取不到就留空并记 `none`。留空**不影响展示**：照片照常进候选池、照常轮播，只是画面上不显示拍摄时间，也无法参与月日匹配，而是通过补足档进入当天画面。历史遗留的 `mtime` 记录可用 `scripts/fix_mtime_dates.py` 按新口径修正（默认只预览，`--apply` 才写库并自动备份）。

要点：

- 兜底结果写入规范字段 `exif_datetime`，同时维护 `exif_json.datetime` 和 `exif_json.date_source` 兼容键；渲染和公开月日清单以规范字段为准
- 非 `exif` 来源会在分析日志里打印「日期兜底：… （来源 xxx）」
- `EXIFTOOL_AVAILABLE` 在模块加载时即检测，不依赖 `require_exiftool()` 的调用顺序
  （否则单独 import 本模块调用 exiftool 相关函数会静默拿不到数据）
- 存量数据不会自动跟上新规则（分析脚本按 `path` 去重会跳过），用
  `scripts/backfill_metadata.py` 回填，该脚本不调用 VLM、不花额度

## 类型规范化

VLM 输出的 `type` 格式不稳定，见过 `风景/旅行` 与 `孩子, 旅行, 风景, 日常` 两种写法。
`server.py` 按 `/` 拆标签，逗号写法会让整串变成一个畸形分类污染分类页。

`normalize_type()` 在写库前把 `，,、|；;` 统一成 `/` 并去重，`server.py` 的
`_split_type_tags()` 再兼容一次兜住历史数据。

## 数据库迁移与连接边界

分析入口先调用 `src.migrations.migrate_database()`，结构变更按 `sql/migrations/`
顺序执行并写入 `schema_migrations`。`ensure_table()` 断言基础主键、日期来源以及阶段 4 的
原始文件名、内容摘要、分析状态、软删除、时间戳和版本字段，不再静默执行 `ALTER TABLE`。
元数据预览也不会改表。

所有连接由 `src.database` 创建，统一启用 WAL、外键检查、5 秒忙等待和
`sqlite3.Row`。照片扫描、视觉语言模型请求和图片处理位于事务外；状态转换和单张
UPSERT 使用短事务，失败先回滚再继续。

## 写库方式

每分析完一张照片立即写库并 COMMIT，用 UPSERT：

```sql
INSERT INTO photo_scores (path, caption, ...) VALUES (...)
ON CONFLICT(path) DO UPDATE SET caption = excluded.caption, ...
```

不用 `INSERT OR REPLACE`，原因是后者在 `path` 冲突时是「删旧行 + 插新行」，
会让自增 `id` 变化，导致 WebUI 的 `/api/photo/<id>` 链接在重新分析后失效。
UPSERT 原地更新，`id` 保持不变；`used_at` 不在更新列表里，因此重新分析不会清掉展示记录。

## 云端 API 对接要点

- 接口按 OpenAI 兼容协议，鉴权用 `Authorization: Bearer $API_KEY`，图片走 base64 内联
- **每张照片消耗 2 次 API 调用**：一次出描述与评分（`call_vlm`），一次出文案（`generate_side_caption`），
  两次都要上传图片。估算额度时按张数 × 2 计算
- **图片只编码一次**：`analyze_single_photo` 在配置覆盖生效期内调用 `encode_image_to_b64`，
  把同一份 base64 分别传给 `call_vlm(path, image_b64)` 与 `generate_side_caption(path, image_b64)`。
  两个函数的第二参数省略时仍自行编码，因此只重写文案的 `generate_narration` 任务不受影响。
  编码包含解码、方向纠正、缩放与 JPEG 重编码，2000 万像素原图上单次约 400 毫秒，
  省掉的这一次对全量导入是纯收益；编码失败在两次模型调用之前抛出，不会浪费额度
- 部分平台的模型名需带 provider 前缀（如小米大模型平台要 `tongyi/qwen3-vl-30b-a3b-instruct`，
  只填 `qwen3-vl-30b-a3b-instruct` 会返回 400 `Unsupported model`）。
  可用 `GET /v1/models` 查询，模型名 = `owned_by/id`

## 性能参考

- 本地 30B 模型：约 30-120 秒/张
- 云端 API（qwen3-vl-30b 档位，长边 1568）：实测约 3-5 秒/张，单次约 1200 image tokens
