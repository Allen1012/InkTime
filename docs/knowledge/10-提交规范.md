# 提交规范

本项目采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/) 规范。

## 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `<type>`、`<subject>` 必填；`<scope>`、`<body>`、`<footer>` 选填。
- header（首行）不超过 50 字，结尾不加句号。

## type（必填，小写）

| type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(admin): 照片管理增加添加时间排序` |
| `fix` | Bug 修复 | `fix(render): 修复选片算法空指针` |
| `docs` | 仅文档/知识库 | `docs: 补充部署说明` |
| `refactor` | 不改行为的重构 | `refactor(auth): 拆分鉴权逻辑` |
| `perf` | 性能优化 | `perf(query): 优化列表查询避免全表扫描` |
| `test` | 测试增改 | `test(upload): 补充上传边界单测` |
| `chore` | 构建/依赖升级/杂务 | `chore: 升级依赖版本` |
| `ci` | CI/CD 配置 | `ci: 调整流水线部署阶段` |
| `style` | 仅格式（不改行为） | `style: 统一缩进与格式` |

## scope 词表

`admin` / `analysis` / `render` / `server` / `worker` / `display` / `esp32` / `config` / `db` / `upload` / `trash` / `auth`

scope 用变更集中的模块名，新增模块时同步更新本表。

## subject

- 用动词开头，说清「做了什么」，中文即可，结尾不加句号。
- ❌ 反例：`优化代码`、`修改注释`、`添加日志`（太含糊）
- ✅ 正例：`fix(worker): 修复重试逻辑死循环`、`feat(admin): 新增手机号登录`

## body（选填）

写「为什么」改、背景与设计取舍，空一行后书写。涉及对外接口/公共 API 变更时强烈建议补充。

## footer（选填）

- 关联单号：`Refs: #123` 或 `Closes #123`
- 破坏性变更：`BREAKING CHANGE: <说明>`，或用 `feat!:` 的 `!` 简写

## 版本号策略

type 不驱动版本号，仅用于历史可读性。版本号由 git tag 独立管理。

## 分支命名

```
<type>/<负责人>_<说明>_<日期MMDD>
```

示例：`feat/meng_admin-date-range_0813`、`fix/meng_es-npe_0701`

- type 与提交一致（`feat` 而非 `feature`）
- 三段用 `_` 分隔，说明内部用 `-` 连接
- 负责人用小写字母/数字；日期用 `MMDD`（4 位）或 `YYYYMMDD`（8 位）
- 校验正则：`^(feat|fix|docs|refactor|perf|test|chore|ci|style)/[a-z][a-z0-9]*_.+_([0-9]{4}|[0-9]{8})$`
- `master`/`main`/`dev`/`release/*` 长期分支自动放行

## 执行流程（人机协同）

1. AI 生成提交信息并 `git commit`，**绝不自动 push**
2. 人工审阅后 push
3. 返工/review 修改一律追加新提交
4. 禁止对已 push 的提交 `--amend` / `rebase`
5. MR 标题同样遵循 `<type>(<scope>): <subject>` 格式

## 校验钩子

本项目通过 `scripts/git-hooks/commit-msg` 和 `scripts/git-hooks/pre-push` 进行本地校验。

安装：

```bash
./scripts/install-git-hooks.sh
```

安装后提交信息格式和分支名会自动校验，不符合规范的提交/推送会被拒绝。
