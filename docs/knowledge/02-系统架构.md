## 阶段 5 上传与后台任务

后台上传采用 `Blueprint → UploadService → AdminJobRepository`。整批文件先写入 `IMAGE_DIR/.upload-staging`，在原始文件仍可读时提取拍摄时间、GPS 与相机字段；随后在 `IMAGE_DIR/uploads/YYYY/MM` 中创建系统专属临时文件，用 Pillow 解码、核对格式、固化可交换图像文件格式（EXIF）方向并重编码。临时文件完成 `flush + fsync` 后计算最终字节 SHA-256，再以 `os.replace` 原子发布到随机正式名。整批校验失败不会创建照片、任务或正式文件；数据库单事务失败会反向删除本批正式文件。启动时只清理由本系统专属后缀标识的孤儿临时文件。

独立入口 `python -m src.analysis.run_worker` 按优先级原子认领任务，租约 120 秒、每 30 秒续租，过期任务可恢复。认领事务同时递增 `photo_scores.version`、切换分析状态并刷新 `admin_jobs.photo_version`。模型和图片处理期间不持有数据库事务。worker 与批量脚本复用 `src.analysis.photo_analyzer` 的单张分析编排；上传时保存的原始拍摄字段会在结果提交前覆盖重编码文件产生的弱兜底值，结果再按认领版本条件写回。历史摘要使用 `backfill_content_hash` 低优先级任务流式处理，遇到取消、停止或高优先级任务会在文件块边界让出，且不会调用视觉语言模型。

## 阶段 6 回收站与显示产物安全发布

阶段 6 在阶段 5 照片任务之外新增独立 `admin_maintenance_jobs` 队列，只允许
`render_display` 和 `cleanup_expired_trash`。两套队列分别保留检查约束、租约、最多三次尝试、
取消、重试和事件；工作进程先轮询维护任务，再轮询照片任务，并对两套任务都做显式类型分派，
未知类型稳定失败，绝不会退化为视觉语言模型分析。

软删除把活动文件不覆盖地移动到照片所属根目录自己的 `<root>/.trash/<photo_id>/`（`IMAGE_DIR` 可配置多个根，回收站按根隔离），数据库事务保存原始路径、
实际回收站路径、删除时间和管理员快照；事务失败会把文件移回。恢复采用相反顺序，原位置存在
文件时返回冲突，数据库失败会反向移回回收站。文件移动前先提交带租约的持久化操作台账；
崩溃对账会把数据库中可能保留的相对路径和台账绝对路径统一解析到 `IMAGE_DIR` 受管区域，
再判断严格业务前态或后态。软删除、恢复、补偿、崩溃对账和永久删除都必须取得按照片编号稳定
命名的跨进程文件锁，并在锁内重新验证操作所有权；失租旧请求与新恢复者不能同时触碰文件。
数据库所有权检查和业务提交仍使用短事务，不会在文件操作期间占用 SQLite 全局写锁。两种成功路径
都会清理月日缓存，并在照片事务内把 `display_artifact_state.blocked` 设为 1、去重创建
`render_display` 任务。

维护工作进程在 `BIN_OUTPUT_DIR` 同文件系统临时目录中完成 7.3 寸四色与 13.3 寸六色两套渲染。
每个产物都携带来源 `photo_scores.id` 清单；全部临时产物完成后逐文件 `os.replace` 到固定兼容名，
再在一个数据库事务校验任务载荷的期望代次 `desired_generation`，将已发布代次 `generation` 设置为该代次、保存 manifest 并解除屏蔽。任一步失败都保持 blocked，
设备下载与 `/files/` 因此不会回退暴露含已删除照片的旧产物。

永久删除不复用维护队列：先单独提交 `purge_requested` 不可逆审计，再删除回收站文件，最后用短事务
写 `purge_completed` 并依次清理 `admin_job_events`、`admin_jobs`、`photo_audit_log`、
`display_stats` 和 `photo_scores`。生命周期审计不对照片建立强外键，因此照片行消失后仍保留。

## 数据流

### 完整数据流向

1. **照片输入** → `analyze_photos_docker.py` 扫描 IMAGE_DIR
2. **AI 分析** → 调用 VLM API，获取描述、分类、评分
3. **EXIF 提取** → PIL + exiftool 获取拍摄时间、GPS、相机信息
4. **城市解析** → 本地 CSV 数据库将 GPS 坐标转为中文城市名
5. **文案生成** → 再次调用 VLM 生成一句话旁白文案
6. **数据库写入** → 所有结果存入 `photo_scores` 表
7. **每日选片** → `render_daily_photo.py` 按月日匹配 + 评分筛选
8. **图像渲染** → 照片 + 文案 + 日期 + 地点 → 480×800 画布
9. **四色抖动** → Floyd-Steinberg 算法量化为黑/白/红/黄
10. **BIN 输出** → 行优先、1字节/像素的二进制文件
11. **ESP32 下载** → HTTP GET 获取 .bin 文件
12. **墨水屏刷新** → SPI 驱动写入像素数据

### 运行时序与部署拓扑

```text
[受控升级 - 仅运维显式执行]
  scripts/database_admin.py backup
    → 对一致性副本执行 migrate / verify
    → 对受控目标显式执行 migrate
    → check-schema 只读确认当前结构

[常驻运行 - systemd]
  inktime-schema.service（oneshot）
    → scripts/database_admin.py check-schema
    → assert_current_schema；不执行迁移
    ├─成功→ inktime-server.service：python -m src.server.run_server
    └─成功→ inktime-worker.service：python -m src.analysis.run_worker
  server 和 worker 均 Requires/After schema

[Docker Compose 六服务]
  镜像通用入口：python -m src.container_entrypoint
    → 取得 <database>.initialize.lock 排他锁
    → 数据库不存在时完整迁移 50 个版本；已有库只做严格结构检查
  inktime-schema（入口初始化或校验后执行只读 check-schema）
    ├─成功→ inktime-server（常驻 Web，再次经过入口校验）
    ├─成功→ inktime-worker（常驻后台工作进程，再次经过入口校验）
    └─成功→ tools profile：inktime-analyzer / inktime-render-7c / inktime-render-133c

[每天一次 - crontab 触发]
  render_daily_photo.py
    → 读取数据库
    → 选片（历史上的今天）
    → 渲染 + 抖动
    → 输出 photo_0.bin ~ photo_4.bin

[每天定时唤醒 - ESP32 Deep Sleep]
  ink-display-7C-photo.ino
    → 连接 WiFi
    → NTP 同步时间
    → 随机选一张 photo_{0-4}.bin 下载
    → 刷新墨水屏
    → 进入 Deep Sleep

[按需运行 - 手动或定时]
  analyze_photos_docker.py
    → 调用 migrate_database：先校验迁移历史，再补齐缺少的已知迁移
    → 扫描新照片并跳过已分析记录
    → 逐张调用视觉大模型并写入数据库
```

直接运行 Web 服务、后台工作进程或 systemd 单元时，应用只做结构门禁，不自动迁移；Docker 与 Podman 镜像则先经过 `src.container_entrypoint`，仅为完全不存在的数据库自动建库并应用 50 个迁移，已有数据库仍只校验。容器入口还会创建数据库父目录、输出目录和环境变量指定的照片目录。基础 Docker Compose 不依赖 `.env`，统一使用 `/app/data/photos.db`、`/app/data/photos`、`/app/data/output`，并把宿主 `data/` 整体挂载到 `/app/data`。

应用工厂在数据库结构门禁通过后才加载运行时密钥。显式配置的 `SECRET_KEY` 与 `DOWNLOAD_KEY` 优先；缺省时分别从数据库同目录 `.inktime-secret-key` 与 `.inktime-download-key` 读取或在排他锁内原子创建，新文件权限为 `0600`。已有文件不是安全普通文件、权限向组或其他用户开放、内容损坏或不可读时拒绝启动，不会静默覆盖。随后才完成安全配置归一化、输出目录创建和服务注册。

容器入口使用数据库同目录排他锁串行化并发启动，每个等待者取得锁后都会重新检查数据库，准备成功后通过 `os.execvp()` 原样替换为目标进程。迁移执行前与只读 `check-schema` 都复用同一迁移历史校验：本地迁移文件和完整数据库台账必须恰好连续为 1 至 50，并且每个版本的名称与 SQL 文件 SHA-256 校验值必须匹配。未来版本或同版本不同身份的分叉历史会拒绝迁移和应用启动；遇到高版本数据库必须升级程序，不能用旧程序继续写库。

首管理员链路为 `/admin/setup` → `SetupForm` 的跨站请求伪造保护和密码确认 → `AuthenticationService` 按部署策略校验可选初始化令牌、用户名与至少 12 个字符的密码 → `AdminUserRepository` 在一个立即写事务内检查全表为空并插入密码哈希。未配置 `INITIAL_SETUP_TOKEN` 或令牌文件时，可信局域网内首位完成页面的人可创建管理员；配置后仍严格校验，错误令牌返回 HTTP 403。两个不同用户名并发时只能成功一个；存在任意管理员后设置入口返回 HTTP 404。初始化令牌不写入数据库；使用了部署令牌时，成功设置后应删除来源并重启进程。

当前部署文件定义了上述拓扑。历史 Podman 单镜像验收不覆盖当前未构建的家庭局域网零配置改动；Docker Compose 六服务整组、当前镜像产物和 Linux systemd 主机仍未完成新一轮实机验收。

## 信息面板数据层（src/server/panel.py）

为展示页的 `dashboard` 模板提供右侧信息栏数据，与照片主链路解耦：

| 数据块 | 来源 | 联网 |
|--------|------|------|
| 公历日期 | 本地计算 | 否 |
| 农历 / 节气 / 干支 / 传统节日 | lunar-python | 否 |
| 历史上的今天 | 维基百科 feed API + zhconv 繁转简 | 是 |

三条设计约束：

1. **外部数据一律走服务端**。前端直连有跨域问题，且每次切换照片都会重复请求；
   服务端还便于统一缓存
2. **每块独立降级**。任一数据源失败只让对应块 `available=false`，前端隐藏该区域，
   不影响整个面板
3. **缓存分层**。候选池按 月-日 缓存 24 小时，AI 筛选结果单独缓存 24 小时，
   使每天仅需 1 次模型调用

## 展示页选片（src/server/gallery.py）

web 展示页的选片与墨水屏**完全独立**：墨水屏走「历史上的今天」逻辑
（`render_daily_photo.py`，产物是 `.bin`），web 展示页走轮次制随机，
两者互不影响，展示计数也分开记（`display_stats.channel`）。

算法：只从「当前最小展示次数」的照片中加权随机选一张，选中即 +1。
一轮内每张恰好出现一次（覆盖性），轮内随机（新鲜感），
新照片对齐当前轮次基线并在同层内加权（公平性 + 更早出现）。

服务端选片而非前端持有列表，带来两个好处：新入库的照片每次请求都会被查到，
无需定时拉取；前端也不必接收上千条照片元数据。

## 模块间接口

### 数据库与后台认证接口

| 表 | 写入方 | 读取方 |
|----|--------|--------|
| `photo_scores` | analyze_photos_docker.py | render_daily_photo.py, PhotoRepository |
| `display_stats` | gallery.py | gallery.py |
| `admin_users` | `flask --app src.server.app create-admin`、认证服务 | AdminUserRepository、Flask-Login |
| `admin_login_failures` | AuthenticationService | AuthenticationService（跨进程共享滑动窗口） |

`display_stats` 与 `photo_scores` 拆开的原因：前者是运行时展示状态，后者是分析产物。
混在一张表里会让分析脚本的 UPSERT 每次都要小心别覆盖掉展示计数。
`admin_users` 只保存管理员用户名、安全密码哈希、启用状态和登录时间，不保存默认账号或明文密码，
并与照片数据保持独立。

```text

  → AuthenticationService（统一失败提示 + dummy hash + 连续失败限流）
```

## 配置层级

阶段 7 配置核心由独立于 Flask 的 `src/configuration.py` 提供，所有入口共享同一注册表和解析规则：

```text
可热更新配置：app_settings 数据库覆盖值 > 进程启动时捕获的环境或 .env 初始值 > 注册表默认值
系统与一般敏感配置：显式进程环境 > 项目 .env > 注册表默认值
运行时密钥：显式 SECRET_KEY / DOWNLOAD_KEY > 数据库同目录持久化密钥文件
```

`SECRET_KEY` 与 `DOWNLOAD_KEY` 不属于数据库热配置。应用在数据库结构门禁通过后，才为未显式配置的值读取或原子创建 `.inktime-secret-key` 与 `.inktime-download-key`；新文件权限为 `0600`。文件异常、权限向组或其他用户开放、内容含空白或长度不足时拒绝启动。

`SettingDefinition` 为每项配置声明类型、范围、枚举、敏感性、是否可编辑、是否需要重启和任务生效范围。`ConfigurationService` 每次访问先读取 `app_settings.version`，仅在版本变化时重载 `settings_json`，避免进程间缓存长期不一致。管理端批量更新先完成整批校验，再由 `SettingsRepository` 在一个 `BEGIN IMMEDIATE` 事务内更新配置、递增全局版本并写入 `app_settings_audit`；过期版本返回冲突，不会部分写入。

需要热生效的服务不再把配置冻结在构造参数上：上传上限、任务尝试次数、租约与续租间隔、轮询间隔、回收站保留天数、两个浏览开关都改为在方法内按需读取，构造参数只作为未注入配置服务时的回退值。因此 Web 与工作进程都能感知对方触发的配置变更，无需重启任一进程。

敏感配置只暴露“已配置/未配置”，不返回真实值，也不进入审计或任务快照；`API_KEY` 可在线只写覆盖，因此它是唯一会以明文进入数据库热配置的敏感项。`admin_jobs` 和 `admin_maintenance_jobs` 在首次认领的同一数据库事务中，分别按 `analysis`、`render` 或 `worker` 作用域保存配置版本与完整非敏感快照。首次认领以认领前 `started_at IS NULL` 判断；租约恢复与自动重试不会改写快照，确保同一张照片不会分析途中被换掉模型。**人工重试例外**：`retry()` 清空 `started_at`，下次认领按当前配置重新固化快照，因为使用者对「重试」的预期是「用现在的状态再来一次」；任务历史仍由 `admin_job_events` 完整保留。分析与两套渲染入口在模块级重入锁内临时应用快照并在 `finally` 恢复旧模块全局值；模型密钥不进入快照，由工作进程在调用前按当前生效配置（数据库热值优先，其次启动环境）单独传入。仅升级前已经启动且仍为版本 0、空 JSON 的任务按当前配置兼容执行，其他损坏快照统一失败为 `invalid_config_snapshot`。

项目 `.env` 是本地脚本和自定义部署的可选启动配置来源，`config/config.py` 已废弃。四个入口脚本都自行 `load_dotenv(override=False)`，因此存在 `.env` 时无需先 `source`，已有进程环境变量不会被覆盖；基础 Docker Compose 不依赖该文件。systemd 仍通过 `EnvironmentFile=` 加载部署配置。

- `analyze_photos_docker.py`：唯一分析入口，纯环境变量驱动。
  用 `load_dotenv(override=False)`，因此 `BATCH_LIMIT=20 python ...` 这类临时覆盖有效
- `render_daily_photo.py` / `render_daily_photo_133c.py`：读环境变量
- `src/server/app.py`：在 `create_app()` 调用期间读取环境变量和 `.env`，完成类型转换、相对路径解析与实例配置；模块导入不创建应用

> 注意：`.env` 中含空格的值必须加引号（如 `PROJECT_NAME="InkTime 相册"`），
> 否则 `source .env` 会把值当命令执行而报错。python-dotenv 和 systemd 都能正确处理引号。
